# 知見（ヒューリスティクス）

全プロジェクトで参照する、経験から来る判断基準を置く場所です。仕組みは要件定義書の F-18、使い方は C-56 を参照してください。

## 置き方

```text
knowledge/
├─ frontend/   フロントエンド
├─ backend/    バックエンド
├─ db/         DB
└─ general/    分野をまたぐもの
```

- テーマごとに1ファイルにする（例：`db/sql-complexity.md`）
- 追加・変更はPRで行い、状態の変更には根拠を示す

## 書き方

1つの判断基準ごとに、次の見出しをそろえて書きます。

```markdown
## <判断基準の名前>

- 状態：仮説／検証中／確立／廃止
- 種類：性能／設計

### 基準
判断のルール。AIが迷わないよう、できるだけ機械的に判定できる書き方にする。

### 理由
その基準にした理由。

### 例外
当てはまらない場面と、そのときの判断方法。

### 確かめ方
何を、どの道具で測って確かめるか。
- 性能：知見に従った場合・従わない場合を、同じ条件で実測して比べる
- 設計：代わりの指標（変更時に触ったファイル数、不具合の数、複雑度等）の傾向を見る

### 根拠
実測値や、きっかけになった事例（プロジェクトのADRへのリンク等）。まだない場合は「未検証」と書く。

### 対象
実測・適用した条件の範囲（DB・ライブラリとバージョン、データ量、実行環境等）。

### 適用の記録
| 日付 | プロジェクト | 結果 | 根拠へのリンク |
| --- | --- | --- | --- |
```

## 実測を根拠にするときの注意

実測で言えるのは「その条件の下では効率が良い」までです。詳しいルールは F-18 の「実測を根拠として使うときのルール」を参照してください。

- 測った条件を必ず一緒に記録する
- 何を良くしたいのかと、「意味のある差」の基準を、測る前に決める
- 同じ条件で複数回測り、中央値とばらつきを記録する

知見は絶対のルールではありません。共通仕様（MUST・MUST NOT）が知見より優先します。
