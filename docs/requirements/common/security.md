## C-05：プロジェクトに書き込む標準ルール

ハーネスを使う人（身内を含む）のPCには、作成者個人のグローバル設定（`~/.claude/CLAUDE.md`等）が存在しない。そのため、次の標準ルールは生成するプロジェクトのAI向け設定ファイルに直接含める。[F-04](../functional.md#f-04)に従い、ルールの本体は共通ルールとして1か所で管理し、`CLAUDE.md`・`AGENTS.md`等の各ファイルへはアダプタで出力する。

各ルールの文面は、別途「生成するAI向け設定ファイルの内容」として詰める（未決定事項を参照）。以下は含める内容の骨子である。

### テストデータ（実データ・個人情報の使用禁止）

- 本番・ステージングの実データを、匿名化せずにテストへ持ち込まない
- 実在の個人名、実在しうるメールアドレス・電話番号・住所・カード番号等、本物の認証情報を使わない
- メールアドレス・ドメインは`example.com`等の予約ドメインを使う。氏名は`testuser_001`等の明らかな架空名、パスワードは`TestPass123!`のようなテスト専用の固定値を使う
- テストデータには`testuser_%`などの接頭辞や`[E2E_TEST]`などのタグを付けて識別できるようにし、識別子だけを条件に削除する後始末用スクリプトをセットで用意する
- 本番DBに接続しうる設定でテストを実行しない

### 秘密情報

- DB認証情報・APIキー・トークン等の実際の値は、`.gitignore`で除外したファイル（`.env`等）にだけ置く
- コミットするファイルでは、環境変数展開やプレースホルダで参照する。値の例は`.env.example`にプレースホルダだけを書く
- 「テスト用・開発用だから安全」と判断しない。`password`・`admin`のような推測しやすい値を使わない
- 秘密情報の値は、チャット・コミットメッセージ・PR・Issueの本文にも書かない
- 作業対象外のファイルで秘密情報の直書きを見つけた場合は、勝手に直さず、別のIssueにしてユーザーに知らせる

### ログインUI（アプリ独自認証を選んだ場合）

- パスワード入力欄には、入力内容の表示・非表示を切り替えるボタンを付ける
- 新規登録・パスワード再設定など新しいパスワードを決める画面には確認用の再入力欄を設け、一致しない場合は画面側でエラーを表示してAPIを呼ばない（ログイン画面には確認欄を付けない）

### AIと秘密情報のファイル

- **MUST**：AIは、実際の値が入った秘密情報のファイル（`.env`・`.env.development`・`.env.test`・`.env.production`等）を直接読まない。AIの設定（[C-75](design-principles.md#c-75)・[F-25](../functional.md#f-25)）でも読み込みを禁止する。値の見本の`.env.example`は読んでよい
- **MUST**：足りない項目の確認は、専用のスクリプト（例：`npm run env:check`）で行う。スクリプトは`.env.example`と実際のファイルの**項目の名前だけ**を比べ、足りない項目の名前を表示する。値は一切表示しない
- **MUST**：利用者から「設定で足りないものは」と聞かれたら、AIはこのスクリプトを実行し、項目の名前だけで答える
- **MUST**：秘密情報の値は利用者が入力する。AIは入力の手順とコマンドを案内するだけで、値を扱わない。秘密情報を入力するコマンド（`wrangler secret put`・`gh secret set`等）は、AIではなく利用者自身がターミナルで実行する（AIが実行すると、入力した値がAIとの会話に残る可能性があるため）

### 秘密情報の入力の手順

生成するプロジェクトの`docs/secrets.md`に、次の手順を書く。

| 環境 | 手順 |
| --- | --- |
| 開発・検証（手元のPC） | `.env.example`をコピーして`.env.development`・`.env.test`を作る → エディタで値を書く → `npm run env:check`で足りない項目がないことを確かめる → コンテナを起動し直す（[C-40](project-env.md#c-40)） |
| 本番（Cloudflare） | `wrangler secret put <項目名>`を利用者が実行し、聞かれた値をその場で入力する → `wrangler secret list`で項目の名前を確かめる。本番の値は手元の平文のファイルに置かず、控えておく場合はパスワード管理ソフト等の暗号化された保管場所に置く（[C-40](project-env.md#c-40)）。Cloudflare上に検証の環境を足した場合は、`--env <環境>`を付ける |
| CI（GitHub Actions） | GitHubの設定画面（Settings → Secrets and variables → Actions）で登録する。または`gh secret set <項目名>`を利用者が実行して入力する |
| Terraform | 秘密情報はコードに書かず、環境変数（`TF_VAR_<項目名>`）で渡す |

- 値をチャットに貼らない。スクリーンショットにも写さない

## C-09：個人情報の取扱いとアプリケーションセキュリティ

- 個人情報保護法および個人情報保護委員会ガイドラインを法令・規制上の基準として扱い、JIS Q 15001:2023とISO/IEC 27701:2025を個人情報保護マネジメントの参照基準として活用する。
- アプリケーションの技術的なセキュリティ要件と検証にはOWASP ASVSを参照する。ASVSのレベルは、プロジェクトに関する質問への回答から判定する（判定の方法は[F-26](../functional.md#f-26)）。
- チェックリストには、各項目の回答と、その回答がレベル判定にどう影響したかを記録できるようにする。具体的な質問、判定基準、該当しない項目の扱いは別途定める。
- 参照する法令・ガイドライン・規格・ASVSの版を明記し、法令や参照資料が改定された場合に見直せるようにする。
- これらの基準を参照して要件を生成することは、法令適合、規格適合または認証取得を保証するものではない。

<a id="c-12"></a>

## C-12：認証方式の選択

- 認証方式は「認証なし」「アプリ独自認証」「外部IdPによるOIDC認証」「アプリ独自認証とOIDC認証の併用」から選択できるようにする。
- 認証なしを選ぶ場合は、認証を必要としない公開対象を明示する。
- 外部IdPを利用できる場合はOIDC認証を推奨する。アプリ独自認証を選ぶ場合は、パスワードや認証情報の保護、ログイン試行への対策、認証情報の再設定、セッション管理等の追加要件を適用する。具体的な要件は認証方式と技術スタック別の設計で定める。
- 併用する場合のアカウント連携、重複アカウントの扱い、認証手段の追加・解除等は、別途設計する。

<a id="c-13"></a>

## C-13：認可の基本原則

- 認可はデフォルト拒否とし、明示的に許可した操作だけを実行できるようにする。認証不要で公開するAPIや機能は、その対象を明示する。
- 認証が必要なAPIでは、バックエンドが各リクエストで利用者と対象リソースに対する操作権限を確認する。
- フロントエンドで画面や操作ボタンを非表示にすることは、認可の代わりにならない。画面表示の制御とは別に、バックエンドで認可を強制する。

<a id="c-14"></a>

## C-14：認可範囲の定義

- 認可要件では、誰が（主体）、何を（操作）、どのリソースに対して行えるかを定義する。必要に応じて、テナント・組織・所属・状態などの条件も含める。
- 認可条件には、認証済みであること、ロールやグループ、リソースの所有者・所属関係などを組み合わせて使える。全プロジェクト共通の「一般利用者」ロールや固定のロール名は必須にしない。
- 管理者ロールは全プロジェクトで必須とはしない。管理者向け機能を設ける場合は、機能要件ごとに管理者が行える操作と対象データの範囲を定義し、「管理者」を無制限の権限として扱わない。
- 複数人でアプリ内のデータや設定を作成・編集する機能では、機能要件に所有単位（個人・チーム・組織等）と、共同編集を許可する利用者の範囲・操作を定義する。作成者、所有者、共同編集者は同一とは限らないため、必要に応じてそれぞれ区別する。
- ログインしたことだけで、すべての機能やデータへのアクセスを許可してはならない。利用者ID・ロール・テナントID等の権限判断に使う値は、クライアントから送られた値をそのまま信用せず、認証済み主体やサーバー側の情報から取得・検証する。
- 権限の付与・変更・取り消しも保護対象の操作として扱い、機能要件で実行できる主体、対象者、変更可能な権限と範囲を定義する。権限管理者の階層や委任範囲はプロジェクトごとに定め、最上位の管理者だけが変更できる構成も、下位管理者が許可された範囲で管理できる構成も選べるようにする。
- 管理者が自分自身の権限を不正に引き上げたり、許可範囲を超えて他者へ権限を付与したりできないよう、バックエンドで現在の主体と委任範囲を検証する。
- 認証を要求する機能で認可範囲が要求に定義されていない場合は、権限の不足としてユーザーに確認する。確認が済むまでは、該当する保護対象の操作を拒否する。
- リソースIDを指定して取得・変更・削除する操作では、そのリソース単位で毎回権限を確認する。一覧取得では、利用者がアクセスできる範囲に結果を絞る。
- 認可テストでは、未認証、許可された主体、許可されていない主体、異なる所有者・所属のリソースを使い、閲覧・作成・更新・削除などの操作ごとに許可／拒否を確認する。共同編集機能では、所有者・許可された共同編集者・許可されていない利用者の境界を確認する。
- 権限管理機能がある場合は、許可された主体による権限変更に加え、自己昇格、委任範囲を超えた付与、上位管理者の権限変更など、要件上許可されない操作が拒否されることをテストする。

<a id="c-16"></a>

## C-16：セッションとログアウトの範囲

- アプリケーションからログアウトするときは、認証方式にかかわらず、アプリケーション自身のセッションをクライアントとサーバーの両方で終了・無効化する。
- OIDCを利用する場合、アプリケーションのセッションと外部IdPのセッションは別のものとして扱う。アプリケーションからログアウトしてもIdP側のセッションが残り、次回ログイン時に利用者が再認証せずアプリケーションへ戻る場合があることを前提とする。
- IdP側のセッションも終了させるかどうかはプロジェクトごとに明示する。IdPからのログアウトは、同じIdPを使う他のアプリケーションの利用にも影響し得るため、アプリケーションのログアウトと常に一体の動作にしてはならない。
- OIDCのログアウト範囲を選択した場合は、ログアウト後の画面遷移、IdP側セッションの状態、次回ログイン時の再認証または自動ログインの挙動を確認し、テストする。利用者にとってログアウト完了の意味が分かるように案内する。
- アプリ独自認証とOIDCを併用する場合も、どの認証方法でログインしたかにかかわらずアプリケーション自身のセッションは終了する。IdP側セッションの終了は、OIDCログアウト方針に従って別途扱う。

<a id="c-17"></a>

## C-17：アプリケーション発行トークンのライフサイクル

- アクセストークンとリフレッシュトークンの組み合わせは、アプリケーション独自認証で必須とはしない。サーバー側セッション等を含め、クライアント種別とシステム構成に適した方式を選ぶ。アプリケーションがこのトークン方式を採用する場合は、以下を適用する。
- アクセストークンは必要な用途・対象に限定し、漏えい時の悪用可能時間を抑える有効期間を設定する。リフレッシュトークンにはアイドル期限または最長有効期間を設け、具体的な期間はリスク、利用形態、クライアント種別を根拠に技術設計で決定する。
- リフレッシュトークンを発行する場合は、更新ごとに新しいトークンを発行して旧トークンを無効化するローテーションを行う。無効化済みトークンの再利用を検知した場合は、同一セッション／トークン系列を失効させ、再認証を要求する。複数タブ・同時リクエストで正当な更新が競合しないよう、更新処理を調整する。
- リフレッシュトークンの更新期限を延長する場合も、初回認証時に定めた最長有効期間を超えて無期限に延長してはならない。アイドル期限と最長有効期間をどのように組み合わせるかは、認証方式別の設計に記録する。
- ログアウト、アカウント停止、認証情報の変更・漏えい等でセッションを終了する際は、該当するリフレッシュトークンと関連セッションをサーバー側で失効させる。アクセストークンの有効期限が残る間の扱い（短い有効期間、失効照会等）も明示する。
- トークン方式を採用する場合、トークンの保存場所・送信方法をクライアント種別ごとに決める。ブラウザーでは、JavaScriptから読み取れるWeb Storageへ認証トークンを保存せず、BFFまたは適切なCookie等の保護策を検討する。
- アプリケーション発行トークンと外部IdP発行トークンは、発行者、用途、対象（audience）、署名鍵、更新・失効管理を分離する。外部IdPのIDトークンをアプリのAPI用アクセストークンとして扱わず、受信する各トークンの発行者・署名・対象・有効期限・用途を検証する。OIDCログイン後にアプリ独自のセッションまたはトークンを発行する場合は、そのライフサイクルをIdP側のトークンとは別に定義する。
- 権限変更の反映をトークン内の古いロール情報だけに依存させない。保護対象の操作ではC-13・[C-14](#c-14)に従って権限を確認し、即時反映が難しい構成を採用する場合は、反映までの時間差と補完策を明示する。
- トークンの有効期限・更新成功／失敗・ローテーション・旧トークン再利用・ログアウト後の利用・アカウント停止後の利用・権限変更後の操作をテストする。期限切れ時の画面動作はC-15、ログアウトの範囲はC-16にも従う。

<a id="c-18"></a>

## C-18：認証情報・認証要素の回復

- OIDCを利用する場合、IdPが管理するパスワード、MFA等の認証情報・認証要素の回復はIdPの手続きに委ねる。アプリケーションはIdPの回復機能を独自に代行・迂回しない。
- アプリ独自認証で管理するパスワードや認証要素の回復は、アプリケーションの責任として設計する。OIDCとアプリ独自認証を併用する場合は、どの認証手段を回復する手続きなのかを利用者に明示し、相互に取り違えない。
- アプリ独自のパスワード再設定では、アカウントの有無を第三者に推測されにくい応答とし、再設定用トークン／コードを推測困難・一回限り・期限付きにする。再設定の要求だけでアカウントを変更・停止せず、有効な再設定証明を確認してから変更する。
- 回復手続き完了後は利用者へ通知し、回復後の自動ログインを既定にしない。通常の認証手続きを行わせる。回復前のセッションやリフレッシュトークンを失効させる方針を定め、関連する挙動をテストする。
- MFA等の認証要素を回復・交換する場合は、既存要素を利用できない状況も想定した本人確認方法を設計する。回復手続きが通常の認証より弱い経路にならないようにし、変更後の通知とセッションの扱いを定める。
- OIDCの回復先、アプリ独自回復の手順・有効期限・試行制限・通知方法・セッション失効範囲は、認証方式と機能要件に応じて具体化し、正常系と不正・期限切れ・再利用等の拒否ケースをテストする。

<a id="c-19"></a>

## C-19：ログイン試行制限とセキュリティ通知

- アプリ独自認証のログイン、パスワード再設定、認証要素の確認・回復など、オンラインで秘密を試せる処理には、総当たり・自動化された試行を抑えるレート制限を設ける。制限はアカウント単位を基本とし、IPアドレス・端末・挙動等の信号も組み合わせて回避と誤検知の両方を抑える。
- 失敗回数の閾値、観測期間、待ち時間、解除条件は一律の共通数値に固定せず、認証方式、利用者数、扱う情報の重要度、攻撃リスクに応じて技術スタック別に定める。失敗が続く場合は待ち時間を段階的に延ばす方法等を検討し、恒久的なアカウントロックを自動適用することを既定にしない。
- 制限の設計では、第三者が他人のアカウントを意図的にロックして利用を妨害できないようにする。登録アカウントの有無をログイン応答から推測されにくくし、試行制限によって正当な利用者が締め出された場合の安全な回復手段を用意する。
- 個人情報や重要データを扱うなどリスクが高いアプリでは、不審な試行の集中や強い制限の発動を、登録済みの連絡先等へ通知する方法を設ける。通知頻度を抑制・集約し、通知機能自体が大量送信攻撃に利用されないようにする。
- セキュリティ通知は不審な事象を知らせるものであり、それだけでログインを承認したり、本人確認を完了したり、制限を解除したりしてはならない。追加の本人確認やアカウント回復は、[C-18](#c-18)に従う別の安全な手段で行う。通知には心当たりがない場合の次の行動を分かりやすく示す。
- OIDC認証のログイン試行制限は原則としてIdP側の機能・ポリシーに委ね、アプリ側で独自に迂回・重複した制限を設けない。アプリ独自認証を併用する場合は、アプリ独自認証の経路に本項を適用する。
- 試行制限の境界値、待ち時間、解除・回復、通知の発生条件と頻度、アカウント有無の秘匿、正当なログインへの影響をテストする。具体的な回数・期間・通知先・通知方法は技術スタック別の設計時に決定する。

<a id="c-20"></a>

## C-20：多要素認証（MFA）と重要操作の再認証

- MFAを全利用者に必須とするか、任意とするか、特定の利用者・機能だけで要求するかは、扱う情報、操作による影響、想定される攻撃、利用者層および運用負荷を踏まえたリスク評価で決定する。簡易的なアプリであっても、MFAの適用要否を検討せずに省略してはならない。
- 管理者・高権限利用者については、アカウント乗っ取り時にできる操作と影響範囲を評価し、MFAを必須とするかを明示的に決定する。利用者やデータが広範囲に及ぶサービス、個人情報・金銭・設定変更等を扱うサービスでは、管理者MFAを原則として要求する方向で検討する。
- パスワードや認証要素、登録メールアドレス、権限、送金・公開・削除等の重要な操作では、現在のログイン状態だけで足りるかを評価し、必要に応じてMFAまたは再認証（step-up authentication）を求める。対象操作と必要な認証強度は機能要件で定義する。
- OIDCを利用する場合は、IdPで行われたMFAまたは再認証をどの条件で受け入れるか、アプリ側で追加確認が必要な条件は何かを定める。アプリ独自認証の場合は、採用するMFA方式、認証要素の追加・交換・回復をC-18に従って設計する。
- MFAや再認証の要求、失敗、認証要素の追加・変更・解除、回復をテストする。認証の強さが不足する場合は、重要操作を実行させない。

<a id="c-27"></a>

## C-27：入力チェックとXSS対策

- 入力チェックは必ずバックエンドで行う。画面側のチェックは利用者の補助であり、代わりにならない
- SQLはライブラリのパラメータ機能（プレースホルダ）で組み立て、文字列の連結で作らない（詳しくはC-72）
- 画面への出力はフレームワークの自動エスケープに任せる。`dangerouslySetInnerHTML`などエスケープを外す書き方は原則禁止し、やむを得ず使う場合は信頼できるサニタイズ処理を通して、理由を記録する
- 利用者が入力したURLをリンク等に使う場合は、`http:`・`https:`など許可したスキームだけを受け付ける（`javascript:`等を拒否する）
- CSP（Content Security Policy）ヘッダーを設定し、読み込んでよいスクリプトの出どころを制限する。具体的な設定値は技術スタック別に定める

<a id="c-28"></a>

## C-28：HTTPメソッドの安全性とCSRF対策

- GET・HEAD・OPTIONSでは、DBの更新・ログアウト・メール送信など、状態を変える処理をしない（RFC 9110の安全なメソッド）。状態を変える操作は、POST・PUT・PATCH・DELETEで行う
- 認証にCookieを使う場合は、`SameSite=Lax`を標準とし、あわせて`Secure`・`HttpOnly`を付ける。`SameSite=None`はクロスサイトでの利用が必要な場合に限り、理由を記録する
- `SameSite=Lax`は、別サイトからのリンクによるGETの画面遷移ではCookieを送るため、上記の「GETで状態を変えない」ルールとセットでCSRF対策として扱う
- SameSiteは同じサイトの別サブドメインからのリクエストを防げないため、状態を変えるリクエストでは`Origin`ヘッダー（またはCSRFトークン）も確認し、許可していない送信元からの要求を拒否する

### 必須のテスト（結合テスト）

- **GETで状態が変わらないこと**：すべてのGETのAPIを呼び出し、呼ぶ前と後でDBの内容が変わっていないことを確認する。対象のAPIはテストコードに手で列挙せず、アプリのルーティング定義から取得して、APIの追加時にテストの漏れが出ないようにする
- **CSRF対策が効いていること**：状態を変えるAPIに、許可していない`Origin`や`Origin`なしで要求したときに拒否されること、許可した`Origin`からは成功することを確認する
- **Cookieの属性**：ログイン等で発行するCookieに`SameSite`・`Secure`・`HttpOnly`が意図どおり付いていることを確認する

<a id="c-29"></a>

## C-29：CORSの設定

- 画面とAPIを同じオリジン（同じドメイン）から配信する構成を標準とする。この場合、CORSは許可しない
- 別のオリジンから呼び出す必要がある場合だけCORSを許可し、許可する送信元（Origin）を明示的に列挙する。次の設定は禁止する
  - 認証情報（Cookie等）を送る設定で、`Access-Control-Allow-Origin: *`を返す
  - 要求の`Origin`を確認せずに、そのまま`Access-Control-Allow-Origin`に返す
  - `null`のOriginを許可する

### 必須のテスト（結合テスト）

- 許可したOrigin・許可していないOrigin・`null`・`Origin`なしのそれぞれで要求し、`Access-Control-Allow-Origin`・`Access-Control-Allow-Credentials`が意図どおりであることを確認する
- 事前確認（preflight、`OPTIONS`）の要求に対して、許可するメソッド・ヘッダーが必要最小限であることを確認する
- CORSを許可しない構成では、CORSを許可するヘッダーを返していないことを確認する
- 結合テストで確認できるのはアプリ側の設定だけである。Cloudflare等のインフラ側でヘッダーを追加・変更している場合は、デプロイした環境に対しても同じ確認を行う

<a id="c-63"></a>

## C-63：ファイルのアップロードと保存

アプリに含める画像（ロゴ・アイコン等）はアプリと一緒にデプロイし、ここでは**利用者がアップロードするファイル**（写真・動画・文書等）を対象とする。

### 公開範囲

- **MUST**：保存場所（R2のバケット等）とファイルは、**すべて非公開をデフォルト**とする
- **MUST**：ファイルを配信するときは、アプリが権限を確認してから配信するか、期限の短い一時的なURLを発行する（[C-13](#c-13)）
- 公開にしたいファイルがある場合は、後から公開に切り替える。その場合は次を守る
  - 公開する理由と対象をADR（[C-35](workflow.md#c-35)）に記録し、承認を得る
  - 公開用と非公開用の保存場所を分け、同じ保存場所に混ぜない
  - 公開する場合も、書き込み・削除はアプリからだけ行えるようにする

### アップロードの方法

| 方法 | 使うとき |
| --- | --- |
| アプリのサーバーを経由する（標準） | 画像など小さめのファイル。サーバーで中身を確認してから保存する |
| ブラウザからストレージへ直接送る | 動画など大きいファイル。サーバーが期限付きのアップロード用URLを発行し、ブラウザはそのURLへ直接送る。アップロードの完了後に、サーバーで中身を確認する |

- 実行環境が1回のリクエストで受け取れるサイズの上限（Cloudflare Workersは契約プランによって異なる）を超えるファイルは、直接送る方式にする。具体的な上限は技術スタック別に確認する

### 安全対策

- **MUST**：ファイルの種類ごとにサイズの上限を決め、画面側とサーバー側の両方でチェックする（[C-47](frontend.md#c-47)）
- **MUST**：拡張子やブラウザが申告する形式を信用せず、ファイルの先頭の中身で形式を判定する。許可した形式だけを受け付ける
- **MUST**：利用者が付けたファイル名を、保存場所の名前に使わない。ランダムな名前を付ける
- **MUST**：写真の撮影場所などの情報（Exif）を削除してから保存する（[C-09](#c-09)）
- **MUST NOT**：SVGなどスクリプトを含み得る形式を、原則として受け付けない。受け付ける場合は、画面に直接表示せずダウンロードさせる扱いにする（[C-27](#c-27)）
- **MUST**：利用者ごとの保存容量の上限と、アップロードの回数の制限を設ける（[C-59](#c-59)）
- **MUST**：データの削除時・退会時に、関係するファイルも削除する。DBとストレージの食い違い（どこからも参照されないファイル）を定期的に掃除する

### 動画

- アップロードされた動画をそのまま再生するだけなら、通常の保存先（R2等）で扱う
- 再生用の形式への変換や、通信速度に合わせた画質の切り替えが必要な場合は、動画専用のサービス（Cloudflare Stream等）を使うかをプロジェクトごとに検討し、ADRに記録する

### 必須のテスト

- 上限を超えるファイル、許可していない形式、拡張子を偽ったファイルが拒否されること
- 権限のない利用者・未ログインの利用者が、ファイルを取得できないこと
- 保存したファイルに位置情報が残っていないこと
- データの削除時に、関係するファイルも削除されること

<a id="c-58"></a>

## C-58：セキュリティヘッダー

CSP（[C-27](#c-27)）に加えて、すべての応答に次のヘッダーを付ける。

| ヘッダー | 値 | 目的 |
| --- | --- | --- |
| `Strict-Transport-Security` | `max-age=31536000; includeSubDomains` | 常にHTTPSで通信させる |
| `X-Content-Type-Options` | `nosniff` | ファイルの種類の勝手な推測を防ぐ |
| CSPの`frame-ancestors`と`X-Frame-Options` | `'none'`と`DENY` | ほかのサイトへの埋め込み（クリックジャッキング）を防ぐ |
| `Referrer-Policy` | `strict-origin-when-cross-origin` | 別のサイトへ移るときに、URLの詳細を渡さない |
| `Permissions-Policy` | 使わない機能（カメラ・マイク・位置情報等）を無効にする | 不要なブラウザの機能を使わせない |
| `Cache-Control`（認証が必要なAPI・個人向けのデータ） | `no-store` | 個人向けのデータをキャッシュに残さない（[C-10](backend.md#c-10)） |

- 他のサイトへの埋め込みが必要な機能を作る場合は、許可する埋め込み元を明示し、理由をADR（[C-35](workflow.md#c-35)）に記録する

### 必須のテスト（結合テスト）

- 主要な応答に、上記のヘッダーが意図どおりの値で付いていることを確認する
- Cloudflare等のインフラ側でヘッダーを追加・変更している場合は、デプロイした環境に対しても同じ確認を行う

<a id="c-59"></a>

## C-59：APIのレート制限

ログイン等の認証の試行制限（[C-19](#c-19)）に加えて、API全体にレート制限を設ける。

- **MUST**：公開するAPIすべてにレート制限を設ける。ログインしている場合は利用者ごと、ログインしていない場合はIPアドレスごとに数える
- **MUST**：重い処理（検索、データの書き出し、メール送信、ファイルのアップロード等）には、通常より厳しい制限を設ける
- **MUST**：制限を超えた場合は`429`と`Retry-After`ヘッダーを返し、利用者には「しばらく待ってから再試行する」ことを案内する（[C-15](error-response.md#c-15)）
- 制限の値は、プロジェクトの利用規模に応じて決める。インフラの入口（エッジ）で制限するか、アプリで制限するかは技術スタック別に定める
- **MUST**：制限の境界値（上限ちょうど・上限を超えた場合）と、制限が解除されることをテストする
- **MUST**：E2Eでは、レート制限のあるAPIの呼び出しを必要最小限にする。E2Eは同じ送信元から続けて実行されるため、途中で上限に達して失敗しやすい。レート制限そのものの検証は、バックエンドのテストで行う

<a id="c-72"></a>

## C-72：SQLインジェクション対策

- **MUST**：SQLに値を入れるときは、必ずライブラリのパラメータ機能（プレースホルダ）で渡す。利用者の入力を、文字列の連結・テンプレート文字列でSQLに埋め込まない
- **MUST**：生SQL（[C-03](backend.md#c-03)の`*.sql.ts`等）を書く場合も、値はパラメータで渡す。ライブラリが用意している、値をそのまま埋め込む機能（Drizzleの`sql.raw`等）に、利用者の入力を渡さない
- **MUST**：並び替えの列名・並び順（`ASC`／`DESC`）・テーブル名など、パラメータで渡せない部分を入力で変える場合は、許可した値の一覧（許可リスト）と照合し、一覧にある値だけを使う
- **MUST**：`LIKE`で検索する場合は、入力に含まれる`%`・`_`を無害化してから、パラメータで渡す
- **MUST**：`IN`の条件に複数の値を渡す場合も、値を1つずつパラメータで渡す
- **SHOULD**：アプリがDBに接続するユーザーの権限は、必要な操作だけに絞る（テーブルの削除等の権限を与えない）
- **MUST**：検索・並び替えなど入力をSQLに使う処理では、SQLインジェクションを狙った入力（`'`・`;`・`--`・`OR 1=1`等を含む値）を渡しても、意図しない結果にならないことをテストする
