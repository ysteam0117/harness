<a id="c-36"></a>

## C-36：開発環境のDockerコンテナ

- バックエンドとDBの開発環境は、Docker（Docker Compose）のコンテナで動かす。開発者のPCに直接インストールする必要があるものを減らし、誰の環境でも同じ状態で動かせるようにする
- DBがCloudflare D1の場合は、開発ツール（wrangler）がローカルでSQLiteファイルとして再現するため、DB専用のコンテナは作らず、バックエンドのコンテナの中で扱う。PostgreSQLの場合は、DB用のコンテナを作る

### D1を使う場合の開発環境（本番と互換性のある構成）

D1を最初から使う場合は、本番と同じ実行環境をローカルで再現できるため、次の方式を標準とする。

| 項目 | 方式 |
| --- | --- |
| 実行環境 | バックエンドのコンテナ内で`wrangler dev`をローカルモードで動かす。本番のCloudflare Workersと同じ実行エンジン（workerd）でHonoのアプリが動く |
| DB | wranglerがローカルに再現するD1（SQLiteファイル）を使う。本番のD1と同じSQLite系のSQLで動く |
| データの保持 | ローカルのD1のデータ（`.wrangler/state`）は、Dockerのボリュームで保持し、コンテナを作り直しても消えないようにする。このフォルダはコミットしない |
| マイグレーション | 本番と同じマイグレーションファイルを使い、まずローカルに適用して確認してから、本番に適用する |
| テスト | 結合テストも同じローカルのD1に対して実行し、テストごとに初期状態へ戻せるようにする |

- 開発・テストでは、本番のD1に接続する設定（`--remote`等）を使わない（[C-05](security.md#c-05)のテストデータのルール）。本番への適用は、デプロイの手順としてユーザーの承認を得て行う
- ローカルのD1は、本番と比べてデータ量・性能・利用上限が異なる。実行計画の確認（[C-10](backend.md#c-10)）はローカルで行えるが、性能の最終判断は実運用に近いデータ量で行う
- 使うツールのバージョンと具体的な設定（`wrangler.toml`の書き方、テストの実行方法等）は、技術スタック別に定める

### 命名規則

- Docker Composeのプロジェクト名（`name:`）をアプリ名にする
- コンテナ名は `<アプリ名>-<役割>` にする（例：`myapp-backend`、`myapp-db`）。コンテナが1つだけの場合も役割を付けてそろえる
- アプリ名は英小文字・数字・ハイフンで書く
- DBの認証情報などは`docker-compose.yml`に直接書かず、`.env`から読み込む（[C-05](security.md#c-05)）

<a id="c-39"></a>

## C-39：本番環境の構築（IaC）

- 本番環境（Workers・D1・R2・DNS・環境変数の設定など）は、管理画面での手作業ではなく、IaCのコードで構築する。同じコードから、同じ環境を何度でも再現できるようにする
- IaCのツールはTerraformを標準とする（Cloudflare用の公式プロバイダーがある）。Terraformとwranglerの役割の分け方（インフラの作成はTerraform、アプリのデプロイはwrangler等）は、技術スタック別に定める
- IaCのコードはアプリと同じリポジトリの`infra/`で管理し、変更はほかのコードと同じくIssue・PRで行う
- 管理画面で直接設定を変えない。緊急で変えた場合は、同じ変更をIaCのコードに反映し、コードと実際の環境の食い違いをなくす
- 環境（開発用・検証用・本番など）ごとに設定を分け、同じコードで作れるようにする

### 秘密情報と状態ファイル

- APIトークンなどの秘密情報は、IaCのコードに書かず、環境変数や秘密情報の管理機能から渡す（[C-05](security.md#c-05)）
- Terraformの状態ファイル（`terraform.tfstate`）には秘密情報が含まれ得るため、リポジトリにコミットしない。アクセスを制限した保存先（リモートの状態管理）に置く

### 適用の手順

1. PRで、IaCの変更内容と、適用したときの差分（`terraform plan`の結果）を確認する
2. ユーザーの承認を得てから、本番に適用する（`terraform apply`）。AIが承認なしに本番へ適用しない
3. 適用後、コードと実際の環境に食い違いがないことを確認する

<a id="c-40"></a>

## C-40：環境の分け方

開発・検証・本番の3つの環境を、**環境変数の設定を切り替えて**分ける。開発と検証は手元のPCで使い、本番だけをCloudflareに置く。切り替えを誤っても、テストなどがほかの環境に影響しないようにする。

| 環境 | 動かす場所 | 環境変数の置き場所 | 使うとき |
| --- | --- | --- | --- |
| 開発 | 手元 | `.env.development` | 実装中の動作確認 |
| 検証 | 手元 | `.env.test` | 自動テスト（単体・結合・E2E）、攻撃を試すテスト・ペネトレーションテスト（[C-82](quality-test.md#c-82)）、負荷・限界のテスト、受け入れの確認 |
| 本番 | Cloudflare | 手元に置かない。Cloudflareの秘密情報・設定（`wrangler secret`・IaC、[C-39](#c-39)）だけ | クライアント・利用者が実際に使う |

- 環境の名前を環境変数`APP_ENV`（`development`・`test`・`production`）で持つ。Workersの手元の設定（`.dev.vars`等）も、同じ名前で分ける
- 見本は`.env.example`の1つにし、各環境のファイルはそれをコピーして作る（[C-05](security.md#c-05)）。実際の値が入ったファイルはコミットしない
- 開発と検証は、DB・ファイルの保存先を分ける。検証のDBは、テストのたびに作り直してよいものにし、テストが開発のデータを消さないようにする
- **MUST NOT**：本番の値（秘密情報・本番のDBの接続先）を、手元の平文のファイルに置かない（プロジェクトの外のファイルも含む）。手元から本番につながる設定がない状態にする
- 本番の値を控えておく必要がある場合（再登録・引き継ぎ等）は、パスワード管理ソフト等の暗号化された保管場所に置く。使うソフトはプロジェクトごとに選び、`docs/secrets.md`に書く（例：Bitwarden・KeePassXC・1Password・OSに標準の資格情報の管理）
- 本番のデータを開発・検証に持ち込まない（[C-05](security.md#c-05)のテストデータのルール）

### テストがほかの環境を使わないための仕組み

| # | 仕組み |
| --- | --- |
| 1 | テストのコマンドは、検証の設定（`.env.test`）だけを読み込む。ほかの設定を読む書き方をしない |
| 2 | テストを始める前に、`APP_ENV`が`test`であること、DBの接続先が手元（`localhost`・D1のローカル）であることを確かめ、違えば止める |
| 3 | `npm run env:check`と、アプリの起動のときに、今の環境の名前を表示する（値は表示しない） |
| 4 | テストのスクリプトでは、wranglerの`--remote`（Cloudflare上のD1等につなぐ設定）を使わない。品質チェックで、使っていないことを確かめる |

### Cloudflare上の環境

- 既定では、Cloudflare上には本番だけを作る
- 次の必要がある場合は、Cloudflare上に検証の環境を足すかを検討し、ADR（[C-35](workflow.md#c-35)）に記録する。足す場合は、本番と同じIaCのコードから作り、DB・秘密情報・ドメインを本番と分ける
  - 本番に近い構成で、性能を計測する（手元の計測は、本番の性能の目安にならない）
  - クライアントが、インターネット越しに受け入れの確認をする
  - Cloudflare上でしか確かめられない動き（本番と同じD1・R2・設定）を確かめる
- ほかの共通仕様で「検証環境」と書いたものは、手元で検証の設定で動かしたアプリを指す。Cloudflare上に検証の環境を足した場合は、そちらを使ってもよい

## C-41：デプロイと切り戻し

### デプロイ

- デプロイは自動化せず、承認を得てから行う。マージしただけで本番に反映される仕組みにしない
- 承認するのは、その時点の開発リーダーとする（個人開発の場合は、その個人）
- AIは承認なしにデプロイしない。承認を依頼するときは、デプロイする内容・DBの変更の有無・切り戻しの方法を示す
- 本番へのデプロイは、検証（[C-40](#c-40)）で確認済みの同じバージョンで行う

### 切り戻し

- 不具合が出た場合は、前のバージョンを再デプロイすることを基本とする。そのため、デプロイしたバージョン（[C-08](workflow.md#c-08)）を記録し、前のバージョンをすぐに再デプロイできる状態を保つ
- 大規模な案件では、Blue-Greenデプロイメントやカナリアリリースを採用するかを検討し、結果をADR（[C-35](workflow.md#c-35)）に記録する

### 本番DBの変更（後方互換性）

アプリを前のバージョンに切り戻しても動くように、本番DBの変更は後方互換性を確保してから破壊的変更を行う（[C-37](backend.md#c-37)）。

1. **追加**：新しいカラム・テーブルを追加する。前のバージョンのアプリはこれを使わないので、そのまま動く
2. **移行**：新しいバージョンのアプリをデプロイし、データを新しい構造へ移す。この間は古い構造も残しておく
3. **削除（破壊的変更）**：切り戻す可能性がなくなったことを確認してから、別のデプロイで古いカラム・テーブルを削除する

- カラムの削除・名前の変更・型の変更など、前のバージョンが動かなくなる変更を、1回のデプロイで行わない

### バックアップと復元

- DBのバックアップは、使うDB・サービスで可能な限り行う（D1ならTime Travel等の復元機能、PostgreSQLなら定期バックアップ）
- 本番DBにマイグレーションを適用する前に、その時点に戻せること（復元ポイントやバックアップ）を確認する
- 復元の手順を文書にし、検証の設定（[C-40](#c-40)）で実際に復元できることを確認しておく
- 具体的なバックアップの方法・頻度・保存期間は、技術スタック・DB別に定める
