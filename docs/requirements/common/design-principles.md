## C-38：メンテナンス性を考慮した設計

共通仕様（[C-01](workflow.md#c-01)〜）を守ることを前提に、次の基準で設計・実装する。「メンテナンス性」を感覚で判断せず、下の基準で確認する。

| 観点 | 基準 |
| --- | --- |
| 既存に合わせる | 新しく書くコードは、プロジェクト内の既存の書き方・命名・構成に合わせる。別の書き方を持ち込む場合は、理由をADR（[C-35](workflow.md#c-35)）に記録する |
| 単純さ | 要求を満たす一番単純な方法を選ぶ。今は必要のない将来の拡張のための仕組み（使われない設定・抽象化など）を作らない |
| 変更の影響範囲 | 1つの変更が、関係のない多くのファイルに波及しない構成にする。層の責務（[C-03](backend.md#c-03)・[C-06](frontend.md#c-06)）を守ることで、変更を1つの層に閉じ込める |
| 重複 | 同じ処理・同じ知識（ルールや定数）を複数の場所に書かない。ただし、偶然似ているだけの処理を無理に共通化しない |
| 命名 | 名前だけで役割が分かるようにする。省略語や、`data`・`util`のような意味の広い名前を避ける |
| 大きさ | 1つの関数・ファイルが複数の役割を持ち始めたら分割する |
| 値の直書き | 環境によって変わる値や、意味のある定数をコードに直書きしない。設定や名前付きの定数にする |
| 不要なコード | 使われていないコード・コメントアウトしたコードを残さない（履歴はGitで追える） |
| コメント | コードを読めば分かる「何をしているか」は書かず、コードから読み取れない「なぜそうしたか」だけを書く |
| 依存関係 | ライブラリは必要なものだけに絞る（[C-32](quality-test.md#c-32)）。標準機能や既存の依存関係で済む場合は、新しく追加しない |
| テストしやすさ | 外部サービス・時刻・乱数などへの依存は、テストで差し替えられる形にする（[C-25](quality-test.md#c-25)） |

- 上記の基準は、レビュー（[C-33](workflow.md#c-33)）の観点にも使う

<a id="c-53"></a>

## C-53：AIの作業ルール

フロントエンド・バックエンド・DB・IaCなど、すべての作業に適用する。ルールの強さの表記（MUST等）は2.4と同じ。

作業の進め方

- **MUST**：変更する前に、既存のコードの設計・命名・ディレクトリ構成を確認する
- **MUST**：変更の範囲は、要求された機能に必要な最小限にする
- **MUST NOT**：依頼されていない大規模なリファクタリングを、同時に行わない
- **MUST NOT**：既存の公開API・型・動作を、理由なく変更しない
- **MUST**：設計の選択肢が複数ある場合は、既存のパターンを優先する（[C-38](#c-38)）
- **SHOULD**：既存のコードに同じような実装がある場合は、それを参照してそろえる

確認とエラーの扱い

- **MUST**：既存のテストがある場合は、変更後に実行する
- **MUST**：lint・型チェック・テストを通す
- **MUST NOT**：エラーを無視するために、`eslint-disable`や`@ts-ignore`を安易に追加しない
- **MUST**：失敗した場合は原因を修正する。エラーを隠して成功扱いにしない（[C-25](quality-test.md#c-25)）

依存ライブラリの追加（[C-32](quality-test.md#c-32)に加えて）

- **MUST NOT**：目的を達成するためだけに、新しいパッケージを無断で追加しない
- **MUST**：新しいライブラリを追加する前に、次を確認し、結果を承認の依頼に含める
  - 既存のライブラリで代わりにならないか
  - 言語・フレームワークの標準機能で実装できないか
  - メンテナンスが続いているか
  - セキュリティ上の問題がないか
  - バンドルサイズへの影響

<a id="c-56"></a>

## C-56：知見（ヒューリスティクス）の使い方

使い方のルールは全分野で共通とし、知見の中身は分野ごとに`knowledge/`（[F-18](../functional.md#f-18)）に置く。

- **MUST**：判断に迷う場面（分割するか、共通化するか、どの構成にするか等）では、まず`knowledge/`の該当する分野の知見を確認する
- **MUST**：知見は絶対のルールではない。共通仕様（MUST・MUST NOT）が知見より優先する
- **MUST**：知見に当てはまらない場面では、実測や根拠に基づいて判断し、理由を記録する（[C-35](workflow.md#c-35)）
- **SHOULD**：知見が外れた例や、新しく得た判断基準は、[F-18](../functional.md#f-18)の流れで知見に反映する

<a id="c-57"></a>

## C-57：コードの自動整形と命名規則

- **MUST**：自動整形ツール（TypeScriptならPrettier等）を使い、書式について人やAIが判断しない
- **MUST**：品質チェック（[F-16](../functional.md#f-16)）で整形済みかを確認し、整形されていなければ失敗とする

| 対象 | 規則 | 例 |
| --- | --- | --- |
| Reactコンポーネントのファイル | PascalCase | `UserList.tsx` |
| Custom Hookのファイル | `use`＋camelCase | `useUserList.ts` |
| その他のTypeScriptファイル | kebab-case | `date-format.ts` |
| ディレクトリ | kebab-case | `user-profile/` |
| テスト | 対象と同じ場所に置き、`.test`を付ける | `UserList.test.tsx` |
| DAOの生SQL | `.sql.ts` | `sales-report.sql.ts` |
| マイグレーション | 番号＋snake_case | `0003_add_users_email_index.sql` |
| 変数・関数 | camelCase | `fetchUsers` |
| 型・コンポーネント | PascalCase | `UserResponse` |
| 定数 | UPPER_SNAKE_CASE | `MAX_PAGE_SIZE` |
| 環境変数 | UPPER_SNAKE_CASE | `DATABASE_URL` |
| DBのテーブル・カラム | snake_case。テーブルは複数形 | `users`、`created_at` |

## C-75：破壊的な操作

取り消しが難しい操作や、ほかの人の作業・環境に影響する操作は、実行する前に止まり、何を・なぜ・どの範囲で行うかと、取り消す方法を示して、利用者の判断を仰ぐ。

- **MUST**：次の操作は、実行する前に利用者の判断を仰ぐ。利用者が一度承認しても、別の場面では改めて確認する
  - ファイル・フォルダの削除（作業の範囲外のもの、まとめての削除）
  - Gitの履歴や変更を失う操作（`git reset --hard`、`git push --force`、`git branch -D`、`git clean`、未コミットの変更の破棄、リベース、コミットの書き換え）
  - DBのデータや構造を消す操作（テスト用DBをテストの手順どおりに作り直す場合を除く）
  - 自分が起動したか分からないプロセスの停止（[C-69](quality-test.md#c-69)）
  - 依存ライブラリの削除・バージョンを下げること
  - 本番環境・共有の環境に影響する操作（[C-41](project-env.md#c-41)のデプロイ、`terraform apply`等）
  - ほかの人から見える場所への操作（PRのクローズ、Issue・ブランチの削除等）
- **MUST**：確認する前に、`git status`等で失われるものがないかを確かめる
- **SHOULD**：迷った場合は、削除ではなく、移動・名前の変更・一時的な退避など、元に戻せる方法を選ぶ
- **MUST**：役割ごとのエージェント（[C-66](workflow.md#c-66)）は、破壊的な操作をしない。必要だと判断した場合は、実行せずに統括に報告し、統括が利用者の判断を仰ぐ

### AIの設定による守り

指示だけに頼らず、AIの設定でも、危険なコマンドに確認を求め、特に危険なものは禁止する（[F-25](../functional.md#f-25)）。

| 扱い | Claude Code | Codex | 対象 |
| --- | --- | --- | --- |
| 毎回確認を求める | `permissions.ask` | `decision = "prompt"` | Gitの履歴や変更を失う操作（`git push --force`・`git reset --hard`・`git clean`・`git branch -D`・`git rebase`・`git checkout --`・`git restore`）、ファイルの削除（`rm -r`）、本番・共有の環境（`terraform apply`・`terraform destroy`・`wrangler deploy`・`--remote`を付けた`wrangler d1`）、依存関係の削除（`npm uninstall`）、GitHubでほかの人から見える操作（`gh pr close`・`gh issue delete`・`gh repo delete`）、Dockerのデータの削除（`docker system prune`・`docker volume rm`） |
| 禁止する | `permissions.deny` | `decision = "forbidden"` | `main`への強制push（[C-42](workflow.md#c-42)）、実際の値が入った秘密情報のファイルの読み込み（[C-05](security.md#c-05)） |

- 確認を求める設定は、AIに任せて進める設定にしていても、必ず確認を求める
- 禁止は、許可の設定で上書きできない。各自の個人の設定で緩めても、禁止したものは守られる

### 何重にも守る

AIの設定のルールは、AIがふだん書く形のコマンドに当てはまるだけで、安全を保証する壁ではない（例：`bash -c '...'`や、コマンドの絶対パスで書かれると当てはまらない）。そのため、次を重ねて守る。

| 守り | 内容 |
| --- | --- |
| 指示 | 本項と`AGENTS.md`で、破壊的な操作は判断を仰ぐよう指示する |
| AIの設定 | 上記の確認・禁止のルール |
| 書き込みの制限 | Codexの編集しない役割は`read-only`で動かす（[F-21](../functional.md#f-21)） |
| GitHubの設定 | `main`への直接のpush・強制pushを、ブランチ保護で禁止する（[C-42](workflow.md#c-42)） |
| 取り消しの手段 | DBのバックアップ（[C-41](project-env.md#c-41)）、Gitの履歴 |
