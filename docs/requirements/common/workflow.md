<a id="c-07"></a>

## C-07：Issueの分け方

1つの機能・1つの文書を**親Issue**とし、必要な作業を**子Issue**（GitHubのsub-issue）に分ける。子Issueごとにブランチ・PRを作成し、親Issueは全体の進み具合と完了条件を管理する。

### 機能実装の場合

| 階層 | 内容 | 例 |
| --- | --- | --- |
| 親Issue | 実装する機能と、その完了条件 | ログイン機能を実装する |
| 子Issue | 機能に必要な作業を、作業領域ごとに分けたもの | 下表を参照 |

| 作業領域 | 子Issueにする条件 | 例 |
| --- | --- | --- |
| DB | テーブル・カラムの追加や変更がある | ユーザーテーブルのマイグレーション |
| バックエンド | APIや業務ロジックの追加・変更がある | ログインAPI（Controller／Service／Repository） |
| フロントエンド | 画面や部品の追加・変更がある | ログイン画面（PasswordFieldを含む） |
| その他 | CI・インフラ・設定の変更がある | 認証用の環境変数の追加 |

- 必要のない作業領域の子Issueは作らない（例：画面のないAPIのみの機能ではフロントエンドの子Issueを作らない）
- 子Issueの間に依存関係がある場合は本文に明記する（例：バックエンドのIssueはDBのIssueの完了後に着手する）
- 各子Issueには、その作業領域での完了条件を書く

### 文書作成の場合

親Issueを文書全体とし、子Issueを章（タイトル）ごとに分ける。この要件定義書もこの方式で管理する（親Issue #1）。

<a id="c-21"></a>

## C-21：ブランチ名

`<種類>/<Issue番号>-<内容>` の形式にする。内容は英小文字とハイフンで短く書く。

| 種類 | 使うとき | 例 |
| --- | --- | --- |
| `feature` | 機能の追加 | `feature/12-login-api` |
| `fix` | 不具合の修正 | `fix/15-password-toggle` |
| `docs` | 文書の追加・修正 | `docs/3-common-spec` |
| `refactor` | 動作を変えないコードの整理 | `refactor/20-split-user-service` |
| `chore` | 設定・依存関係・CIなどの変更 | `chore/8-add-eslint` |

<a id="c-22"></a>

## C-22：コミットメッセージ

Conventional Commits に従い、`<種類>: <説明>` の形式にする。種類は英語、説明は日本語で書く。

| 種類 | 使うとき | 例 |
| --- | --- | --- |
| `feat` | 機能の追加 | `feat: ログインAPIを追加` |
| `fix` | 不具合の修正 | `fix: パスワード表示トグルが動かない問題を修正` |
| `docs` | 文書のみの変更 | `docs: 共通仕様にブランチ名のルールを追加` |
| `refactor` | 動作を変えないコードの整理 | `refactor: UserServiceを分割` |
| `test` | テストの追加・修正のみ | `test: ログインAPIの認可テストを追加` |
| `chore` | 設定・依存関係・CIなどの変更 | `chore: ESLintを導入` |

- 以前の内容と両立しない変更には、種類の後ろに`!`を付ける（例：`feat!: APIのレスポンス形式を変更`）。初回完成後は、[C-08](#c-08)のバージョンを上げる判断に使う

<a id="c-23"></a>

## C-23：PR

- 本文に `Closes #<子Issue番号>` を書き、マージと同時に子Issueが自動でクローズされるようにする。親Issueは `Refs #<親Issue番号>` で参照し、クローズしない
- マージは **Squash** で行い、PR1つが`main`上のコミット1つになるようにする。Squash後のコミットメッセージもC-22に従う
- マージ前に、[C-24](quality-test.md#c-24)のテストと品質チェック（[F-16](../functional.md#f-16)）が通っていることを確認する
- マージの後に、`Closes`で指定したIssueが自動でクローズされたかを確かめる。クローズされていない場合は、マージしたPRの番号を書いたコメントを付けて、手動でクローズする（GitHubが`Closes`の紐付けを認識しない場合があるため）
- マージ後は、ローカルの`main`を最新にし、統合済みであることを確かめてから、対応するローカルの作業ブランチを削除する。別のworktreeで使用中のブランチや、未コミットの変更があるブランチは削除せず、状態を報告する

<a id="c-42"></a>

## C-42：`main`ブランチの保護

- `main`ブランチへの直接のpushを禁止する。AIも利用者も、変更はすべてC-21のブランチからPRを作成し、[C-23](#c-23)に従ってマージする
- GitHubのブランチ保護（またはRuleset）で、直接のpushと強制push（force push）を禁止する設定を行う。設定の手順は生成するプロジェクトのREADMEに記載する
- 例外的に`main`を直接変更する必要が生じた場合も、AIは実行せず、理由を示してユーザーに判断を求める

<a id="c-08"></a>

## C-08：バージョンの付け方

### 初回完成まで

- バージョンは付けない。Issueを解決しても、バージョンは上げない
- ハーネスが一通り完成した時点で`0.0.0`を付ける

### 初回完成後

| 桁 | 上げるとき | 例 |
| --- | --- | --- |
| MAJOR | 以前の内容と両立しない大きな変更をしたとき | `0.4.2` → `1.0.0` |
| MINOR | 項目の追加・仕様の決定など、内容が増えたとき | `0.0.3` → `0.1.0` |
| PATCH | 誤字の修正・表現の調整など、意味が変わらない修正をしたとき | `0.1.0` → `0.1.1` |

- 下の桁は、上の桁を上げたときに`0`へ戻す
- 要件定義書と、ハーネスが生成するプロジェクト・CLIツール本体のすべてに同じルールを適用する

<a id="c-11"></a>

## C-11：Superpowersを使ったAI開発フロー

- Claude CodeまたはCodexを利用する開発では、Superpowersプラグインを利用可能な状態にする。プラグインは各AI環境に個別に導入する。
- 要件整理・設計では`brainstorming`を使い、ユーザーへの質問、選択肢とトレードオフの整理、合意した設計の記録を行う。設計の合意前に実装へ進まない。
- 設計合意後は`writing-plans`で作業を実行可能な単位へ分解し、実装では`test-driven-development`、`requesting-code-review`、`verification-before-completion`等の該当スキルを使う。
- Superpowersの手順・成果物は日本語を基本とし、スキル名やコマンド名は識別できるよう原文のまま記載してよい。
- プラグインが利用できない場合は、その旨をユーザーに伝え、必要な導入手順を案内する。プラグインを前提とする作業を、利用できないまま黙って進めない。
- プラグインの導入はユーザーのAI環境に対して行い、生成したアプリケーションの実行時依存には含めない。プラグインを自動インストールするスクリプトは生成しない。
- Superpowersの指示は、ユーザーの指示とプロジェクト固有ルールに従う。
- 実装の進め方はC-66の流れを主とし、SuperpowersのSkillは各役割の中で使う（[C-66](#c-66)の「Superpowersとの関係」を参照）。
- `brainstorming`は、要件定義（[C-76](#c-76)）で使う。その際、次の2点はハーネスの決まりを優先する（`brainstorming`自身も、保存先は利用者の指定が優先すると定めている）。
  - 成果物（設計書）は、`docs/superpowers/specs/`ではなく、要件定義書（`docs/requirements.md`）に書く
  - 設計の承認の後は、`writing-plans`に進まず、プロトタイプ → Issueへの分割に進む。`writing-plans`は、Issueごとの実装の計画（`planner`）で使う

<a id="c-33"></a>

## C-33：レビューの進め方

- 実装したAIとは別のAIでレビューする。見落としの重なりを減らすため、次の優先順位に従う
  1. 原則：別の会社のAIでレビューする（例：Claude Codeで実装したらCodexでレビューする）
  2. 1が使えない場合：同じ会社の別のモデルで、新しい会話（実装の経緯を渡さない状態）でレビューする
  3. 最低限：同じモデルでも、必ず新しい会話でレビューする。実装と同じ会話の中での見直しは、レビューとして扱わない
- どの段階でレビューしたかを、レビュー結果の記録（[C-66](#c-66)）に書く
- 合意済みの設計判断（ADR等で決定したもの）がレビューで再び指摘された場合は、レビューの回数に数えず、コードも変更しない。既知のトレードオフである理由と参照先を、レビューしたAIに伝えるだけにする
- レビューの指摘は、そのまま受け入れず、要求・仕様に照らして妥当かを確認してから対応する。対応しない指摘は理由を記録する
- 人によるレビューは任意とする。開発人数（[F-14](../functional.md#f-14)）にかかわらず、この流れは同じとする

<a id="c-76"></a>

## C-76：要件定義とIssueへの分割の進め方

実装（[C-66](#c-66)）の前に、次の2つの段階を行う。どちらも利用者との対話が必要なため、役割ごとのエージェント（途中で利用者に質問できない）ではなく、**統括（メインの会話）が担当する**。

| 段階 | 担当 | 使うもの | 成果物 |
| --- | --- | --- | --- |
| 1. 要件定義 | 統括（利用者と対話） | Superpowersの`brainstorming` | 要件定義書 |
| 2. プロトタイプ | 統括（洗い出し）・プロトタイプの作成の役割（作成） | HTML・CSS・JavaScript | 画面の動きを再現したプロトタイプ、更新した要件定義書 |
| 3. Issueへの分割 | 統括 | — | 親Issue・子Issue（受け入れ条件付き） |
| 4. Issueごとの実装 | 役割ごとのエージェント | [C-66](#c-66)の流れ | 実装・PR |

### 1. 要件定義

- **MUST**：利用者と対話しながら、目的・想定する利用者・機能・範囲（作らないもの）・受け入れ条件を決める。質問は一度に多くせず、選択肢と推奨案・その理由を示して決めてもらう
- **MUST**：決まっていないことは推測で埋めず、「未決定」として要件定義書に書く
- **MUST**：技術・ライブラリの選定は、利用者が決める（[C-32](quality-test.md#c-32)・[F-19](../functional.md#f-19)）。AIは候補と理由を示す
- **MUST**：要件定義書に書いて利用者の合意を得るまで、実装に進まない（[C-11](#c-11)）
- **MUST**：共通仕様の判定に必要な項目（[F-26](../functional.md#f-26)の質問A〜G）を確認する。「未定」の項目を決め、決まっている項目も要件と食い違っていないかを確かめる。変わった場合は、`.harness/config.yaml`と要件定義書を更新する
- **MUST**：Superpowersの`brainstorming`を使う場合も、成果物は要件定義書に書き、承認の後はプロトタイプに進む（[C-11](#c-11)）
- **SHOULD**：大きな判断（構成の選択等）は、背景と理由をADR（[C-35](#c-35)）に残す

### 2. プロトタイプ

要件定義書の内容を、実際に画面で動かして利用者と確かめる。作り直しを繰り返すことを前提に、手軽さと速さを優先する。

- **MUST**：要件定義書の合意の後、Issueへの分割の前に作る。画面がないプロジェクト（APIのみ等）では作らない
- **MUST**：HTML・CSS・JavaScriptだけで作る。ビルドの道具・フレームワーク・外部のライブラリは使わず、ブラウザでファイルを開くだけで動くようにする
- **MUST**：バックエンドには接続しない。データはプロトタイプの中の架空のデータ（[C-05](security.md#c-05)のテストデータのルールに従う）で再現し、画面の操作による変化はブラウザの中だけで保持する
- **MUST**：秘密情報・本物のAPIキー・実在の個人情報を含めない
- **MUST**：画面ごとに、読み込み中・データあり・データなし・エラーの表示（[C-48](frontend.md#c-48)）と、操作の後に再読み込みせずに表示が変わること（[C-77](frontend.md#c-77)）を再現する
- **MUST**：プロトタイプは、動きを確かめるための使い捨てのものとし、本番のコード（`frontend/`）に流用しない。`prototype/`に置き、確かめた記録としてコミットする

進め方：

1. **洗い出し**（統括、上位のモデル）：要件定義書から、画面の一覧・画面の移り変わり・画面ごとの状態と操作を洗い出し、利用者に承認を得る
2. **作成**（プロトタイプの作成の役割）：洗い出しに沿って、プロトタイプを作る
3. **確認**：利用者がブラウザで動かして確かめる。気づいたことを受け取る
4. **反映**：受け取った内容で、要件定義書を更新し、必要ならプロトタイプを直す。3〜4を、利用者が承認するまで繰り返す
5. 利用者の承認を得てから、Issueへの分割に進む

### 3. Issueへの分割

- **MUST**：要件定義書から、機能ごとの親Issueと、作業領域（DB・バックエンド・フロントエンド・その他）ごとの子Issueに分ける（[C-07](#c-07)）
- **MUST**：子Issueには、次を書く
  - 対象の作業領域
  - 参照する要件定義書の箇所・文書
  - 番号付きの受け入れ条件（`AC-1`、`AC-2`…、[C-26](quality-test.md#c-26)）
  - 依存するIssueの番号
- **MUST**：1つの子Issueは、単独でレビュー・マージできる最小の単位にする。依存関係のある作業を1つのIssueに詰め込まない
- **MUST**：Issueを作成する前に、分割の一覧（タイトル・受け入れ条件の要約・依存関係・着手の順番）を利用者に示し、承認を得る

### 4. 実装中に要件が変わった場合

- 実装中に要件の追加・変更が必要になった場合は、実装を止めて段階1に戻り、要件定義書を更新して利用者の合意を得てから、Issueを更新または追加する
- 要件定義書と実装が食い違っていることに気づいた場合も、同じく止まって利用者の判断を仰ぐ

<a id="c-66"></a>

## C-66：AIによる実装の進め方

Issue 1件の実装を、次の役割に分けて進める。

| # | 役割 | やること | 触ってよいもの | 成果物 |
| --- | --- | --- | --- | --- |
| 0 | 統括 | 全体の進行。各役割を呼び出し、成果物を受け渡し、完了の定義（[C-34](#c-34)）で判定する | — | 最終報告 |
| 1 | 計画 | Issueの受け入れ条件から、変更するファイル・手順・テストケースを決める | 読み取りのみ | 実装計画 |
| 2 | 計画レビュー | 計画の要件漏れ・既存の動作の退行・テスト不足・秘密情報の混入を指摘する | 読み取りのみ | 指摘 |
| 3 | テスト | 受け入れ条件（[C-26](quality-test.md#c-26)）からテストを実装より先に書く（この時点では失敗する） | テストのファイルのみ | テスト |
| 4 | 実装 | テストが通るように実装する | 計画にあるファイルのみ。テストは変更しない | 実装 |
| 5 | 品質チェック | Lint・型・テスト・E2E等を、手元とCIで共通の1つのコマンド（[C-61](quality-test.md#c-61)）で実行し、失敗の原因を報告する | 読み取りと実行のみ | 結果の報告 |
| 6 | コードレビュー | 実装とは別のAIでレビューする（[C-33](#c-33)） | 読み取りのみ | 指摘 |
| 7 | ドキュメント | 変更に関係する文書（API仕様・要件定義書・`tech-stack.md`・ADR・README）を確認・更新し、PRの「知見」の欄（[F-18](../functional.md#f-18)）を書く | 文書のみ | 文書の更新、PR本文 |

- 実装は**テスト駆動開発**（Red → Green → Refactor）で進める
  - **Red**：テストの役割が、テストを先に書き、実装がないために失敗することを確かめる
  - **Green**：実装の役割が、テストが通る最小限の実装をする
  - **Refactor**：実装の役割が、テストが通る状態を保ったまま、重複の除去・名前の改善などの整理をする。整理の後にテストを実行し直す。整理で動作を変えない
- テスト（3）と実装（4）を別の役割にし、テストを先に書くことで、実装に合わせて期待値を決めることを防ぐ（[C-25](quality-test.md#c-25)）。実装の役割がテストを変更する必要があると判断した場合は、理由を示して統括に戻し、テストの役割が要求に照らして修正する
- 各役割は、表の「触ってよいもの」の範囲を超えて変更しない

### レビューの回数

- 計画レビュー・コードレビューとも、最大3回とする。重大な指摘があれば修正して再レビューする
- 3回目でも重大な指摘が残る場合は、先に進まず、ユーザーに判断を求める
- ただし、データ破損・認証の回避・情報漏えいにつながる重大な指摘は、回数の上限を超えても、解消するまでレビューを続ける
- レビューを重ねた結果、Issueが「単独でレビュー・マージできる最小単位」を明らかに超えた場合（新しい基盤が必要になった、複数の独立した成果物に分かれた、手間と価値が釣り合わない等）は、レビューを続けずにユーザーに相談する。「厳密にやる／範囲を縮める／後回しにする」の選択肢と、範囲を縮めた場合に何を名乗れなくなるかを示す。範囲を縮めた場合は、検証の限界を成果物に明記する

### ユーザーによる動作確認

- 品質チェック・コードレビューが終わったら、コミットの前に一度止まり、ユーザーに動作確認を依頼する。確認の手順と、確認してほしい受け入れ条件を示す
- 変更の大きさが「小」の場合は、動作確認を省略してよいかをユーザーに確認する

### 複数のIssueを続けて進める場合

次をすべて満たす場合は、ユーザーに確認せずに次のIssueに着手してよい。

- 直前のIssueのPRがマージ済みである
- 直前のIssueの受け入れ条件と動作確認を満たしている
- 次のIssueが依存するIssueが、すべて完了している

次の場合は、必ず立ち止まってユーザーに判断を求める。

- ユーザーによる動作確認が必要な工程に着いた
- 文書と実装の食い違いを見つけた（どちらを正とするかの判断が必要）
- 依存ライブラリの追加など、共通仕様に影響する変更が必要になった
- 要件定義書等で「要調査」「未検証」とされている項目に着手する

### 記録

- 実装計画、計画レビュー・コードレビューの結果（指摘の数・採用した数・採用しなかった指摘と理由）、品質チェックの結果を、該当するIssueのコメントに残す
- 実装中に計画を変更した場合は、変更した内容と理由を、その都度Issueのコメントに残す
- レビューの結果の記録は、どのAIがどの役割に向いているかを知見（[F-18](../functional.md#f-18)）として確かめる根拠にも使う

### Superpowersとの関係

この流れを主とし、SuperpowersのSkill（[C-11](#c-11)）は各役割の中で使う。

| 役割 | 使うSkillの例 |
| --- | --- |
| 計画 | `brainstorming`（要件が曖昧な場合）、`writing-plans` |
| テスト | `test-driven-development` |
| コードレビュー | `requesting-code-review` |
| 統括（完了の判定） | `verification-before-completion` |

### 変更の大きさと起動する役割

毎回すべての役割を起動すると、時間とトークンが増えるため、変更の大きさによって起動する役割を変える。大きさは次の基準で決める。

| 大きさ | 基準 | 起動する役割 |
| --- | --- | --- |
| 小 | 誤字の修正・文書だけの変更・設定値1か所の変更など、動作のロジックを変えないもの | 実装 → 品質チェック → コードレビュー |
| 通常 | 小・影響大のどちらにも当たらないもの | すべての役割 |
| 影響大 | 認証・認可・個人情報・データ移行・DBスキーマの破壊的変更に関わるもの | すべての役割。テストの設計とコードレビューは上位のモデルで行う |

- どの大きさでも、完了の定義（[C-34](#c-34)）と、テスト・品質チェックが通ることは省略しない
- 判断した大きさと理由を、Issueのコメントに書く

### 運用のルール

- **MUST**：各役割には、会話全体ではなく、目的・対象のファイル・制約・完了条件など必要な情報だけを渡す。レビューの役割には実装の経緯を渡さない（[C-33](#c-33)）
- **MUST**：品質チェックは実行結果と要件（受け入れ条件）との照合を、コードレビューはコードの不具合・影響範囲・テスト不足を担当し、範囲を重ねない
- **MUST**：レビューの1回目は全体を確認し、2回目以降は指摘した箇所とその関連部分に絞って確認する（上限の3回は変えない）
- **MUST**：最初から全員を上位のモデルにしない。次の条件に当たる場合に切り替える

| 条件 | 切り替え先 |
| --- | --- |
| 認証・認可・個人情報・データ移行・重要な業務ルールに関わる（テストの設計・コードレビュー） | 一番性能の高いモデル |
| 複雑な新規設計や、重大な設計判断が必要 | 一番性能の高いモデル |
| 同じ失敗を2回直しても解消しない | 一番性能の高いモデル。または計画の役割に戻す |
| 単純な置換・定型の変更 | 軽いモデル |

### 役割とAI・モデルの割り当て

- モデル名はハーネスのルールに直接書かず、「役割 → AI・モデル」の対応を設定ファイルにし、プロジェクトごとに変えられるようにする
- 生成時に、主に使うAIに応じて次の初期値を設定する。モデル名は変わるため、設定する前に、実際に選べるモデル名を確認する

| 役割 | Claude Codeが主の場合 | Codexが主の場合（推論の強さ） |
| --- | --- | --- |
| 統括 | Opus 5.5 | GPT-6 Sol（medium） |
| 計画 | Opus 5.5 | GPT-6 Sol（high）。複雑な新規設計はGPT-6 Astra |
| 計画レビュー | 別の会社のAI。使えなければOpus 5.5（新しい会話） | 別の会社のAI。使えなければGPT-6 Solの別エージェント（high）。重大な設計判断はGPT-6 Astra |
| テスト（設計・追加） | Sonnet。影響の大きい処理はOpus 5.5 | GPT-6 Sol（medium）。影響の大きい処理はGPT-6 Astra |
| 実装 | Sonnet。同じ失敗が2回続く場合はOpus 5.5 | GPT-6 Sol（medium）。単純な置換・定型の変更はGPT-6 Luna |
| 品質チェック（テストの実行・結果の整理を含む） | Sonnet | GPT-6 Luna（low〜medium）。原因の調査が難しい場合はGPT-6 Sol |
| コードレビュー | 別の会社のAI。使えなければOpus 5.5（新しい会話） | 別の会社のAI。使えなければGPT-6 Solの別エージェント（high）。認証・権限・データ移行等はGPT-6 Astra |
| ドキュメント | Sonnet | GPT-6 Luna（medium）。設計意図の整理はGPT-6 Sol |
| プロトタイプの洗い出し（[C-76](#c-76)） | Opus 5.5（統括） | GPT-6 Sol（high） |
| プロトタイプの作成（[C-76](#c-76)） | Sonnet。複雑な画面の移り変わりや、2回直しても意図どおりにならない場合はOpus 5.5 | GPT-6 Sol（medium） |

- レビューのとき、計画と同じモデルを使う場合は、計画を作った会話とは別の、新しい会話で行う
- 割り当ては、レビュー結果の記録（指摘の数・採用した数・誤った指摘の数）をもとに、知見（[F-18](../functional.md#f-18)）として見直す

##### Claude Codeが使えないとき

トークンの上限などでClaude Codeが使えないときは、Codexで作業を続ける。

- **MUST**：同じ流れ（[C-76](#c-76)・本項）のまま、上の表の「Codexが主の場合」の割り当てで続ける。主に使うモデルはGPT-6 Solとする
- **MUST**：切り替えたことと、その理由・時点を、Issueのコメントに残す
- **MUST**：レビューは[C-33](#c-33)の優先順位に従い、実装したAIとは別のAIで行う。Codexで実装した部分は、Claude Codeが使えるようになってからClaude Codeでレビューするか、待てない場合はCodexの別のエージェントで、新しい会話でレビューする
- Claude Codeが使えるようになったら、Claude Codeに戻してよい。戻したこともIssueに残す

<a id="c-67"></a>

## C-67：日本語での表示

- **MUST**：AIが利用者に見せるもの（作業中の説明・途中経過・報告・計画・レビュー結果・質問）と、Issue・PR・コミットメッセージの説明部分は、すべて日本語で書く
- **MUST**：サブエージェントや別のAI（Codex等）に作業を依頼するときも、日本語で出力するよう指示に含める。英語で返ってきた結果は、日本語にしてから利用者に見せる
- 関数名・ファイル名・コマンド・エラーメッセージの原文・ライブラリ名など、識別に必要なものは原文のまま書いてよい
- このルールは、生成する`CLAUDE.md`・`AGENTS.md`の冒頭に明記する（AIの種類によって英語が混ざりやすいため）

<a id="c-68"></a>

## C-68：AI向けの設定の共有範囲

| 種類 | 中身 | 置き場所 | 他の人への反映 |
| --- | --- | --- | --- |
| プロジェクトのルール | 共通仕様を実現するためのSkill・エージェントの定義（[C-66](#c-66)の役割、テストのルール等） | プロジェクトのリポジトリ（コミットする） | 反映される。変更は必ずPRを通す（[C-42](#c-42)）ため、知らないうちには変わらない |
| 個人の道具 | 各自が自分用に作ったSkill・エージェント | 各自のPCの個人の設定フォルダ（`~/.claude/`・`~/.agents/skills/`・`~/.codex/agents/`等）。コミットしない | 反映されない |

- 各自のAI環境に入れるプラグインのうち、必須とするのはSuperpowers（[C-11](#c-11)）だけとする。それ以外のプラグイン・Skillは個人の道具として扱い、使うかどうかは各自が決める
- **MUST NOT**：個人の道具をプロジェクトのリポジトリにコミットしない。コミットすると、pullした全員に自動で反映されてしまう
- **MUST NOT**：個人の設定ファイル（`settings.local.json`等）はコミットしない
- 個人の道具を他の人に紹介する場合は、ハーネスのリポジトリの「任意のSkillの一覧（カタログ）」に、できること・導入方法を書き、Issue等で知らせる。使うかどうかは各自が決め、使う人だけが自分の個人の設定フォルダに入れる

<a id="c-34"></a>

## C-34：完了の定義（Definition of Done）

次のすべてを満たしたときに、作業を完了とする。AIは、満たしていない項目がある状態で完了を報告しない。

1. Issueの受け入れ条件をすべて満たしている
2. 該当するテスト（[C-24](quality-test.md#c-24)）と品質チェック（[F-16](../functional.md#f-16)）が通っている
3. 変更に関係する文書（要件定義書・API仕様・設計書（[C-81](#c-81)）・README等）を更新している
4. PRにIssueを紐付けている（[C-23](#c-23)）

<a id="c-35"></a>

## C-35：記録の置き場所

| 記録する内容 | 置き場所 |
| --- | --- |
| 作業中のやり取り・判断、テストを省略した理由、レビュー指摘への対応 | 該当するIssue・PR |
| 後から参照する大きな設計判断（DAOの構成を選んだ理由、ライブラリの選定理由など） | `docs/adr/`に1件1ファイル（ADR） |
| 確定した仕様 | 要件定義書・API仕様などの文書 |

- 学びや手直しの記録は、専用のファイル（`lessons-learned.md`等）を作らず、ADRと、PRの「知見」の欄（[F-18](../functional.md#f-18)）にまとめる
- ADRには、背景・選択肢・決定・理由を書く。決定を変えるときは、元のADRを消さずに新しいADRを追加する

<a id="c-78"></a>

## C-78：ハーネスの改善の提案

生成したプロジェクトで作業する中で、ハーネス（ルール・Skill・テンプレート）の改善点や修正点に気づいた場合は、記録して利用者の判断に回す。

### 記録するきっかけ

| きっかけ | 例 |
| --- | --- |
| ルール同士が食い違っている | `AGENTS.md`とSkillで、レビューの回数が違う |
| ルールに従った結果、手戻りや不具合が起きた | ルールどおりに作ったら、別のルールに違反した |
| ルールが足りない | 判断の基準がどこにもなく、毎回迷う |
| ルール・Skillの書き方が分かりにくい | 解釈が2通りに取れる |
| 手順・コマンドが動かない | Skillに書かれたコマンドが、ツールの更新で動かなくなった |
| 生成されたファイルがおかしい | 必要なファイルが生成されていない |

設計の判断基準（知見）に関する気づきは、PRの「知見」の欄（[F-18](../functional.md#f-18)）に書く。

### 記録の仕方

- **MUST NOT**：AIは、ハーネスのルール・Skill・テンプレートを自分で直さない。改善の提案として記録するだけにする
- **MUST**：記録は、`harness-feedback`のラベルを付けたIssueとして、決まった形（事象・関係するルールの番号やファイル・起きた場面・影響・改善の案・急ぎかどうか）で書く
- **MUST**：ハーネスはほかのプロジェクトと共有するため、記録にはプロジェクト固有の機密・秘密情報・個人情報を書かず、事象を一般化して書く
- **MUST**：記録したことを、作業の報告の中で利用者に伝える。記録のために作業を止めない（ただし、ルールの食い違いで作業を進められない場合は、[C-66](#c-66)の立ち止まる条件に従う）

### 記録する場所

| 設定 | 記録する場所 | 使う場面 |
| --- | --- | --- |
| `project`（既定） | 作業中のプロジェクトのリポジトリ | 誰でも使える。AIは作業中のリポジトリの権限を持っているため、確実に作れる |
| `harness` | ハーネスのリポジトリ | ハーネスのリポジトリに権限がある人だけが選べる。ほかのリポジトリへの操作になるため、Issueを作る前に毎回利用者の承認を得る（[C-75](design-principles.md#c-75)） |

設定は`.harness/config.yaml`で切り替える。

### 検討の仕方

- 利用者が記録を読み、採用するものはハーネスのリポジトリでIssue・PRにして直す。採用しないものは、理由を書いて閉じる
- `project`の設定で記録したものは、月1回の知見の見直し（[F-18](../functional.md#f-18)）と同じタイミングで、各プロジェクトから`harness-feedback`のラベルを条件に集めて確認する

<a id="c-80"></a>

## C-80：プロジェクト固有のルールとハーネスのルールの分け方

プロジェクト固有のルールは、ハーネスが管理するファイル（`AGENTS.md`・Skill等）に書き足さず、`docs/project-rules.md`に書く。ハーネスを更新したとき（[F-27](../functional.md#f-27)）に、プロジェクト固有のルールが消えたり、差分の確認が増えたりすることを防ぐため。

### 判断の3つの問い

| # | 問い | はい | いいえ |
| --- | --- | --- | --- |
| 1 | このアプリの業務や中身（扱うデータ・画面・取引先・お客さまの要望）を知らないと、書けないルールか？ | プロジェクト固有 | 問い2へ |
| 2 | 特定の技術（Drizzle・Hono・Spring Boot等）を使うときにだけ必要なルールか？ | ハーネス（技術プロファイル、[F-24](../functional.md#f-24)） | 問い3へ |
| 3 | どのアプリでも、同じように守るべき作り方・進め方・品質・安全のルールか？ | ハーネス（共通仕様） | プロジェクト固有として始め、様子を見る |

| 例 | 分類 | 理由 |
| --- | --- | --- |
| レシピの材料は最大50件まで | プロジェクト固有 | このアプリの業務のルール |
| お客さまの指定で、ログは3年保存する | プロジェクト固有 | このお客さまの要望 |
| 決済は特定の会社のAPIを使い、テストはその会社の検証環境で行う | プロジェクト固有 | このアプリが使う外部サービスの事情 |
| D1では`db.transaction()`を使わず`db.batch()`を使う | ハーネス（技術プロファイル） | D1とDrizzleを使えば、どのアプリでも同じ |
| エラーをもみ消さない | ハーネス（共通仕様） | どのアプリでも同じ |
| このアプリでは、画面の文言に絵文字を使わない | プロジェクト固有 | このアプリの方針 |

### 迷ったとき・後から分かったときの流れ

1. 迷ったら、まずプロジェクト固有として`docs/project-rules.md`に書く
2. ほかのアプリでも通用すると気づいたら、ハーネスの改善の提案（[C-78](#c-78)）として記録する
3. 利用者が採用を決めたら、ハーネスに取り込み、次のハーネスの更新でプロジェクトに届ける
4. 取り込んだら、`docs/project-rules.md`から同じ内容を消し、2か所に同じルールを残さない

### ハーネスのルールと食い違う場合

| 食い違い方 | 扱い |
| --- | --- |
| ハーネスより厳しくする | プロジェクト固有のルールとして書いてよい |
| ハーネスより緩める | ハーネスのMUSTを緩める場合は、理由をADR（[C-35](#c-35)）に記録し、利用者の承認を得る。`docs/project-rules.md`には、ADRへのリンクを付けて書く |

### 知見との違い

| 種類 | 性質 | 置き場所 |
| --- | --- | --- |
| ルール（ハーネス・プロジェクト固有） | 守るもの（MUST・SHOULD） | 共通仕様・技術プロファイル／`docs/project-rules.md` |
| 知見 | 判断の目安。当てはまらない場合もある | `knowledge/`（[F-18](../functional.md#f-18)） |

<a id="c-81"></a>

## C-81：設計書

実装したコードが「どのファイルが何を担当し、どうつながっているか」を、1か所で見渡せるようにする。要件定義書（何を作るか）とコードの間にある、「どう作ったか」の地図である。

### 置き場所

| 文書 | 場所 | 内容 |
| --- | --- | --- |
| 全体の構成 | `docs/design/overview.md` | 全体の構成・フォルダとファイルの役割・処理の流れ・機能ごとの設計書の一覧 |
| 機能ごとの設計書 | `docs/design/<機能の名前>.md` | 1つの機能（まとまり）について、下の項目を書く |

### 機能ごとの設計書に書くこと

| 項目 | 書くこと |
| --- | --- |
| 目的 | 何のための機能か。要件定義書のどの項目に対応するか |
| ファイルと役割 | 関係するファイルと、それぞれの担当（層：Controller・Service・Repositoryなど） |
| 処理の流れ | 入口から出口までの流れ（呼び出しの順）。図を使ってよい |
| 主な関数の入力と出力 | 主な関数の名前と、受け取る値・返す値・投げるエラー |
| テストの場所 | この機能を確かめるテストのファイル |
| 関係するIssue・ADR | 実装したIssue・PRと、設計判断を記録したADR（[C-35](#c-35)） |

### 書き方と更新

- **コードは書き写さない**。ファイル名・関数名で指し示す。書き写すと、コードを直したときに食い違う
- 設計書は、**実装したPRの中で更新する**（[C-34](#c-34)の「関係する文書」）。実装と設計書が食い違った状態でマージしない
- 実装の後に、役割「ドキュメント」が、変更したファイル・関数と設計書を照らして更新する（[C-66](#c-66)）
- 設計書はプロジェクトのもの。ハーネスを更新したとき（[F-27](../functional.md#f-27)）に、上書きしない（ひな形は最初の1回だけ出す）

## C-83：GitHubを使わないプロジェクト

GitHubを利用できないプロジェクトでは、リモートのサービスを使わず、手元のGitだけで管理する。Issue駆動（[C-01](#c-01)）・ブランチ（[C-21](#c-21)）・コミット（[C-22](#c-22)）・レビュー（[C-33](#c-33)）・品質チェック（[C-61](quality-test.md#c-61)）の流れは変えず、GitHubの機能の代わりを次のように置く。

| GitHubを使う場合 | GitHubを使わない場合 |
| --- | --- |
| Issue（親Issue・子Issue、[C-07](#c-07)） | `docs/issues/`に1件ずつMarkdownで置く（例：`0012-login.md`）。番号・親のIssue・状態（未着手・作業中・完了）・受け入れ条件を書く。一覧は`docs/issues/README.md` |
| PR・レビュー（[C-23](#c-23)・[C-33](#c-33)） | 作業のブランチで行う。レビューの結果（レビューしたAI・指摘・採用・採用しなかった理由）と、受け入れ条件の確認を、Issueのファイルに追記する |
| マージ（Squash） | 手元で`main`に取り込む。取り込みは1つのコマンド（例：`npm run merge:check`）で行い、品質チェックとテストのすべて（`npm run check`）が通った場合だけ取り込む。取り込んだらIssueのファイルの状態を「完了」にする |
| ブランチ保護（[C-42](#c-42)） | Gitのフック（`pre-commit`）で、`main`の上での直接のコミットを止める。取り込みのコマンドによる取り込みだけを許す |
| CI（[F-12](../functional.md#f-12)） | なし。コミットの前に軽い確認（秘密情報の混入（gitleaks、[C-82](quality-test.md#c-82)）・整形・Lintを、変えたファイルだけ）を`pre-commit`で行う。全部の確認は取り込みのコマンドで行う |
| 公開・非公開（[F-13](../functional.md#f-13)） | 非公開として扱い、質問しない。`LICENSE`は作らない |
| ハーネスの改善の提案（[C-78](#c-78)） | 提案の下書きを`docs/harness-feedback/`に置き、利用者がハーネスのリポジトリに伝える |

- **MUST**：フックは、生成するプロジェクトに入れる（`.githooks/`等に置き、`git config core.hooksPath`を設定する手順をREADMEに書く）。フックを外して確認を飛ばさない（[C-75](design-principles.md#c-75)）
- **MUST**：GitHubのコマンド（`gh`）を使う手順は、AIに実行させない。Skill・AGENTS.mdでは、GitHubを使う場合と使わない場合の手順を分けて書き、プロジェクトの設定（`.harness/config.yaml`）に合う方だけを使う
- 後でGitHubに移す場合は、`.harness/config.yaml`の設定を変えて`harness update`を実行し、`.github/`等を加える。`docs/issues/`のIssueをGitHubのIssueに移す方法は、移すときに決める
