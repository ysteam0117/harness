# 2.4 フロントエンド

React（TypeScript）を前提とする。ルールの強さは次の3段階で表す。

| 表記 | 意味 |
| --- | --- |
| **MUST** | 必ず守る |
| **MUST NOT** | 必ず避ける |
| **SHOULD** | 原則として守る。守らない場合は理由をPR等に書く |

| ID | 内容 |
| --- | --- |
| [C-06](#c-06) | フロントエンドは決められたディレクトリ構成に従い、**責務を分離**する |
| [C-43](#c-43) | コンポーネントは主な責務を1つにし、Propsには型を付けて必要なデータだけを渡す |
| [C-44](#c-44) | TypeScriptは`strict`で使い、`any`や型エラー回避のためのキャストを使わない |
| [C-45](#c-45) | 状態はUI状態とServer Stateに分けて管理し、`useEffect`は外部システムとの同期に限る |
| [C-46](#c-46) | API通信は専用の層に集約し、エラーを明示的に処理し、レスポンスを検証する |
| [C-47](#c-47) | フォームは画面側とサーバー側の両方で入力チェックし、多重送信を防ぐ |
| [C-48](#c-48) | 非同期の画面ではloading・success・empty・errorを明示的に扱い、利用者向けの表示とログを分ける |
| [C-49](#c-49) | 外部入力を信頼せず、秘密情報をフロントエンドに含めず、認可をフロントエンドだけで保証しない |
| [C-50](#c-50) | 性能の最適化は根拠に基づいて行い、`key`には安定した一意のIDを使う |
| [C-51](#c-51) | 要素の意味に合ったHTMLを使い、キーボードで操作できるようにする |
| [C-52](#c-52) | 機能変更・不具合修正にはテストを伴わせ、利用者の操作に基づいて検証する |
| [C-54](#c-54) | フロントエンドの完了の定義を満たしてから完了とする |
| [C-55](#c-55) | アプリアイコン・ファビコンは必ず用意し、画像がない場合は仮の画像を入れて後で差し替える |

<a id="c-06"></a>

## C-06：ディレクトリ構成と責務

```text
src/
├─ pages/          ルーティング単位の画面（レイアウトと機能の組み合わせのみ）
├─ features/       機能単位の実装
├─ components/     全体で使う共通UI
├─ hooks/          共通Custom Hook
├─ services/       共通のAPI通信
├─ schemas/        共通のZodスキーマ
├─ types/          共通の型
├─ utils/          純粋関数
├─ constants/      共通の定数
└─ test/           テストの共通処理
```

| ディレクトリ | 置くもの | 置かないもの |
| --- | --- | --- |
| `pages/` | URLごとの画面。レイアウトと、機能の組み合わせだけを行う | API通信、状態管理、業務ロジック |
| `components/` | 複数の機能で使う見た目の部品 | API通信、汎用ロジック、特定の機能に依存する処理 |
| `features/` | 機能ごとの実装（その機能専用の部品・Hook・API層・スキーマ・定数） | 他の機能から直接参照される共通処理 |
| `hooks/` | 複数の機能で使うCustom Hook | 1つの機能でしか使わないHook（`features/`に置く） |
| `services/` | 複数の機能で使うAPI通信 | 画面の状態、表示の処理 |
| `schemas/` | Zodスキーマ（入力チェック・APIレスポンスの検証） | ロジック |
| `types/` | 複数の機能で使う型 | ロジック |
| `utils/` | 画面や状態に依存しない純粋関数（日付の整形など） | 状態、API通信 |
| `constants/` | 定数 | 環境によって変わる値（設定として扱う） |
| `test/` | テストの共通処理（テスト用の描画関数、モック等） | 本番コード |

- **MUST**：API通信の処理は、`services/`または各機能の`features/<機能>/api`層に置く
- **MUST NOT**：画面のコンポーネントの中に、`fetch`・`axios`を直接書かない（API通信はAxiosのインスタンスを使う。下記「Axiosとインターセプター」）
- **MUST NOT**：汎用ロジックを`components/`に置かない
- **MUST NOT**：`pages/`にAPI通信・状態管理・業務ロジックを書かない
- **MUST NOT**：`features/`から`pages/`を参照しない
- **SHOULD**：ほかの機能の内部を直接参照せず、各機能の公開部分（`index.ts`）を通す
- 依存の向きは「`pages/` → `features/` → 共通のもの（`components/`・`hooks/`・`services/`等）」の一方向とする
- 1つの機能でしか使わないスキーマ・定数・Hookは、共通のディレクトリではなく`features/<機能>/`に置く
- データの流れは「画面 → Hook → API層 → バックエンド」の一方向とし、見た目の部品は表示に専念させる。Webアプリ・モバイルアプリの両方で同じ考え方を使う

<a id="c-43"></a>

## C-43：コンポーネントの責務とProps

責務

- **MUST**：1つのコンポーネントの主な責務を1つにする
- **SHOULD**：表示と複雑な状態管理が混ざる場合は、状態管理をCustom Hookに分ける
- **SHOULD**：独立した複数の表示領域を持つ場合は、子コンポーネントに分ける
- **MUST NOT**：API通信・データ変換・入力チェック・画面の描画を、1つのファイルに集中させない
- 分割するかどうかは、行数よりも責務で判断する

Props

- **MUST**：Propsの型を定義する
- **SHOULD**：子コンポーネントには、必要なデータだけを渡す
- **MUST NOT**：大きなオブジェクトを、理由なく丸ごと子コンポーネントへ渡さない
- **SHOULD**：Propsのバケツリレー（Props drilling）が深くなる場合は、設計を見直す

<a id="c-44"></a>

## C-44：TypeScriptの型

- **MUST**：`tsconfig`の`strict`を有効にする
- **MUST**：公開する関数・APIレスポンス・Propsには、明示的な型を付ける
- **MUST NOT**：`any`を原則使わない
- **MUST NOT**：型エラーを回避することだけを目的に、`as`によるキャストを使わない
- **SHOULD**：型が分からない値は`unknown`で受け、型ガードまたはZodで絞り込む

<a id="c-45"></a>

## C-45：状態管理・Hooks・useEffect

状態管理

- **MUST**：コンポーネント固有のUIの状態には、`useState`を使う
- **MUST**：サーバーから取得したデータは、Server Stateとして扱う
- **SHOULD**：Server Stateの管理には、TanStack Queryを使う
- **SHOULD**：複数の画面で共有するUIの状態に限り、Zustand等を検討する
- **MUST NOT**：Server Stateをグローバルなストアへコピーして、二重に管理しない

Custom Hook

- **MUST**：Hookの名前は`use`から始める
- **MUST**：Hookの中でも、React Hooksのルールを守る
- **SHOULD**：複数の状態・副作用・イベント処理をまとめる場合に、Custom Hookを検討する
- **MUST NOT**：単純な1〜2行の処理を、理由なくHookにしない
- 再利用性がなく単純な処理は、抽象化しない（[C-38](design-principles.md#c-38)）

useEffect

- **MUST NOT**：値を計算するだけの目的で`useEffect`を使わない
- **MUST NOT**：PropsやStateから導き出せる値を、別のStateとして持たない
- **SHOULD**：`useEffect`は、外部システムとの同期に限って使う
- **MUST**：`useEffect`を使う場合は、依存配列の意味を確認する

<a id="c-46"></a>

## C-46：API通信

- **MUST**：API通信は専用の層（[C-06](#c-06)）に集約する
- **MUST NOT**：コンポーネントから直接`fetch`・`axios`を呼び出さない
- **MUST**：HTTPのエラーを明示的に処理する（401・403の扱いはC-15に従う）
- **MUST**：APIのレスポンスを、TypeScriptの型だけで信用しない
- **SHOULD**：外部APIのレスポンスは、Zod等で検証する

### Axiosとインターセプター

API通信にはAxiosを使い、全体に共通する処理はインターセプター（すべての要求・応答の前後に共通の処理を挟む仕組み）にまとめる。各所に同じ処理を書かないことで、読みやすさと保守性を上げる。

- **MUST**：Axiosのインスタンスは、API層（`services/`）で1つ作り、アプリ全体でそれを使う。コンポーネントやHookから`axios`を直接importしない
- **MUST**：共通の設定（接続先のURL・時間切れの時間・Cookieを送る設定等）は、インスタンスにまとめて書く。接続先のURLは環境変数から読む（[C-40](project-env.md#c-40)）
- 要求のインターセプターで行うこと
  - リクエストIDの付与（[C-30](backend.md#c-30)）
  - 認証・CSRF対策に必要なヘッダーの付与（[C-17](security.md#c-17)・[C-28](security.md#c-28)。認証トークンの扱いは、プロジェクトの認証設計に従う）
- 応答のインターセプターで行うこと
  - エラーを、アプリ内で扱う共通のエラーの形（HTTPステータス・アプリケーションエラーコード・利用者向けメッセージ）に変換する（[C-15](error-response.md#c-15)・[C-73](error-response.md#c-73)）
  - `401`を受けた場合の、認証の更新と、ログイン画面への遷移（[C-15](error-response.md#c-15)の手順。更新・遷移を重複させない）
  - エラーのログへの記録（[C-30](backend.md#c-30)。秘密情報を出さない）
- **MUST NOT**：インターセプターの中でエラーをもみ消さない。変換した後も、必ず失敗として呼び出し元へ返す（[C-71](error-response.md#c-71)）
- **MUST NOT**：インターセプターに、特定の画面や機能だけの処理（業務ロジック）を書かない。全体に共通する処理だけにする
- 取得したデータの保持・再取得・キャッシュは、TanStack Query（[C-45](#c-45)）が担当し、インターセプターは通信に共通する処理だけを担当する
- Axiosの追加は、ライブラリの追加の承認（[C-32](quality-test.md#c-32)）として記録し、バージョンを固定する（[C-62](quality-test.md#c-62)）

<a id="c-47"></a>

## C-47：フォームと入力チェック

- **MUST**：画面側（クライアント側）の入力チェックを実装する
- **MUST**：サーバー側でも入力チェックすることを前提にする（[C-27](security.md#c-27)）。画面側のチェックは利用者の補助であり、代わりにならない
- **SHOULD**：React Hook Form＋Zodを標準にする。Zodスキーマは`schemas/`に置く
- **MUST**：送信中は、多重送信を防ぐ
- **MUST**：API側でも、二重送信の対策とデータの整合性の保証を行うことを前提にする

<a id="c-48"></a>

## C-48：画面の状態とエラー表示

画面の状態

- **MUST**：非同期でデータを扱う画面では、次の4つの状態を明示的に扱う
  - loading（読み込み中）
  - success（成功）
  - empty（データなし）
  - error（エラー）

エラー表示

- **MUST**：予期できるエラー（入力の誤り、権限不足など）と、予期しないエラーを区別する
- **MUST**：利用者向けのエラー文と、ログへの出力を分ける（[C-15](error-response.md#c-15)・[C-30](backend.md#c-30)）
- **MUST NOT**：内部の例外・スタックトレース・機密情報を、画面に表示しない
- **SHOULD**：React Error Boundaryを適切な単位で配置する

<a id="c-49"></a>

## C-49：フロントエンドのセキュリティ

- **MUST NOT**：`dangerouslySetInnerHTML`を原則使わない（[C-27](security.md#c-27)）
- **MUST NOT**：秘密鍵・API Secret・パスワードをフロントエンドのコードに含めない
- **MUST NOT**：認可の判断を、フロントエンドだけで保証しない。フロントエンドでの権限制御は表示の制御であり、最終的な認可はバックエンドで行う（[C-13](security.md#c-13)）
- **MUST**：外部からの入力を信頼しない。URL・フォームの値・APIのレスポンスを、外部からの入力として扱う
- **SHOULD**：認証トークンの保存方法は、プロジェクトの認証設計（[C-17](security.md#c-17)）に従う

<a id="c-50"></a>

## C-50：パフォーマンス

- **MUST NOT**：根拠なく`useMemo`・`useCallback`・`memo`を使わない
- **SHOULD**：実測の結果、または再レンダリング上の明確な理由がある場合に使う
- **SHOULD**：大量のリストでは、ページング・仮想化（virtualization）等を検討する
- **MUST**：Reactの`key`には、安定した一意のIDを使う
- **MUST NOT**：配列の添字（index）を、安易に`key`として使わない

<a id="c-51"></a>

## C-51：アクセシビリティ

- **MUST**：ボタンの役割を持つ要素には、`button`要素を使う
- **MUST**：フォームの入力欄には、`label`を設定する
- **MUST**：画像には、適切な`alt`を設定する
- **MUST**：キーボードだけで操作できるようにする
- **SHOULD**：`aria`属性は、必要な場合に限って使う

<a id="c-52"></a>

## C-52：フロントエンドのテスト

[C-24](quality-test.md#c-24)〜[C-26](quality-test.md#c-26)に加えて、次を守る。

- **MUST**：機能を変更するときは、対応するテストを追加または更新する
- **MUST**：不具合を修正するときは、再発を防ぐテストを追加する
- **SHOULD**：純粋なビジネスロジックには、単体テストを書く
- **SHOULD**：Reactコンポーネントは、Testing Libraryを使って利用者の操作に基づいて検証する
- **MUST NOT**：内部の実装だけを検証するテストに頼らない
- **SHOULD**：主要な利用の流れは、E2Eテストで担保する（[C-24](quality-test.md#c-24)）

<a id="c-54"></a>

## C-54：フロントエンドの完了の定義

[C-34](workflow.md#c-34)に加えて、次のすべてを満たした場合だけ、フロントエンドの実装を完了とする。

- 要求された機能が動作する
- TypeScriptのエラーがない
- ESLintのエラーがない
- フォーマッターを適用している
- 対象のテストが成功している
- 既存のテストを壊していない
- loading・error・emptyの状態を考慮している
- アクセシビリティを確認している（[C-51](#c-51)）
- 不要な`console.log`が残っていない
- 不要な依存関係を追加していない
- セキュリティのルール（[C-49](#c-49)）に違反していない

<a id="c-55"></a>

## C-55：アプリアイコン・ファビコン

- **MUST**：アプリアイコンとファビコンを必ず用意する。CLIはプロジェクトを生成するときに、次の仮の画像を必ず出力する
  - ファビコン（`favicon.ico`・`favicon.svg`）
  - スマートフォンのホーム画面用アイコン（`apple-touch-icon.png`）
  - Web App Manifest用のアイコン（192×192・512×512）と、それを参照する`manifest`ファイル
- 仮の画像は、アプリ名の頭文字などを入れた単純なものとし、仮であることが分かるようにする
- **MUST**：仮の画像を使っていることを、生成するプロジェクトのREADMEと、差し替え用のIssueに記録する。本番へ公開する前に正式な画像へ差し替える
- 差し替えるときは、同じファイル名・サイズで置き換えるだけで済むようにする
