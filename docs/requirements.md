## 1. プロジェクト概要

| 項目 | 内容 |
| --- | --- |
| プロジェクト名 | ハーネス設計 |
| 目的 | AIが機能を実装するときに、構成・実装方法・GitHubフロー・テスト機構などがブレないようにする |
| 想定ユーザー | 本人と身内（少人数・内部利用） |
| 成果物の形 | **CLIツール**。コマンドを実行して質問に答えると、ハーネス一式（AI向け設定ファイル・ルール・テンプレート等）が生成される |
| 実装言語 | **TypeScript（Node.js）**。`npx`で実行できる形で配布する |

### 成果物の形をCLIツールにした理由

- AIがなくても動き、同じ回答なら毎回同じハーネスが生成される（AIによるブレをなくすというこのプロジェクトの目的に合う）
- 質問の分岐・整合性チェックのルールがコードとして明文化される

### 進め方の方針

- 最初は言語に依存しない**共通部分**から決める
- 言語ごとの差分は、共通部分が固まってから追加する

### 初回完成（`0.0.0`）の範囲

初回は、よく作る構成1つに絞って完成させ、その後に対応範囲を広げる。

| 項目 | 初回の範囲 | 初回の後に追加する予定 |
| --- | --- | --- |
| プロジェクト種別 | Webアプリ（画面＋API） | モバイルアプリ（Webアプリの内容に沿って作成）、APIのみ |
| インフラ・デプロイ先 | Cloudflare | — |
| フロントエンド | React（TypeScript） | — |
| バックエンド | Hono（TypeScript） | Spring Boot（Java） |
| DB | Cloudflare D1（標準）／PostgreSQL（Hyperdrive経由、クライアントの要望がある場合） | — |

- Spring Bootは、Cloudflare Workersで動かせずデプロイ先・品質チェックが別系統になるため、初回の範囲から外す。層構成（C-03）は言語共通のため、後から技術スタックの選択肢として追加する
- DBはD1とPostgreSQLの両方を選べるようにするため、データアクセスのライブラリは両方に対応するものを選ぶ（#5で決定）

## 2. 共通仕様（全プロジェクトに適用するルール）

全プロジェクトに適用する設計・開発のルール。多くは対話で質問しない固定ルールだが、C-12（認証方式）のように、CLIの質問で選んだ内容に応じて適用範囲が変わるものも含む。

番号（C-xx）は項目の識別子であり、見出しの中では番号順に並ばない。項目を追加するときは、次の番号を振って該当する見出しに入れる。

#### C-07：Issueの分け方

1つの機能・1つの文書を**親Issue**とし、必要な作業を**子Issue**（GitHubのsub-issue）に分ける。子Issueごとにブランチ・PRを作成し、親Issueは全体の進み具合と完了条件を管理する。

##### 機能実装の場合

| 階層 | 内容 | 例 |
| --- | --- | --- |
| 親Issue | 実装する機能と、その完了条件 | ログイン機能を実装する |
| 子Issue | 機能に必要な作業を、作業領域ごとに分けたもの | 下表を参照 |

| 作業領域 | 子Issueにする条件 | 例 |
| --- | --- | --- |
| DB | テーブル・カラムの追加や変更がある | ユーザーテーブルのマイグレーション |
| バックエンド | APIや業務ロジックの追加・変更がある | ログインAPI（Controller／Service／Repository） |
| フロントエンド | 画面や部品の追加・変更がある | ログイン画面（PasswordFieldを含む） |
| その他 | CI・インフラ・設定の変更がある | 認証用の環境変数の追加 |

- 必要のない作業領域の子Issueは作らない（例：画面のないAPIのみの機能ではフロントエンドの子Issueを作らない）
- 子Issueの間に依存関係がある場合は本文に明記する（例：バックエンドのIssueはDBのIssueの完了後に着手する）
- 各子Issueには、その作業領域での完了条件を書く

##### 文書作成の場合

親Issueを文書全体とし、子Issueを章（タイトル）ごとに分ける。この要件定義書もこの方式で管理する（親Issue #1）。

#### C-21：ブランチ名

`<種類>/<Issue番号>-<内容>` の形式にする。内容は英小文字とハイフンで短く書く。

| 種類 | 使うとき | 例 |
| --- | --- | --- |
| `feature` | 機能の追加 | `feature/12-login-api` |
| `fix` | 不具合の修正 | `fix/15-password-toggle` |
| `docs` | 文書の追加・修正 | `docs/3-common-spec` |
| `refactor` | 動作を変えないコードの整理 | `refactor/20-split-user-service` |
| `chore` | 設定・依存関係・CIなどの変更 | `chore/8-add-eslint` |

#### C-22：コミットメッセージ

Conventional Commits に従い、`<種類>: <説明>` の形式にする。種類は英語、説明は日本語で書く。

| 種類 | 使うとき | 例 |
| --- | --- | --- |
| `feat` | 機能の追加 | `feat: ログインAPIを追加` |
| `fix` | 不具合の修正 | `fix: パスワード表示トグルが動かない問題を修正` |
| `docs` | 文書のみの変更 | `docs: 共通仕様にブランチ名のルールを追加` |
| `refactor` | 動作を変えないコードの整理 | `refactor: UserServiceを分割` |
| `test` | テストの追加・修正のみ | `test: ログインAPIの認可テストを追加` |
| `chore` | 設定・依存関係・CIなどの変更 | `chore: ESLintを導入` |

- 以前の内容と両立しない変更には、種類の後ろに`!`を付ける（例：`feat!: APIのレスポンス形式を変更`）。初回完成後は、C-08のバージョンを上げる判断に使う

#### C-23：PR

- 本文に `Closes #<子Issue番号>` を書き、マージと同時に子Issueが自動でクローズされるようにする。親Issueは `Refs #<親Issue番号>` で参照し、クローズしない
- マージは **Squash** で行い、PR1つが`main`上のコミット1つになるようにする。Squash後のコミットメッセージもC-22に従う
- マージ前に、C-24のテストと品質チェック（F-16）が通っていることを確認する
- マージ後は、ローカルの`main`を最新にし、統合済みであることを確かめてから、対応するローカルの作業ブランチを削除する。別のworktreeで使用中のブランチや、未コミットの変更があるブランチは削除せず、状態を報告する

#### C-42：`main`ブランチの保護

- `main`ブランチへの直接のpushを禁止する。AIも利用者も、変更はすべてC-21のブランチからPRを作成し、C-23に従ってマージする
- GitHubのブランチ保護（またはRuleset）で、直接のpushと強制push（force push）を禁止する設定を行う。設定の手順は生成するプロジェクトのREADMEに記載する
- 例外的に`main`を直接変更する必要が生じた場合も、AIは実行せず、理由を示してユーザーに判断を求める

#### C-08：バージョンの付け方

##### 初回完成まで

- バージョンは付けない。Issueを解決しても、バージョンは上げない
- ハーネスが一通り完成した時点で`0.0.0`を付ける

##### 初回完成後

| 桁 | 上げるとき | 例 |
| --- | --- | --- |
| MAJOR | 以前の内容と両立しない大きな変更をしたとき | `0.4.2` → `1.0.0` |
| MINOR | 項目の追加・仕様の決定など、内容が増えたとき | `0.0.3` → `0.1.0` |
| PATCH | 誤字の修正・表現の調整など、意味が変わらない修正をしたとき | `0.1.0` → `0.1.1` |

- 下の桁は、上の桁を上げたときに`0`へ戻す
- 要件定義書と、ハーネスが生成するプロジェクト・CLIツール本体のすべてに同じルールを適用する

#### C-11：Superpowersを使ったAI開発フロー

- Claude CodeまたはCodexを利用する開発では、Superpowersプラグインを利用可能な状態にする。プラグインは各AI環境に個別に導入する。
- 要件整理・設計では`brainstorming`を使い、ユーザーへの質問、選択肢とトレードオフの整理、合意した設計の記録を行う。設計の合意前に実装へ進まない。
- 設計合意後は`writing-plans`で作業を実行可能な単位へ分解し、実装では`test-driven-development`、`requesting-code-review`、`verification-before-completion`等の該当スキルを使う。
- Superpowersの手順・成果物は日本語を基本とし、スキル名やコマンド名は識別できるよう原文のまま記載してよい。
- プラグインが利用できない場合は、その旨をユーザーに伝え、必要な導入手順を案内する。プラグインを前提とする作業を、利用できないまま黙って進めない。
- プラグインの導入はユーザーのAI環境に対して行い、生成したアプリケーションの実行時依存には含めない。プラグインを自動インストールするスクリプトは生成しない。
- Superpowersの指示は、ユーザーの指示とプロジェクト固有ルールに従う。
- 実装の進め方はC-66の流れを主とし、SuperpowersのSkillは各役割の中で使う（C-66の「Superpowersとの関係」を参照）。

#### C-33：レビューの進め方

- 実装したAIとは別のAIでレビューする。見落としの重なりを減らすため、次の優先順位に従う
  1. 原則：別の会社のAIでレビューする（例：Claude Codeで実装したらCodexでレビューする）
  2. 1が使えない場合：同じ会社の別のモデルで、新しい会話（実装の経緯を渡さない状態）でレビューする
  3. 最低限：同じモデルでも、必ず新しい会話でレビューする。実装と同じ会話の中での見直しは、レビューとして扱わない
- どの段階でレビューしたかを、レビュー結果の記録（C-66）に書く
- 合意済みの設計判断（ADR等で決定したもの）がレビューで再び指摘された場合は、レビューの回数に数えず、コードも変更しない。既知のトレードオフである理由と参照先を、レビューしたAIに伝えるだけにする
- レビューの指摘は、そのまま受け入れず、要求・仕様に照らして妥当かを確認してから対応する。対応しない指摘は理由を記録する
- 人によるレビューは任意とする。開発人数（F-14）にかかわらず、この流れは同じとする

#### C-66：AIによる実装の進め方

Issue 1件の実装を、次の役割に分けて進める。

| # | 役割 | やること | 触ってよいもの | 成果物 |
| --- | --- | --- | --- | --- |
| 0 | 統括 | 全体の進行。各役割を呼び出し、成果物を受け渡し、完了の定義（C-34）で判定する | — | 最終報告 |
| 1 | 計画 | Issueの受け入れ条件から、変更するファイル・手順・テストケースを決める | 読み取りのみ | 実装計画 |
| 2 | 計画レビュー | 計画の要件漏れ・既存の動作の退行・テスト不足・秘密情報の混入を指摘する | 読み取りのみ | 指摘 |
| 3 | テスト | 受け入れ条件（C-26）からテストを実装より先に書く（この時点では失敗する） | テストのファイルのみ | テスト |
| 4 | 実装 | テストが通るように実装する | 計画にあるファイルのみ。テストは変更しない | 実装 |
| 5 | 品質チェック | Lint・型・テスト・E2E等を、手元とCIで共通の1つのコマンド（C-61）で実行し、失敗の原因を報告する | 読み取りと実行のみ | 結果の報告 |
| 6 | コードレビュー | 実装とは別のAIでレビューする（C-33） | 読み取りのみ | 指摘 |
| 7 | ドキュメント | 変更に関係する文書（API仕様・要件定義書・`tech-stack.md`・ADR・README）を確認・更新し、PRの「知見」の欄（F-18）を書く | 文書のみ | 文書の更新、PR本文 |

- テスト（3）と実装（4）を別の役割にし、テストを先に書くことで、実装に合わせて期待値を決めることを防ぐ（C-25）。実装の役割がテストを変更する必要があると判断した場合は、理由を示して統括に戻し、テストの役割が要求に照らして修正する
- 各役割は、表の「触ってよいもの」の範囲を超えて変更しない

##### レビューの回数

- 計画レビュー・コードレビューとも、最大3回とする。重大な指摘があれば修正して再レビューする
- 3回目でも重大な指摘が残る場合は、先に進まず、ユーザーに判断を求める
- ただし、データ破損・認証の回避・情報漏えいにつながる重大な指摘は、回数の上限を超えても、解消するまでレビューを続ける
- レビューを重ねた結果、Issueが「単独でレビュー・マージできる最小単位」を明らかに超えた場合（新しい基盤が必要になった、複数の独立した成果物に分かれた、手間と価値が釣り合わない等）は、レビューを続けずにユーザーに相談する。「厳密にやる／範囲を縮める／後回しにする」の選択肢と、範囲を縮めた場合に何を名乗れなくなるかを示す。範囲を縮めた場合は、検証の限界を成果物に明記する

##### ユーザーによる動作確認

- 品質チェック・コードレビューが終わったら、コミットの前に一度止まり、ユーザーに動作確認を依頼する。確認の手順と、確認してほしい受け入れ条件を示す
- 変更の大きさが「小」の場合は、動作確認を省略してよいかをユーザーに確認する

##### 複数のIssueを続けて進める場合

次をすべて満たす場合は、ユーザーに確認せずに次のIssueに着手してよい。

- 直前のIssueのPRがマージ済みである
- 直前のIssueの受け入れ条件と動作確認を満たしている
- 次のIssueが依存するIssueが、すべて完了している

次の場合は、必ず立ち止まってユーザーに判断を求める。

- ユーザーによる動作確認が必要な工程に着いた
- 文書と実装の食い違いを見つけた（どちらを正とするかの判断が必要）
- 依存ライブラリの追加など、共通仕様に影響する変更が必要になった
- 要件定義書等で「要調査」「未検証」とされている項目に着手する

##### 記録

- 実装計画、計画レビュー・コードレビューの結果（指摘の数・採用した数・採用しなかった指摘と理由）、品質チェックの結果を、該当するIssueのコメントに残す
- 実装中に計画を変更した場合は、変更した内容と理由を、その都度Issueのコメントに残す
- レビューの結果の記録は、どのAIがどの役割に向いているかを知見（F-18）として確かめる根拠にも使う

##### Superpowersとの関係

この流れを主とし、SuperpowersのSkill（C-11）は各役割の中で使う。

| 役割 | 使うSkillの例 |
| --- | --- |
| 計画 | `brainstorming`（要件が曖昧な場合）、`writing-plans` |
| テスト | `test-driven-development` |
| コードレビュー | `requesting-code-review` |
| 統括（完了の判定） | `verification-before-completion` |

##### 変更の大きさと起動する役割

毎回すべての役割を起動すると、時間とトークンが増えるため、変更の大きさによって起動する役割を変える。大きさは次の基準で決める。

| 大きさ | 基準 | 起動する役割 |
| --- | --- | --- |
| 小 | 誤字の修正・文書だけの変更・設定値1か所の変更など、動作のロジックを変えないもの | 実装 → 品質チェック → コードレビュー |
| 通常 | 小・影響大のどちらにも当たらないもの | すべての役割 |
| 影響大 | 認証・認可・個人情報・データ移行・DBスキーマの破壊的変更に関わるもの | すべての役割。テストの設計とコードレビューは上位のモデルで行う |

- どの大きさでも、完了の定義（C-34）と、テスト・品質チェックが通ることは省略しない
- 判断した大きさと理由を、Issueのコメントに書く

##### 運用のルール

- **MUST**：各役割には、会話全体ではなく、目的・対象のファイル・制約・完了条件など必要な情報だけを渡す。レビューの役割には実装の経緯を渡さない（C-33）
- **MUST**：品質チェックは実行結果と要件（受け入れ条件）との照合を、コードレビューはコードの不具合・影響範囲・テスト不足を担当し、範囲を重ねない
- **MUST**：レビューの1回目は全体を確認し、2回目以降は指摘した箇所とその関連部分に絞って確認する（上限の3回は変えない）
- **MUST**：最初から全員を上位のモデルにしない。次の条件に当たる場合に切り替える

| 条件 | 切り替え先 |
| --- | --- |
| 認証・認可・個人情報・データ移行・重要な業務ルールに関わる（テストの設計・コードレビュー） | 一番性能の高いモデル |
| 複雑な新規設計や、重大な設計判断が必要 | 一番性能の高いモデル |
| 同じ失敗を2回直しても解消しない | 一番性能の高いモデル。または計画の役割に戻す |
| 単純な置換・定型の変更 | 軽いモデル |

##### 役割とAI・モデルの割り当て

- モデル名はハーネスのルールに直接書かず、「役割 → AI・モデル」の対応を設定ファイルにし、プロジェクトごとに変えられるようにする
- 生成時に、主に使うAIに応じて次の初期値を設定する。モデル名は変わるため、設定する前に、実際に選べるモデル名を確認する

| 役割 | Claude Codeが主の場合 | Codexが主の場合（推論の強さ） |
| --- | --- | --- |
| 統括 | Opus 5.5 | GPT-6 Sol（medium） |
| 計画 | Opus 5.5 | GPT-6 Sol（high）。複雑な新規設計はGPT-6 Astra |
| 計画レビュー | 別の会社のAI。使えなければOpus 5.5（新しい会話） | 別の会社のAI。使えなければGPT-6 Solの別エージェント（high）。重大な設計判断はGPT-6 Astra |

| コードレビュー | 別の会社のAI。使えなければOpus 5.5（新しい会話） | 別の会社のAI。使えなければGPT-6 Solの別エージェント（high）。認証・権限・データ移行等はGPT-6 Astra |

- レビューのとき、計画と同じモデルを使う場合は、計画を作った会話とは別の、新しい会話で行う
- 割り当ては、レビュー結果の記録（指摘の数・採用した数・誤った指摘の数）をもとに、知見（F-18）として見直す

#### C-67：日本語での表示

- **MUST**：AIが利用者に見せるもの（作業中の説明・途中経過・報告・計画・レビュー結果・質問）と、Issue・PR・コミットメッセージの説明部分は、すべて日本語で書く
- **MUST**：サブエージェントや別のAI（Codex等）に作業を依頼するときも、日本語で出力するよう指示に含める。英語で返ってきた結果は、日本語にしてから利用者に見せる
- 関数名・ファイル名・コマンド・エラーメッセージの原文・ライブラリ名など、識別に必要なものは原文のまま書いてよい
- このルールは、生成する`CLAUDE.md`・`AGENTS.md`の冒頭に明記する（AIの種類によって英語が混ざりやすいため）

#### C-68：AI向けの設定の共有範囲

| 種類 | 中身 | 置き場所 | 他の人への反映 |
| --- | --- | --- | --- |
| プロジェクトのルール | 共通仕様を実現するためのSkill・エージェントの定義（C-66の役割、テストのルール等） | プロジェクトのリポジトリ（コミットする） | 反映される。変更は必ずPRを通す（C-42）ため、知らないうちには変わらない |

- 各自のAI環境に入れるプラグインのうち、必須とするのはSuperpowers（C-11）だけとする。それ以外のプラグイン・Skillは個人の道具として扱い、使うかどうかは各自が決める
- **MUST NOT**：個人の道具をプロジェクトのリポジトリにコミットしない。コミットすると、pullした全員に自動で反映されてしまう
- **MUST NOT**：個人の設定ファイル（`settings.local.json`等）はコミットしない
- 個人の道具を他の人に紹介する場合は、ハーネスのリポジトリの「任意のSkillの一覧（カタログ）」に、できること・導入方法を書き、Issue等で知らせる。使うかどうかは各自が決め、使う人だけが自分の個人の設定フォルダに入れる

#### C-34：完了の定義（Definition of Done）

次のすべてを満たしたときに、作業を完了とする。AIは、満たしていない項目がある状態で完了を報告しない。

1. Issueの受け入れ条件をすべて満たしている
2. 該当するテスト（C-24）と品質チェック（F-16）が通っている
3. 変更に関係する文書（要件定義書・API仕様・README等）を更新している
4. PRにIssueを紐付けている（C-23）

#### C-35：記録の置き場所

| 記録する内容 | 置き場所 |
| --- | --- |
| 作業中のやり取り・判断、テストを省略した理由、レビュー指摘への対応 | 該当するIssue・PR |
| 後から参照する大きな設計判断（DAOの構成を選んだ理由、ライブラリの選定理由など） | `docs/adr/`に1件1ファイル（ADR） |
| 確定した仕様 | 要件定義書・API仕様などの文書 |

- 学びや手直しの記録は、専用のファイル（`lessons-learned.md`等）を作らず、ADRと、PRの「知見」の欄（F-18）にまとめる
- ADRには、背景・選択肢・決定・理由を書く。決定を変えるときは、元のADRを消さずに新しいADRを追加する

### 2.2 プロジェクト構成・環境

| ID | 内容 |
| --- | --- |
| C-02 | **1つのリポジトリ内で`frontend/`と`backend/`にディレクトリを分ける**（モノレポ） |
| C-36 | バックエンドとDBの開発環境は**Dockerコンテナ**で動かす。コンテナ名は**アプリ名**を基本にする |
| C-39 | 本番環境は**IaC（Terraform等）**で構築し、コードから同じ環境を再現できるようにする |
| C-40 | 環境は**開発・検証・本番**の3つに分け、用途を混ぜない |
| C-41 | デプロイは自動化せず**開発リーダーの承認**で行う。切り戻しは前バージョンの再デプロイを基本とし、本番DBの変更は後方互換性を確保してから破壊的変更を行う |

#### C-36：開発環境のDockerコンテナ

- バックエンドとDBの開発環境は、Docker（Docker Compose）のコンテナで動かす。開発者のPCに直接インストールする必要があるものを減らし、誰の環境でも同じ状態で動かせるようにする
- DBがCloudflare D1の場合は、開発ツール（wrangler）がローカルでSQLiteファイルとして再現するため、DB専用のコンテナは作らず、バックエンドのコンテナの中で扱う。PostgreSQLの場合は、DB用のコンテナを作る

##### D1を使う場合の開発環境（本番と互換性のある構成）

D1を最初から使う場合は、本番と同じ実行環境をローカルで再現できるため、次の方式を標準とする。

| 項目 | 方式 |
| --- | --- |
| 実行環境 | バックエンドのコンテナ内で`wrangler dev`をローカルモードで動かす。本番のCloudflare Workersと同じ実行エンジン（workerd）でHonoのアプリが動く |
| DB | wranglerがローカルに再現するD1（SQLiteファイル）を使う。本番のD1と同じSQLite系のSQLで動く |
| データの保持 | ローカルのD1のデータ（`.wrangler/state`）は、Dockerのボリュームで保持し、コンテナを作り直しても消えないようにする。このフォルダはコミットしない |
| マイグレーション | 本番と同じマイグレーションファイルを使い、まずローカルに適用して確認してから、本番に適用する |
| テスト | 結合テストも同じローカルのD1に対して実行し、テストごとに初期状態へ戻せるようにする |

- 開発・テストでは、本番のD1に接続する設定（`--remote`等）を使わない（C-05のテストデータのルール）。本番への適用は、デプロイの手順としてユーザーの承認を得て行う
- ローカルのD1は、本番と比べてデータ量・性能・利用上限が異なる。実行計画の確認（C-10）はローカルで行えるが、性能の最終判断は実運用に近いデータ量で行う
- 使うツールのバージョンと具体的な設定（`wrangler.toml`の書き方、テストの実行方法等）は、技術スタック別に定める

##### 命名規則

- Docker Composeのプロジェクト名（`name:`）をアプリ名にする
- コンテナ名は `<アプリ名>-<役割>` にする（例：`myapp-backend`、`myapp-db`）。コンテナが1つだけの場合も役割を付けてそろえる
- アプリ名は英小文字・数字・ハイフンで書く
- DBの認証情報などは`docker-compose.yml`に直接書かず、`.env`から読み込む（C-05）

#### C-39：本番環境の構築（IaC）

- 本番環境（Workers・D1・R2・DNS・環境変数の設定など）は、管理画面での手作業ではなく、IaCのコードで構築する。同じコードから、同じ環境を何度でも再現できるようにする
- IaCのツールはTerraformを標準とする（Cloudflare用の公式プロバイダーがある）。Terraformとwranglerの役割の分け方（インフラの作成はTerraform、アプリのデプロイはwrangler等）は、技術スタック別に定める
- IaCのコードはアプリと同じリポジトリの`infra/`で管理し、変更はほかのコードと同じくIssue・PRで行う
- 管理画面で直接設定を変えない。緊急で変えた場合は、同じ変更をIaCのコードに反映し、コードと実際の環境の食い違いをなくす
- 環境（開発用・検証用・本番など）ごとに設定を分け、同じコードで作れるようにする

##### 秘密情報と状態ファイル

- APIトークンなどの秘密情報は、IaCのコードに書かず、環境変数や秘密情報の管理機能から渡す（C-05）
- Terraformの状態ファイル（`terraform.tfstate`）には秘密情報が含まれ得るため、リポジトリにコミットしない。アクセスを制限した保存先（リモートの状態管理）に置く

##### 適用の手順

1. PRで、IaCの変更内容と、適用したときの差分（`terraform plan`の結果）を確認する
2. ユーザーの承認を得てから、本番に適用する（`terraform apply`）。AIが承認なしに本番へ適用しない
3. 適用後、コードと実際の環境に食い違いがないことを確認する

#### C-40：環境の分け方

| 環境 | 使うとき | 使う人 |
| --- | --- | --- |
| 開発 | 実装中の動作確認 | 開発者 |
| 検証 | テスト（本番と同じ構成での確認、受け入れ確認） | 開発者・確認者 |
| 本番 | クライアント・利用者が実際に使う | クライアント・利用者 |

- 3つの環境は、同じIaCのコード（C-39）から作り、設定値だけを環境ごとに分ける
- 環境ごとにDB・秘密情報・ドメインを分け、ほかの環境のものを使わない。特に、開発・検証から本番のDBに接続しない
- 本番のデータを開発・検証に持ち込まない（C-05のテストデータのルール）

#### C-41：デプロイと切り戻し

##### デプロイ

- デプロイは自動化せず、承認を得てから行う。マージしただけで本番に反映される仕組みにしない
- 承認するのは、その時点の開発リーダーとする（個人開発の場合は、その個人）
- AIは承認なしにデプロイしない。承認を依頼するときは、デプロイする内容・DBの変更の有無・切り戻しの方法を示す
- 本番へのデプロイは、検証環境で確認済みの同じバージョンで行う

##### 切り戻し

- 不具合が出た場合は、前のバージョンを再デプロイすることを基本とする。そのため、デプロイしたバージョン（C-08）を記録し、前のバージョンをすぐに再デプロイできる状態を保つ
- 大規模な案件では、Blue-Greenデプロイメントやカナリアリリースを採用するかを検討し、結果をADR（C-35）に記録する

##### 本番DBの変更（後方互換性）

アプリを前のバージョンに切り戻しても動くように、本番DBの変更は後方互換性を確保してから破壊的変更を行う（C-37）。

1. **追加**：新しいカラム・テーブルを追加する。前のバージョンのアプリはこれを使わないので、そのまま動く
2. **移行**：新しいバージョンのアプリをデプロイし、データを新しい構造へ移す。この間は古い構造も残しておく
3. **削除（破壊的変更）**：切り戻す可能性がなくなったことを確認してから、別のデプロイで古いカラム・テーブルを削除する

- カラムの削除・名前の変更・型の変更など、前のバージョンが動かなくなる変更を、1回のデプロイで行わない

##### バックアップと復元

- DBのバックアップは、使うDB・サービスで可能な限り行う（D1ならTime Travel等の復元機能、PostgreSQLなら定期バックアップ）
- 本番DBにマイグレーションを適用する前に、その時点に戻せること（復元ポイントやバックアップ）を確認する
- 復元の手順を文書にし、検証環境で実際に復元できることを確認しておく
- 具体的なバックアップの方法・頻度・保存期間は、技術スタック・DB別に定める

### 2.3 バックエンド

| ID | 内容 |
| --- | --- |
| C-03 | バックエンドは**責務の分離を徹底**し、決められた層に分ける |
| C-04 | データアクセス層は**必要最低限の列だけをDTOで取得する**。Entityを丸ごと取得して画面やAPIに渡すことを禁止する |
| C-10 | バックエンドのDBアクセスと静的メディア配信は、不要なアクセス・転送を避けつつ、正確性・安全性・実測した費用を踏まえて設計する |
| C-30 | ログにパスワード・トークン・個人情報を出さず、形式をそろえる |

| C-64 | トランザクションの範囲はService層で決め、短く保ち、外部の処理と混ぜない。更新の衝突を検知する |
| C-65 | バッチ処理はべき等にし、小分けに処理して再開でき、実行の記録を残す |

#### C-03：バックエンドの層構成

層の分け方と責務は言語共通とし、ディレクトリ名や使うライブラリだけを言語ごとの差分とする。

| 層 | 責務 | してはいけないこと |
| --- | --- | --- |
| Controller | リクエストの受付・入力チェック・レスポンスの返却 | 業務ロジックを書く、データアクセス層を直接呼ぶ |
| Service | 業務ロジック・トランザクション管理 | HTTPに関する処理を書く |
| Repository | Serviceから見たデータの出し入れ。DBの実装方式をServiceから隠す | 業務ロジックを書く |
| DAO | SQLの実行に専念する（下記の条件に当てはまる場合のみ置く） | 業務ロジックを書く、Serviceから直接呼ばれる（Repositoryを置く構成の場合） |
| DTO | 層の間・API間でやり取りするデータの入れ物 | ロジックを持つ |
| Entity | DBのテーブルに対応するデータ | Controllerより外（画面・API）に出す |
| Mapper | Entity ⇔ DTO の変換 | 変換以外の処理を書く |

##### RepositoryとDAOの使い分け

一律に決めず、状況に応じて構成を選ぶ。

| 状況 | 構成 |
| --- | --- |
| 単純なCRUDのみ | Service → Repository（DAOは作らない） |
| 複雑なSQLだけを扱う | Service → DAO |
| ドメインモデルとDBモデルを分離したい（クライアントの要望等） | Service → Repository → DAO |
| 複数のDAOをまとめて1つのデータとして扱いたい | Service → Repository → 複数のDAO |
| DBの実装方式をServiceから隠したい | Service → Repository → DAO |

- 同じ機能の中で、単純なCRUDと複雑なSQLが混在する場合は、機能ごとに上表から選ぶ
- どの構成を選んだかと、その理由を設計（Issueや計画）に記録する

##### Hono（TypeScript）の場合のSQLの書き方

- データアクセスのライブラリは1つにそろえ、書き方を複数用意しない（ライブラリの最終決定は未決定事項を参照。現時点の候補はD1とPostgreSQLの両方に対応するDrizzle ORM）
- 単純なCRUDや、入力によって条件が変わる検索は、ライブラリの通常の書き方でRepositoryに書く
- 複雑なSQLは、DAOの専用ファイル（例：`dao/sales-report.sql.ts`）に1クエリずつ生SQLで書き、Serviceなど他のロジックと混ぜない
- 「複雑なSQL」に当たるかの判断基準は、知見`knowledge/db/sql-complexity.md`（F-18）に従う

#### C-10：DBアクセスと静的メディア配信の効率

- DBアクセスはN+1問題を避け、ユースケースで必要なデータを把握したうえで、JOIN、まとめて取得するクエリ、バッチ取得などから適切な方法を選ぶ。必要な列だけを取得するC-04を守る。
- DBへの往復を減らすことを意識する。ただし、通信回数を減らすためだけに巨大で複雑なSQLへ一本化してはならない。ページング、取得件数、JOINによる行数の増加、読みやすさと保守性を考慮して設計する。
- 一覧・検索などN+1が起こりやすい代表的な処理では、実行SQL数や取得件数を確認して検証する。
- N+1の検証では、同一条件で親データの件数を変えて代表APIまたは画面操作を実行し、SQL発行数とSQL内容を収集する。件数の増加に対してSQL発行数が線形に増加していないことを確認する。ページング用の件数取得やバッチ取得など、増加に合理的な理由がある場合は記録してレビューする。
- 検索・一覧・結合を行う代表的な処理では、実運用を想定したテストデータで実行計画（`EXPLAIN`またはDBごとの同等機能）を取得し、絞り込み、結合、並び順、取得件数に対して適切なインデックスが利用できるかを確認する。不要な全件走査、大量の行読み込み、不要なソート、重複したインデックスなどの兆候を検出した場合は、警告または品質チェックの失敗として扱う。
- N+1検証と実行計画・インデックス確認は、テスト用DBの初期状態から自動実行できるDBアクセス回帰テストとして生成し、選択した実行場所に応じてローカルまたはCIで実行する。SQL発行数の計測、実行計画の取得と解析、結果の判定は技術スタック・DB別の実装にする。
- 全件走査やインデックス未使用を一律に不具合と断定してはならない。テーブル規模、データ分布、選択性、更新コスト、ストレージ容量、実行時間などを根拠に、実行計画と実測値をレビューして最終判断する。

##### インデックス設計方針

- インデックスは、実際に想定する検索条件（`WHERE`）、結合条件（`JOIN`）、並び順（`ORDER BY`）、一意性制約およびアクセス頻度を根拠に設計する。根拠のない一律付与や、問題が起きてからの場当たり的な追加はしない。
- 複合インデックスは、対象クエリの絞り込み条件と並び順に合わせて列の順序を設計する。単一列インデックスを複数作れば同じ効果になるとはみなさない。
- 主キー・一意性制約・外部キー参照のためのインデックスは、DBの自動作成の有無と、結合・削除・更新時のアクセスパターンを確認して判断する。
- 似た役割の重複インデックス、使用されないインデックス、選択性が低く効果の乏しいインデックスは追加しない。インデックス追加時は、読み取り性能だけでなく、書き込み性能、ストレージ使用量、バックアップ・移行時間への影響も評価する。
- インデックスの追加・変更・削除は、スキーマ変更としてマイグレーションに含める。各変更には、対象クエリ、想定データ量、期待する改善、実行計画または計測結果を記録する。
- 検索・結合・並び順を変更する機能では、既存インデックスの妥当性を再確認する。利用規模やデータ分布が大きく変化した場合も、実測値に基づいて見直す。

- 画像・動画などの静的メディアは、更新頻度、再利用可能性、アクセス制御を考慮して、ブラウザーキャッシュやCDNキャッシュを利用する。キャッシュの利用は利用者への転送をなくすものではなく、オリジンストレージやアプリへの再取得を減らすための手段として扱う。
- 認証が必要なデータや個人向けのデータを、他者が取得できる共有キャッシュに保存してはならない。HTTPキャッシュ制御は、データの公開範囲と更新要件に応じて設定する。
- キャッシュの導入・保持・削除を一律のコスト削減策として扱わない。アクセス量、転送量、キャッシュヒット率、ストレージ・CDN・アプリの各費用と負荷を実測して判断する。
- 具体的な取得方法、インデックス、キャッシュ期間、配信構成、費用基準および計測方法は、技術スタック、DB、クラウド・ストレージサービス、利用規模を決定した後に、技術スタック別の設計として定める。SQL発行数の上限、テストデータ量、実行計画の警告・失敗基準も同時に決定する。

#### C-30：ログの方針

##### ログに残さない情報

- 次の情報はログに出さない。やむを得ず関連する情報を残す場合は伏せ字にする
  - パスワード・再設定用トークン／コード・MFAのコード
  - セッションID・アクセストークン・リフレッシュトークン・IDトークン・APIキー
  - `Cookie`・`Set-Cookie`・`Authorization`ヘッダーの値
  - 秘密情報（C-05）、個人情報（氏名・メールアドレス・住所・電話番号等）
  - 認証・個人情報を扱うAPIのリクエスト本文・レスポンス本文、トークンを含み得るURLのクエリ文字列
- 上記の除外は、各所の注意に任せず、共通のロガーで項目名に基づいて自動で伏せ字にする仕組みを設ける
- 例外（スタックトレース等）の内容にも上記が含まれ得るため、ログに出す前に同じ伏せ字処理を通す
- **必須のテスト（単体テスト）**：上記の情報を含むログを出力させ、出力結果に元の値が含まれていないことを確認する

##### ログレベル

| レベル | 使うとき |
| --- | --- |
| `ERROR` | 処理を完了できず、対応が必要なとき |
| `WARN` | 処理は続けたが想定外のことが起きたとき（試行制限の発動など） |
| `INFO` | 正常な重要イベント（ログイン成功など） |
| `DEBUG` | 開発時の調査用。本番では出さない |

##### 形式

- JSON形式で1行1件出す。項目名はOpenTelemetryの標準（`timestamp`・`severity_text`・`trace_id`等）に合わせる
- 日時はUTCのISO 8601（C-31）とし、リクエストIDで1つのリクエストに関係するログをたどれるようにする
- 利用者はログ上で利用者IDで表し、メールアドレスや氏名は書かない。IPアドレスは個人情報に当たり得るため、記録する場合は保存期間を決める
- 利用者の入力をログに書くときは、改行などの制御文字を無害化する（ログインジェクション対策）
- C-15の、利用者に見せないエラーの詳細は、この形式でログに記録する

##### 監査ログ

- 次のイベントは必ず記録する：ログインの成功・失敗、ログアウト、パスワードや認証要素の変更・回復、権限の変更、認可の拒否（403）、試行制限の発動、管理者による操作
- 「誰が・いつ・何を・どの対象に・結果」を記録し、`log_type: audit`を付けて通常のログと区別する

##### 出力先と保存

- アプリは標準出力にログを出すだけにし、出力先を知らない。どこへ送るかは実行環境の設定で決める
- アプリ内に共通のロガーを1つ用意し、各層から直接`console.log`等を呼ばない
- 短期の保存はインフラ標準の保存先を使い、長期の保存が必要な場合はオブジェクトストレージ（R2・S3等）にJSONのまま保存する。監査ログの保存期間が長い場合は、専用の保存先に送る
- 保存期間は一律に決めず、個人情報を扱うか（C-09）とプロジェクトの要件に応じて決め、要件またはADR（C-35）に記録する
- `ERROR`の多発や試行制限の発動の急増などを通知する仕組みを設けるかは、プロジェクトごとに決める
- 具体的な出力先・転送方法・ロガーのライブラリは、技術スタック別に定める

#### C-31：API設計の決まり

- URLは複数形の名詞で表す（例：`/users`、`/users/{id}`）。操作はHTTPメソッドで表し、URLに動詞を入れない
- 日時はISO 8601形式（UTC）でやり取りする（例：`2026-09-28T09:00:00Z`）
- 一覧を返すAPIは、ページングを必須とする
- API仕様はOpenAPIで書き、フロントエンドの型（C-06のTypes）と対応させる
- HTTPメソッドの使い分けはC-28に従う

#### C-37：DBスキーマのバージョン管理

##### マイグレーションのルール

- DBのスキーマ（テーブル・カラム・インデックス・制約）の変更は、すべてマイグレーションファイルで行う。DBを直接操作してスキーマを変えない
- マイグレーションツールは、Flywayと同じく「番号付きのファイルを順番に適用し、適用済みの記録をDBの中に残す」方式のものを使う。具体的なツールは技術スタック・DB別に定める（候補：D1はwranglerのマイグレーション機能、PostgreSQLはFlyway等）
- マイグレーションファイルは、番号（またはタイムスタンプ）と内容が分かる名前にする（例：`0003_add_users_email_index.sql`）
- **一度適用したマイグレーションファイルは書き換えない**。修正が必要な場合は、修正用の新しいマイグレーションファイルを追加する
- ORMのスキーマ定義（Drizzle等）を使う場合は、スキーマ定義とマイグレーションファイルの内容が食い違わないようにする。食い違いの有無を品質チェックで確認する
- インデックスの変更もマイグレーションに含める（C-10）

##### テスト・CIの前にスキーマを最新にする

テスト・CIは、次の順番で実行する。ローカルでのテストとCIで同じ手順にする。

1. 空のテスト用DBを用意する（D1はローカルに再現したもの、PostgreSQLはコンテナ）
2. すべてのマイグレーションを最初から順番に適用し、スキーマを最新にする
3. テストデータ（シード）を投入する（C-05のテストデータのルールに従う）
4. テスト・品質チェックを実行する

- 手順2で失敗した場合は、テストに進まず失敗として扱う。これにより「空のDBから最新のスキーマまで、マイグレーションだけで再現できること」も毎回確認できる
- テスト用DBは毎回作り直し、前回の実行の状態を持ち越さない（C-25の再現性）
- 本番DBへのマイグレーションの適用は、テスト・CIとは別のデプロイの手順として、ユーザーの承認を得て行う（C-36）

##### テスト用DBの状態を毎回同じにする

テストの再現性（C-25）を担保するため、テストは毎回同じDBの状態から始める。

- **シードデータは必要最低限にする**：テストを行うために共通で必要なデータ（例：テスト用の利用者、ロール、マスタデータ）だけを入れる。特定のテストだけで使うデータはシードに入れず、そのテストの中で作成する
- **シードデータは毎回同じ内容にする**：ID・日時などを固定値で書き、乱数や実行時の現在時刻で値を作らない。同じシードを何回投入しても、同じ状態になるようにする
- **テストの間で状態を持ち越さない**：各テストはシード投入直後と同じ状態から始める。テストの中で追加・変更したデータは、テストの終了時に元に戻す（トランザクションの取り消し、テストごとのDBの作り直し等。方法は技術スタック別に定める）
- **テストの実行順序に依存させない**：どの順番で実行しても、1つだけ実行しても、同じ結果になるようにする
- **シードデータもバージョン管理する**：シードのファイルはマイグレーションファイルと一緒にリポジトリで管理し、スキーマを変更したときはシードも合わせて更新する
- シードデータの値は、C-05のテストデータのルール（架空のデータ、識別用の接頭辞・タグ）に従う

##### E2Eのテストデータ

E2Eは動いているアプリを外から操作するため、結合テストのようにトランザクションを取り消して元に戻すことができない。そのため、**DBは毎回空にし、シナリオで使うデータの内容はファイルとして残す**。毎回同じファイルから同じデータを入れることで、いつも同じ状態からテストできるようにする。

- **MUST**：E2Eの実行を始めるときに、テスト用DBを空にして作り直し、マイグレーション（C-37）と共通の最低限のシードを入れる
- **MUST**：シナリオごとに使うデータは、シナリオ用のシードデータとしてファイルに書き、リポジトリで管理する（例：`e2e/seeds/<シナリオ名>`）。どの内容でテストしたかの記録として残し、変更はPRで行う
- **MUST**：シナリオ用のシードデータは、そのシナリオの準備の中で、ファイルから入れる。画面の操作ではなく、APIや準備用の処理で直接入れる（準備を速くし、テストしたい操作以外の失敗に巻き込まれないため）
- **MUST**：シナリオ用のシードデータの値は固定にする。ID・日時も固定値で書き、乱数や実行時の現在時刻で作らない（C-37のシードと同じ考え方）
- **MUST**：シナリオ用のシードデータには、シナリオごとに固定の、ほかのシナリオと重ならない名前を付ける（例：`e2euser_login_001`）。値はC-05のテストデータのルールに従う
- **MUST NOT**：共通のシードのデータを、シナリオの中で書き換えない。書き換えが必要なシナリオは、自分用のシナリオ用シードデータを使う
- 再テストするときは、同じファイルから入れ直すだけで、同じ条件で実行できる
- 実行後のDBの中身は、原因の調査のために次の実行まで残してよい（C-69）。次の実行を始めるときに空にする
- 識別用の名前（C-05の接頭辞）を条件にまとめて削除するスクリプトも用意し、DBを空にできない共有の検証環境（C-40）では、これで削除して残りが0件であることを確認する
- 本番のDBにE2Eのデータを作らない（C-05）

#### C-64：トランザクション

- **MUST**：トランザクションの範囲はService層で決める。Repository／DAOは、自分でトランザクションを始めない（C-03）
- **MUST**：トランザクションは短くする。中で外部APIの呼び出し・メール送信・ファイルのアップロードを行わない。外部の処理を待つ間DBを長く止めてしまい、外部の処理はDBの取り消しと一緒に取り消せないため
- **MUST**：DBと外部の処理（R2・メール等）をまたぐ場合は、順番と失敗時の後始末を決める。例：「DBに『処理中』で記録 → 外部の処理 → DBを『完了』に更新」とし、失敗したものは再実行または後始末の対象にする
- **MUST**：複数の人が同じデータを更新し得る場合は、更新の衝突を検知する（バージョン番号を使う楽観的ロック等）。衝突したら`409`を返し、利用者に再読み込みを案内する（C-15）
- **SHOULD**：二重に実行されると困る処理（登録・決済等）は、同じ要求を2回受けても結果が変わらないようにする（べき等性。重複を防ぐキーを使う等。C-47）
- **MUST**：途中で失敗したときに全体が取り消されること、更新が衝突したときに検知されることをテストする
- **MUST**：主の処理に付随する後始末（ログアウト時のキャッシュ削除等）は、失敗しても主の処理の結果を変えない。後始末は個別にエラーを受け止めてログに記録し、主の処理の失敗として扱わない
- DBによって異なる書き方（D1は`batch()`でまとめて実行、PostgreSQLは`BEGIN`〜`COMMIT`等）は、技術スタック別に定める

#### C-65：バッチ処理

- **MUST**：同じバッチを何度実行しても、結果が同じになるようにする（べき等性）。失敗したときに、安心して再実行できるようにするため
- **MUST**：大量のデータは小分け（チャンク）にして処理し、小分けごとに確定する。途中で止まっても、終わったところから再開できるようにする
- **MUST**：同じバッチが同時に2つ動かないようにする
- **MUST**：実行の記録を残す。開始・終了の日時、処理件数・成功件数・失敗件数、結果を、ログ（C-30）とDBの実行履歴に記録する
- **MUST**：失敗した処理は、回数の上限と間隔を決めて再試行する。上限を超えたものは失敗の一覧に残し、通知する
- **SHOULD**：1件の不正なデータで、バッチ全体を止めない。そのデータを飛ばして失敗の一覧に記録し、残りを続ける。データの整合性のために全体を止める必要がある場合は、その理由を設計に書く
- **MUST**：定期実行の時刻は、設定上はUTCで書き、日本時間での時刻を文書に併記する
- **MUST**：本番で手動で再実行できる手段を用意する。本番での手動実行は、ユーザーの承認を得て行う（C-41）
- **MUST**：再実行しても結果が同じこと、途中で失敗した場合に再開できること、実運用を想定したデータ量で時間内に終わることをテストする
- 定期実行・小分けの処理・再開の仕組みは、技術スタック別に定める

#### C-74：外部APIのバージョン管理

外部APIの提供元が仕様を変えたことで、アプリが突然使えなくなることを防ぐ。

- **MUST**：外部APIは、使うAPIのバージョンを明示して呼び出す（URLのバージョン（`/v2`等）、バージョンを指定するヘッダー、提供元のSDKのバージョン等）。バージョンを指定しない呼び出し（常に最新になるもの）をしない
- **MUST**：使っている外部API・APIのバージョン・SDKのバージョン・提供元の仕様書へのリンクを、`docs/tech-stack.md`に記録する（C-62・C-70）
- **MUST**：外部APIの呼び出しは、専用の層（例：`gateways/`）に集める。アプリの内部では外部APIの応答をそのまま使わず、アプリ用の型に変換してから使う。外部APIが変わったときの修正を、この層に閉じ込めるため（C-03）
- **MUST**：外部APIの応答は、型だけで信用せず、Zod等で検証する（C-46）。想定していない形の応答は、エラーとして扱い、もみ消さない（C-71）
- **MUST**：提供元の変更履歴・廃止予定のお知らせを確認する担当とタイミング（例：月1回の知見の見直しと同時）を決める。廃止予定が分かったら、期限より前に移行のIssueを作る
- **MUST**：外部APIのバージョンを上げる場合は、専用のIssue・PRで行い、モック（C-70）を新しい仕様に合わせて更新してから、テストが通ることを確認する（C-62）

### 2.4 フロントエンド

React（TypeScript）を前提とする。ルールの強さは次の3段階で表す。

| 表記 | 意味 |
| --- | --- |
| **MUST** | 必ず守る |
| **MUST NOT** | 必ず避ける |
| **SHOULD** | 原則として守る。守らない場合は理由をPR等に書く |

| ID | 内容 |
| --- | --- |
| C-06 | フロントエンドは決められたディレクトリ構成に従い、**責務を分離**する |
| C-43 | コンポーネントは主な責務を1つにし、Propsには型を付けて必要なデータだけを渡す |
| C-44 | TypeScriptは`strict`で使い、`any`や型エラー回避のためのキャストを使わない |
| C-45 | 状態はUI状態とServer Stateに分けて管理し、`useEffect`は外部システムとの同期に限る |
| C-46 | API通信は専用の層に集約し、エラーを明示的に処理し、レスポンスを検証する |
| C-47 | フォームは画面側とサーバー側の両方で入力チェックし、多重送信を防ぐ |
| C-48 | 非同期の画面ではloading・success・empty・errorを明示的に扱い、利用者向けの表示とログを分ける |
| C-49 | 外部入力を信頼せず、秘密情報をフロントエンドに含めず、認可をフロントエンドだけで保証しない |
| C-50 | 性能の最適化は根拠に基づいて行い、`key`には安定した一意のIDを使う |
| C-51 | 要素の意味に合ったHTMLを使い、キーボードで操作できるようにする |
| C-52 | 機能変更・不具合修正にはテストを伴わせ、利用者の操作に基づいて検証する |
| C-54 | フロントエンドの完了の定義を満たしてから完了とする |
| C-55 | アプリアイコン・ファビコンは必ず用意し、画像がない場合は仮の画像を入れて後で差し替える |

#### C-06：ディレクトリ構成と責務

```text
src/
├─ pages/          ルーティング単位の画面（レイアウトと機能の組み合わせのみ）
├─ features/       機能単位の実装
├─ components/     全体で使う共通UI
├─ hooks/          共通Custom Hook
├─ services/       共通のAPI通信
├─ schemas/        共通のZodスキーマ
├─ types/          共通の型
├─ utils/          純粋関数
├─ constants/      共通の定数
└─ test/           テストの共通処理
```

| ディレクトリ | 置くもの | 置かないもの |
| --- | --- | --- |
| `pages/` | URLごとの画面。レイアウトと、機能の組み合わせだけを行う | API通信、状態管理、業務ロジック |
| `components/` | 複数の機能で使う見た目の部品 | API通信、汎用ロジック、特定の機能に依存する処理 |
| `features/` | 機能ごとの実装（その機能専用の部品・Hook・API層・スキーマ・定数） | 他の機能から直接参照される共通処理 |
| `hooks/` | 複数の機能で使うCustom Hook | 1つの機能でしか使わないHook（`features/`に置く） |
| `services/` | 複数の機能で使うAPI通信 | 画面の状態、表示の処理 |
| `schemas/` | Zodスキーマ（入力チェック・APIレスポンスの検証） | ロジック |
| `types/` | 複数の機能で使う型 | ロジック |
| `utils/` | 画面や状態に依存しない純粋関数（日付の整形など） | 状態、API通信 |
| `constants/` | 定数 | 環境によって変わる値（設定として扱う） |
| `test/` | テストの共通処理（テスト用の描画関数、モック等） | 本番コード |

- **MUST**：API通信の処理は、`services/`または各機能の`features/<機能>/api`層に置く
- **MUST NOT**：画面のコンポーネントの中に、`fetch`・`axios`を直接書かない（API通信はAxiosのインスタンスを使う。下記「Axiosとインターセプター」）
- **MUST NOT**：汎用ロジックを`components/`に置かない
- **MUST NOT**：`pages/`にAPI通信・状態管理・業務ロジックを書かない
- **MUST NOT**：`features/`から`pages/`を参照しない
- **SHOULD**：ほかの機能の内部を直接参照せず、各機能の公開部分（`index.ts`）を通す
- 依存の向きは「`pages/` → `features/` → 共通のもの（`components/`・`hooks/`・`services/`等）」の一方向とする
- 1つの機能でしか使わないスキーマ・定数・Hookは、共通のディレクトリではなく`features/<機能>/`に置く
- データの流れは「画面 → Hook → API層 → バックエンド」の一方向とし、見た目の部品は表示に専念させる。Webアプリ・モバイルアプリの両方で同じ考え方を使う

#### C-43：コンポーネントの責務とProps

責務

- **MUST**：1つのコンポーネントの主な責務を1つにする
- **SHOULD**：表示と複雑な状態管理が混ざる場合は、状態管理をCustom Hookに分ける
- **SHOULD**：独立した複数の表示領域を持つ場合は、子コンポーネントに分ける
- **MUST NOT**：API通信・データ変換・入力チェック・画面の描画を、1つのファイルに集中させない
- 分割するかどうかは、行数よりも責務で判断する

Props

- **MUST**：Propsの型を定義する
- **SHOULD**：子コンポーネントには、必要なデータだけを渡す
- **MUST NOT**：大きなオブジェクトを、理由なく丸ごと子コンポーネントへ渡さない
- **SHOULD**：Propsのバケツリレー（Props drilling）が深くなる場合は、設計を見直す

#### C-44：TypeScriptの型

- **MUST**：`tsconfig`の`strict`を有効にする
- **MUST**：公開する関数・APIレスポンス・Propsには、明示的な型を付ける
- **MUST NOT**：`any`を原則使わない
- **MUST NOT**：型エラーを回避することだけを目的に、`as`によるキャストを使わない
- **SHOULD**：型が分からない値は`unknown`で受け、型ガードまたはZodで絞り込む

#### C-45：状態管理・Hooks・useEffect

状態管理

- **MUST**：コンポーネント固有のUIの状態には、`useState`を使う
- **MUST**：サーバーから取得したデータは、Server Stateとして扱う
- **SHOULD**：Server Stateの管理には、TanStack Queryを使う
- **SHOULD**：複数の画面で共有するUIの状態に限り、Zustand等を検討する
- **MUST NOT**：Server Stateをグローバルなストアへコピーして、二重に管理しない

Custom Hook

- **MUST**：Hookの名前は`use`から始める
- **MUST**：Hookの中でも、React Hooksのルールを守る
- **SHOULD**：複数の状態・副作用・イベント処理をまとめる場合に、Custom Hookを検討する
- **MUST NOT**：単純な1〜2行の処理を、理由なくHookにしない
- 再利用性がなく単純な処理は、抽象化しない（C-38）

useEffect

- **MUST NOT**：値を計算するだけの目的で`useEffect`を使わない
- **MUST NOT**：PropsやStateから導き出せる値を、別のStateとして持たない
- **SHOULD**：`useEffect`は、外部システムとの同期に限って使う
- **MUST**：`useEffect`を使う場合は、依存配列の意味を確認する

#### C-46：API通信

- **MUST**：API通信は専用の層（C-06）に集約する
- **MUST NOT**：コンポーネントから直接`fetch`・`axios`を呼び出さない
- **MUST**：HTTPのエラーを明示的に処理する（401・403の扱いはC-15に従う）
- **MUST**：APIのレスポンスを、TypeScriptの型だけで信用しない
- **SHOULD**：外部APIのレスポンスは、Zod等で検証する

##### Axiosとインターセプター

API通信にはAxiosを使い、全体に共通する処理はインターセプター（すべての要求・応答の前後に共通の処理を挟む仕組み）にまとめる。各所に同じ処理を書かないことで、読みやすさと保守性を上げる。

- **MUST**：Axiosのインスタンスは、API層（`services/`）で1つ作り、アプリ全体でそれを使う。コンポーネントやHookから`axios`を直接importしない
- **MUST**：共通の設定（接続先のURL・時間切れの時間・Cookieを送る設定等）は、インスタンスにまとめて書く。接続先のURLは環境変数から読む（C-40）
- 要求のインターセプターで行うこと
  - リクエストIDの付与（C-30）
  - 認証・CSRF対策に必要なヘッダーの付与（C-17・C-28。認証トークンの扱いは、プロジェクトの認証設計に従う）
- 応答のインターセプターで行うこと
  - エラーを、アプリ内で扱う共通のエラーの形（HTTPステータス・アプリケーションエラーコード・利用者向けメッセージ）に変換する（C-15・C-73）
  - `401`を受けた場合の、認証の更新と、ログイン画面への遷移（C-15の手順。更新・遷移を重複させない）
  - エラーのログへの記録（C-30。秘密情報を出さない）
- **MUST NOT**：インターセプターの中でエラーをもみ消さない。変換した後も、必ず失敗として呼び出し元へ返す（C-71）
- **MUST NOT**：インターセプターに、特定の画面や機能だけの処理（業務ロジック）を書かない。全体に共通する処理だけにする
- 取得したデータの保持・再取得・キャッシュは、TanStack Query（C-45）が担当し、インターセプターは通信に共通する処理だけを担当する
- Axiosの追加は、ライブラリの追加の承認（C-32）として記録し、バージョンを固定する（C-62）

#### C-47：フォームと入力チェック

- **MUST**：画面側（クライアント側）の入力チェックを実装する
- **MUST**：サーバー側でも入力チェックすることを前提にする（C-27）。画面側のチェックは利用者の補助であり、代わりにならない
- **SHOULD**：React Hook Form＋Zodを標準にする。Zodスキーマは`schemas/`に置く
- **MUST**：送信中は、多重送信を防ぐ
- **MUST**：API側でも、二重送信の対策とデータの整合性の保証を行うことを前提にする

#### C-48：画面の状態とエラー表示

画面の状態

- **MUST**：非同期でデータを扱う画面では、次の4つの状態を明示的に扱う
  - loading（読み込み中）
  - success（成功）
  - empty（データなし）
  - error（エラー）

エラー表示

- **MUST**：予期できるエラー（入力の誤り、権限不足など）と、予期しないエラーを区別する
- **MUST**：利用者向けのエラー文と、ログへの出力を分ける（C-15・C-30）
- **MUST NOT**：内部の例外・スタックトレース・機密情報を、画面に表示しない
- **SHOULD**：React Error Boundaryを適切な単位で配置する

#### C-49：フロントエンドのセキュリティ

- **MUST NOT**：`dangerouslySetInnerHTML`を原則使わない（C-27）
- **MUST NOT**：秘密鍵・API Secret・パスワードをフロントエンドのコードに含めない
- **MUST NOT**：認可の判断を、フロントエンドだけで保証しない。フロントエンドでの権限制御は表示の制御であり、最終的な認可はバックエンドで行う（C-13）
- **MUST**：外部からの入力を信頼しない。URL・フォームの値・APIのレスポンスを、外部からの入力として扱う
- **SHOULD**：認証トークンの保存方法は、プロジェクトの認証設計（C-17）に従う

#### C-50：パフォーマンス

- **MUST NOT**：根拠なく`useMemo`・`useCallback`・`memo`を使わない
- **SHOULD**：実測の結果、または再レンダリング上の明確な理由がある場合に使う
- **SHOULD**：大量のリストでは、ページング・仮想化（virtualization）等を検討する
- **MUST**：Reactの`key`には、安定した一意のIDを使う
- **MUST NOT**：配列の添字（index）を、安易に`key`として使わない

#### C-51：アクセシビリティ

- **MUST**：ボタンの役割を持つ要素には、`button`要素を使う
- **MUST**：フォームの入力欄には、`label`を設定する
- **MUST**：画像には、適切な`alt`を設定する
- **MUST**：キーボードだけで操作できるようにする
- **SHOULD**：`aria`属性は、必要な場合に限って使う

#### C-52：フロントエンドのテスト

C-24〜C-26に加えて、次を守る。

- **MUST**：機能を変更するときは、対応するテストを追加または更新する
- **MUST**：不具合を修正するときは、再発を防ぐテストを追加する
- **SHOULD**：純粋なビジネスロジックには、単体テストを書く
- **SHOULD**：Reactコンポーネントは、Testing Libraryを使って利用者の操作に基づいて検証する
- **MUST NOT**：内部の実装だけを検証するテストに頼らない
- **SHOULD**：主要な利用の流れは、E2Eテストで担保する（C-24）

#### C-54：フロントエンドの完了の定義

C-34に加えて、次のすべてを満たした場合だけ、フロントエンドの実装を完了とする。

- 要求された機能が動作する
- TypeScriptのエラーがない
- ESLintのエラーがない
- フォーマッターを適用している
- 対象のテストが成功している
- 既存のテストを壊していない
- loading・error・emptyの状態を考慮している
- アクセシビリティを確認している（C-51）
- 不要な`console.log`が残っていない
- 不要な依存関係を追加していない
- セキュリティのルール（C-49）に違反していない

#### C-55：アプリアイコン・ファビコン

- **MUST**：アプリアイコンとファビコンを必ず用意する。CLIはプロジェクトを生成するときに、次の仮の画像を必ず出力する
  - ファビコン（`favicon.ico`・`favicon.svg`）
  - スマートフォンのホーム画面用アイコン（`apple-touch-icon.png`）
  - Web App Manifest用のアイコン（192×192・512×512）と、それを参照する`manifest`ファイル
- 仮の画像は、アプリ名の頭文字などを入れた単純なものとし、仮であることが分かるようにする
- **MUST**：仮の画像を使っていることを、生成するプロジェクトのREADMEと、差し替え用のIssueに記録する。本番へ公開する前に正式な画像へ差し替える
- 差し替えるときは、同じファイル名・サイズで置き換えるだけで済むようにする

### 2.5 品質チェック・テスト

| ID | 内容 |
| --- | --- |
| C-24 | 単体テスト・結合テスト・E2Eテストは、該当する場合はすべて必須とする |
| C-25 | テストは要求に基づいて設計し、テストを通すこと自体を目的にしない。検出力と再現性を確認する |
| C-26 | テストと要求（Issueの受け入れ条件）の対応を、テスト名とPR本文で追跡できるようにする |
| C-32 | lockファイルをコミットし、ライブラリの追加は承認を得て、脆弱性を品質チェックで確認する |
| C-62 | バージョン管理されているもの（ライブラリ・実行環境・Dockerイメージ・Terraform・GitHub Actions等）は、すべてバージョンを明確にして固定する |
| C-60 | 性能の目標は、画面はCore Web Vitalsの「良好」、APIとJavaScriptの量は目安の初期値とする |
| C-69 | テストの種類ごとに、事前に必要な環境の構築手順を、順序立てて文書にする |
| C-70 | 外部APIを使う処理のテストは、本物の外部APIを呼ばず、モック等で行う |
| C-61 | CIは開発環境と同じコンテナ・バージョンを使い、手元と同じ1つのコマンドで品質チェックとテストを実行する |

#### C-24：テストの必須範囲

次の3種類のテストを、**該当する場合はすべて必須**とする。

| テスト | 必須になる条件 | 対象 |
| --- | --- | --- |
| 単体テスト | 常に必須 | Service・Mapper・Hooks・Utilsなどのロジック |
| 結合テスト | バックエンドがある場合 | ControllerからDBまで通したAPIの動作（認可・エラー応答を含む） |
| E2Eテスト | フロントエンド（Web画面またはモバイルアプリ）がある場合 | 画面からバックエンドまで通した主要な利用の流れ（ログイン等） |

- 「該当しない」と判断して省略する場合は、その理由をIssueまたはPRに記録する
- テストの設計はC-25、ツールと実行方法はF-16、テスト環境の構築手順はC-69に従う

##### E2Eが今回の実装を検証しているかの確認

テストが「通った」ことと、そのテストが「今回の実装を検証している」ことは別である。E2Eがすべて成功しても、実行されたのが既存のシナリオだけなら、今回の機能は検証されていない。

- **MUST**：今回の変更を検証するE2Eが実在するかを、シナリオ名ではなく中身（新しい画面の要素、新しいAPIのパス等）で確認する
- **MUST**：無ければ追加する。追加できない場合は、理由と、代わりに何が担保しているかを報告する。黙って省略しない
- **SHOULD**：バックエンドを先に作って画面がまだ無い場合は、動いているAPIをPlaywright等から直接呼ぶ「API層のE2E」で代替する。境界値・競合等の網羅はバックエンドのテストに任せ、API層のE2Eは要点に絞る
- **MUST**：後続のIssueに検証を引き継ぐ場合は、そのIssueの本文に追記する

##### Web E2Eでのコンソールの監視

- **MUST**：Web E2Eでは、エラーレベルのコンソール出力と、処理されなかった例外があればテストを失敗にする
- **MUST**：テストが意図して起こす異常（誤ったパスワードでの401等）は、そのテストの中だけで、対象を絞って許可し、理由を書く
- **MUST**：既知の不具合をやむを得ず許可する場合は、追跡するIssueの番号と、許可を外す条件を書く
- **SHOULD**：画像は「表示されたか」ではなく、実際に読み込めたか（画像の幅が0より大きいか等）で確かめる

##### E2Eテストの実行と不具合調査

E2Eテストのツールは、画面の種類によって使い分ける。

| 画面の種類 | ツール | 理由 |
| --- | --- | --- |
| Web画面 | **Playwright** | 主要ブラウザを操作でき、トレース等の調査機能がそろっている |
| モバイルアプリ | **Appium** | iOS・Androidの両方に対応して汎用性が高く、複雑な操作のテストも行える |

Webとモバイルの両方がある場合は、それぞれのツールでテストする。

###### Web画面の不具合調査

E2Eテストは**Playwright**で実行し、失敗した場合や動作の不具合が見つかった場合は、次の順番で原因を突き止める。

1. **Playwrightの記録を確認する**：失敗したテストのトレース・スクリーンショット・コンソールの出力を確認する
2. **Chrome DevToolsで再現して原因を追及する**：同じ操作を再現し、コンソールのエラー、通信（リクエストとレスポンスの中身）、必要に応じて性能やメモリの状態を確認する。コンソールと通信の中身を直接取り出せるため、原因の追及には主にChrome DevToolsを使う
3. **Orcaブラウザでユーザーと画面を確認する**：画面の見た目や操作の流れを、ユーザーと同じ画面で確かめる必要がある場合に使う

- 原因がフロントエンド・バックエンド・テストコード・テストデータ・テスト環境（C-69）のどこにあるかを切り分ける
- 原因を特定してから修正する。原因が分からないままテストの待ち時間を延ばす・再試行させる・期待結果を変える等でテストを通してはならない（C-25）
- 突き止めた原因と修正内容をIssueまたはPRに記録する
- Chrome DevToolsやOrcaを使えない環境では、Playwrightのトレース・スクリーンショット・画面表示ありの実行（headed）で代わりに調査する

| 道具 | 向いていること | できないこと |
| --- | --- | --- |
| Chrome DevTools | コンソールのエラー・通信の中身・性能・メモリの確認（原因の追及） | ユーザーと同じOrcaの画面での確認 |
| Orcaブラウザ | ユーザーと同じ画面での操作と見た目の確認、スクリーンショット | コンソールのログ・通信の中身を一覧で取り出すこと（2026年9月時点の`orca` CLIで確認） |

###### モバイルアプリの不具合調査

- エミュレーター・シミュレーター（または実機）で同じ操作を再現し、Appiumのログ・画面の要素の状態・アプリのログ・通信を確認して原因を切り分ける
- 原因を特定してから修正すること、原因と修正内容を記録することは、Web画面と同じとする
- 具体的な調査ツール（Appium Inspector等）と実行環境は、モバイルの技術スタックを決めるときに定める

#### C-25：テストの設計と信頼性

- テスト設計では、外部仕様や入出力に基づくブラックボックステストと、実装構造や制御の流れに基づくホワイトボックステストの両方を参照し、テスト対象と目的に応じて使い分ける。テストレベルとテスト設計技法を一対一には固定しない。
- 各テストでは、テスト対象・観点・入力または前提条件・期待結果を明確にする。期待結果はテストオラクル（仕様、受け入れ条件、独立して算出した結果、信頼できる参照データ等）に基づいて定め、本番実装と同じ処理から導出しない。期待する振る舞いを決められないほど要求が曖昧な場合は、テストを作り込む前に要求を明確にする。
- テスト実行前に、実装対象のIssueや受け入れ条件などの要求とテストケースを照合し、要求された振る舞いをテストが検証していること、テストのない要求がないことを確認する。各テストには要求・設計・不具合の再発防止などの目的を持たせる。対応に漏れや曖昧さがあれば、解消してからテストを実行する。
- 要求とテストの対応は追跡可能な形で記録する。自動化ツールは対応関係の記録や未対応項目の検出に使えるが、テスト内容が意図した振る舞いを正しく検証しているかは、要求・テスト内容をレビューして判断する。
- テストを通すこと自体を目的に、本番コードを要求と異なる振る舞いに変更したり、テストを無効化・スキップしたり、アサーションや期待結果を根拠なく弱めたり変更したりしてはならない。テストが失敗した場合は、要求に照らして実装とテストのどちらに問題があるかを確認し、根拠に基づいて修正する。
- テスト用のfixture・mock・依存注入などは利用できるが、検証対象の機能を通らないテスト専用分岐を本番コードに追加するなど、テスト結果だけをよく見せる変更をしてはならない。テストが成功していることとは別に、実装が要求された機能を満たすことをレビューする。
- テスト自体の検出力を確かめるため、ミューテーションテストを行う。全コードへの一律適用は必須とせず、認証・認可、個人情報の取扱い、重要な業務ルールなど影響の大きい処理を既定の対象とする。検出されなかった変更（生存ミュータント）を確認し、必要なテストを追加する。ツールと数値の合格閾値は技術スタック別に定める。
- テストの再現性確認では、同じコミットと依存関係、初期状態から実行したときに結果が安定することを確認する。テストデータと外部依存を分離し、テスト間の実行順序や前回実行の状態に依存させず、時刻・乱数などの環境要因は必要に応じて固定または記録する。
- 既定では通常の品質チェックでテストを1回実行し、自動再試行は行わない。再現性を確認する専用実行では、クリーンな状態から3回実行する。再実行で成功しても初回の失敗を成功扱いにせず、不安定なテストとして原因を調査する。実行コスト等に応じた変更は技術スタック別に設定できる。

#### C-26：要求とテストの対応確認

- Issueの受け入れ条件には番号（`AC-1`、`AC-2`…）を振る
- テスト名またはテストの説明に、Issue番号と受け入れ条件の番号を書く（例：`#12 AC-2: 誤ったパスワードでは401を返す`）
- PR本文に、受け入れ条件ごとに対応するテストの一覧を載せる。対応するテストがない受け入れ条件があれば、理由を書く
- テストの内容が受け入れ条件を正しく検証しているかは、C-25に従ってレビューで確認する

#### C-32：依存ライブラリの管理

- lockファイル（`package-lock.json`等）を必ずコミットする
- 新しいライブラリを追加するときは、AIが独断で追加せず、理由を示してユーザーの承認を得る
- 依存ライブラリの脆弱性チェック（`npm audit`等）を品質チェック（F-16）に含める
- バージョンの固定はC-62に従う

#### C-62：バージョンの明確化と固定

##### 目的

- **動作環境を明確にする**：どのバージョンで動いているかが分かるため、動かない原因が環境にある場合に、すぐに突き止められる
- **勝手なバージョンアップによる動作不良を防ぐ**：意図しないタイミングでバージョンが上がり、動かなくなることを防ぐ

##### 固定する対象と方法

| 対象 | 固定の方法 |
| --- | --- |
| npmのライブラリ | `package.json`に正確なバージョンを書き（`^`・`~`を付けない）、lockファイルをコミットする（C-32） |
| Node.js等の実行環境 | `.node-version`等のファイルに書き、手元・Docker・CIで同じものを使う（C-61） |
| Dockerのイメージ | `latest`を使わず、バージョンのタグを書く |
| Terraformとプロバイダー | バージョンを指定し、lockファイル（`.terraform.lock.hcl`）をコミットする |
| GitHub Actionsのアクション | バージョンを指定する。改ざん対策として、コミットのハッシュ値で固定することも検討する |
| wrangler等のCLIツール | 開発用のライブラリとして`package.json`で固定する |

- **MUST NOT**：`latest`・`*`・範囲指定など、実行するたびにバージョンが変わり得る書き方をしない
- **MUST**：使っている主な技術とそのバージョンの一覧を、プロジェクトの文書（例：`docs/tech-stack.md`）に記録する

##### バージョンを更新するとき

- **MUST**：バージョンの更新は、ほかの変更と混ぜず、専用のIssue・PRで行う
- **MUST**：更新の理由（脆弱性の修正、必要な機能、サポート期限等）と、変更点の確認結果をPRに書く
- **MUST**：更新後に、テストと品質チェックが通ることを確認する
- **MUST**：`docs/tech-stack.md`の一覧を更新する

#### C-60：性能の目標

一般的な基準を初期値とし、プロジェクトごとに変更できる。変更した場合は、理由をADR（C-35）に記録する。

##### 画面（Core Web Vitals）

Googleが公開しているCore Web Vitalsの「良好」の基準を目標とする。判定は、ページの読み込みの75パーセンタイルで、モバイルとデスクトップを分けて行い、3つすべてを満たしたときに合格とする。

| 指標 | 測るもの | 目標（良好） | 改善が必要 | 不良 |
| --- | --- | --- | --- | --- |
| LCP | 読み込みの速さ（一番大きい要素が表示されるまで） | 2.5秒以下 | 2.5〜4秒 | 4秒超 |
| INP | 操作への反応の速さ | 200ミリ秒以下 | 200〜500ミリ秒 | 500ミリ秒超 |
| CLS | 表示の安定性（読み込み中のレイアウトのずれ） | 0.1以下 | 0.1〜0.25 | 0.25超 |

出典：web.dev「Web Vitals」（https://web.dev/articles/vitals 、2024年10月31日更新版を2026年9月に確認）。基準が改定された場合は見直す。

##### API・JavaScriptの量（目安）

次の2つは公的な基準ではなく、目安の初期値である。知見（F-18）として「仮説」の状態で扱い、実測の結果をもとに見直す。

| 対象 | 初期値 | 知見 |
| --- | --- | --- |
| APIの応答時間 | 遅い方の5%（p95）で500ミリ秒以下。検索・集計などの重い処理は個別に目標を決める | `knowledge/backend/api-response-time.md` |
| 最初に読み込むJavaScriptの量 | 圧縮後200KB以下。超える場合は分割読み込みを検討する | `knowledge/frontend/initial-bundle-size.md` |

- 測り方は、F-18の「実測を根拠として使うときのルール」に従う
- 目標を満たしているかを、検証環境（C-40）で定期的に測る

#### C-69：テスト環境の構築手順

テストが失敗する原因の多くは、実装ではなく環境（ツールの入れ忘れ、バージョンの違い、ポートの競合等）にある。そのため、テストの種類ごとに、事前に必要な環境の構築手順を文書にする。

##### 対象

| テストの種類 | 事前に必要な環境の例 |
| --- | --- |
| 品質チェック | Node.js、依存ライブラリ、Lint・整形ツール |
| 単体テスト | Node.js、依存ライブラリ、テストの実行ツール |
| 結合テスト | 上記に加えて、テスト用DB（C-37）、ローカルのR2等、実行環境（wrangler等） |
| E2E（Web） | 上記に加えて、ブラウザ（Playwrightのブラウザ等）、起動したアプリ |
| E2E（モバイル） | Appium、エミュレーター・シミュレーター（または実機）、モバイル用のSDK |
| 性能試験・計測 | 負荷試験・計測のツール、実運用を想定したテストデータ、検証環境（C-40） |
| ミューテーションテスト | ミューテーションテストのツール |

##### 手順書に書くこと

テストの種類ごとに、次をそろえて書く。手順書はプロジェクトの`docs/testing/`に置く。

1. **必要なもの**：ツールとバージョン（C-62）。PCに直接入れるものと、Dockerのコンテナに含まれるもの（C-36）を分けて書く
2. **構築の手順**：実行する順番どおりに、番号を付けて書く。コマンドはそのまま実行できる形で書く
3. **確認の方法**：構築できたことを確かめるコマンドと、期待する結果
4. **テストの実行方法**：実行するコマンド（C-61の共通のコマンドとの関係）
5. **後始末**：テストデータの削除（C-05）と、構築・起動したものをすべて停止する手順（下記「テスト後の後始末」）
6. **よくある失敗と対処**：環境が原因で起きやすい失敗と、その確かめ方

##### ルール

- **MUST**：構築の手順は、できる限りスクリプトにして、1つのコマンドで実行できるようにする。手順書には、スクリプトが何をしているかも書く
- **MUST**：CIでも同じ手順（同じスクリプト）で環境を構築する（C-61）
- **MUST**：テストを実行する前に、確認の方法で環境が整っているかを確かめる。テストが失敗した場合は、まず環境が原因でないかを切り分けてから、実装を調べる
- **MUST**：環境が原因の失敗を見つけた場合は、「よくある失敗と対処」に追記する。どのプロジェクトでも起こり得るものは、知見（F-18）の候補にする
- CLIは、選んだ技術スタックに応じた手順書とスクリプトのひな形を生成する

##### テスト後の後始末

使い終わった環境が残ると、次の実行でポートが競合して止まる原因になる。テストのために構築・起動したものは、テストが終わったら必ずすべて閉じる。

- **MUST**：テストの工程が完了したら、そのテストのために起動したもの（開発用サーバー、静的サーバー、ブラウザ、エミュレーター、Dockerのコンテナ、wrangler等）をすべて停止し、使っていたポートを解放する
- テストが失敗した場合は、原因の調査（C-24）と修正後の確認のために、環境を起動したまま残してよい。「完了」とは、次のいずれかになったときを指す
  - 修正後の確認も含めて、テストがすべて成功した
  - ユーザーが、その作業を打ち切る・後回しにすると決めた
  - AIがその作業の報告を終えて、ユーザーに引き渡す（起動したままにする場合は、何が動いているかを報告し、止めてよいかをユーザーに確認する）
- **MUST**：起動したもの（プロセス・コンテナ・使っているポート）を記録しておき、作業が途中で途切れた場合でも、次に始めるときに、自分が残したものだと分かるようにする
- **MUST**：CIなど、人が調査しない環境では、成功・失敗・中断のどの場合でも、最後に後始末を実行する
- **MUST**：停止した後、使っていたポートが解放されたことを確認する
- **MUST**：テストを始める前に、使うポートがすでに使われていないかを確認する。使われている場合は、そのまま別のポートで続けず（別のポートに黙って切り替わるツールもあるため）、何が使っているかを確かめる
- **MUST NOT**：自分が起動したものかどうか分からないプロセスを、確認せずに停止しない。ほかの作業（別のworktree等）で使っている可能性があるため、何が使っているかを示してユーザーに確認する
- **SHOULD**：テストで使うポートは、プロジェクトごとに決めて手順書に書き、ほかのプロジェクトと重ならないようにする

#### C-70：外部APIを使う処理のテスト

本物の外部APIでテストすると、相手側に大きな負荷をかけたり、利用料金が発生したりする。そのため、外部APIを使う処理のテストは、モック等で行う。

##### 基本

- **MUST**：単体テスト・結合テスト・E2Eのいずれでも、本物の外部APIを呼ばない。モック（外部APIの代わりに決まった応答を返す仕組み）を使う
- **MUST**：E2Eでも、外部APIの代わりに応答を返すモックのサーバー等を用意し、アプリの接続先を設定（環境変数等）で切り替える。テストのためだけの分岐を本番のコードに入れない（C-25）
- **MUST NOT**：性能試験・負荷試験で、本物の外部APIを呼ばない
- **MUST NOT**：本番用のAPIキーをテストに使わない（C-05）

##### モックを本物に近づける

モックは本物と食い違っていても気づけないため、次を守る。

- **MUST**：モックの応答は、外部APIの公式の仕様（API仕様書・OpenAPI等）に沿って作る。応答の例は、仕様書の例や、提供元のテスト用環境で取得したものをもとにする
- **MUST**：成功の応答だけでなく、エラー（`4xx`・`5xx`）、要求頻度の制限（`429`）、応答の遅れ・時間切れもモックで再現してテストする
- **MUST**：外部APIの仕様が変わった場合は、モックも更新する。使っている外部APIとその仕様のバージョンを、`docs/tech-stack.md`（C-62）に記録する

##### 本物との食い違いの確認

- 提供元がテスト用の環境（サンドボックス・テストモード等）を用意している場合に限り、本物の外部APIとモックの応答が食い違っていないかを確認してよい
- この確認は、通常のテスト・CIとは分け、実行する頻度と回数を最小限にし、実行する前にユーザーの承認を得る
- テスト用の環境がない外部APIは、本物での確認を行わず、公式の仕様と、本番での監視（C-30）で食い違いに気づけるようにする

#### C-61：CIの実行環境

- **MUST**：CIでも、開発環境と同じコンテナのイメージ（C-36）を使い、「手元では通るのにCIで落ちる」ことを減らす
- **MUST**：Node.js等のバージョンは設定ファイル（`.node-version`等）で固定し、手元とCIで同じものを使う
- **MUST**：ライブラリはlockファイルどおりにインストールする（`npm ci`等）
- **MUST**：品質チェックとテストは、手元とCIで同じ1つのコマンド（例：`npm run check`）で実行する。CIの設定ファイルに、手元と異なる手順を書かない
- 実行の順番は、C-37（テスト用DBを用意 → マイグレーション → シード → テスト）に従う
- **MUST**：品質チェック（Lint・型チェック・整形）は、一部のフォルダだけに限定せず、プロジェクト全体（テストのコードを含む）に対して実行する。CIは全体を検査するため、一部だけ通しても手元では問題に気づけない
- **MUST**：テストを追加・変更した後にも、品質チェックを実行し直す

#### C-05：プロジェクトに書き込む標準ルール

ハーネスを使う人（身内を含む）のPCには、作成者個人のグローバル設定（`~/.claude/CLAUDE.md`等）が存在しない。そのため、次の標準ルールは生成するプロジェクトのAI向け設定ファイルに直接含める。F-04に従い、ルールの本体は共通ルールとして1か所で管理し、`CLAUDE.md`・`AGENTS.md`等の各ファイルへはアダプタで出力する。

各ルールの文面は、別途「生成するAI向け設定ファイルの内容」として詰める（未決定事項を参照）。以下は含める内容の骨子である。

##### テストデータ（実データ・個人情報の使用禁止）

- 本番・ステージングの実データを、匿名化せずにテストへ持ち込まない
- 実在の個人名、実在しうるメールアドレス・電話番号・住所・カード番号等、本物の認証情報を使わない
- メールアドレス・ドメインは`example.com`等の予約ドメインを使う。氏名は`testuser_001`等の明らかな架空名、パスワードは`TestPass123!`のようなテスト専用の固定値を使う
- テストデータには`testuser_%`などの接頭辞や`[E2E_TEST]`などのタグを付けて識別できるようにし、識別子だけを条件に削除する後始末用スクリプトをセットで用意する
- 本番DBに接続しうる設定でテストを実行しない

##### 秘密情報

- DB認証情報・APIキー・トークン等の実際の値は、`.gitignore`で除外したファイル（`.env`等）にだけ置く
- コミットするファイルでは、環境変数展開やプレースホルダで参照する。値の例は`.env.example`にプレースホルダだけを書く
- 「テスト用・開発用だから安全」と判断しない。`password`・`admin`のような推測しやすい値を使わない
- 秘密情報の値は、チャット・コミットメッセージ・PR・Issueの本文にも書かない
- 作業対象外のファイルで秘密情報の直書きを見つけた場合は、勝手に直さず、別のIssueにしてユーザーに知らせる

##### ログインUI（アプリ独自認証を選んだ場合）

- パスワード入力欄には、入力内容の表示・非表示を切り替えるボタンを付ける
- 新規登録・パスワード再設定など新しいパスワードを決める画面には確認用の再入力欄を設け、一致しない場合は画面側でエラーを表示してAPIを呼ばない（ログイン画面には確認欄を付けない）

#### C-09：個人情報の取扱いとアプリケーションセキュリティ

- 個人情報保護法および個人情報保護委員会ガイドラインを法令・規制上の基準として扱い、JIS Q 15001:2023とISO/IEC 27701:2025を個人情報保護マネジメントの参照基準として活用する。
- アプリケーションの技術的なセキュリティ要件と検証にはOWASP ASVSを参照する。ASVSのレベルは、プロジェクトに関するチェックリストへの回答から判定する。
- チェックリストには、各項目の回答と、その回答がレベル判定にどう影響したかを記録できるようにする。具体的な質問、判定基準、該当しない項目の扱いは別途定める。
- 参照する法令・ガイドライン・規格・ASVSの版を明記し、法令や参照資料が改定された場合に見直せるようにする。
- これらの基準を参照して要件を生成することは、法令適合、規格適合または認証取得を保証するものではない。

#### C-12：認証方式の選択

- 認証方式は「認証なし」「アプリ独自認証」「外部IdPによるOIDC認証」「アプリ独自認証とOIDC認証の併用」から選択できるようにする。
- 認証なしを選ぶ場合は、認証を必要としない公開対象を明示する。
- 外部IdPを利用できる場合はOIDC認証を推奨する。アプリ独自認証を選ぶ場合は、パスワードや認証情報の保護、ログイン試行への対策、認証情報の再設定、セッション管理等の追加要件を適用する。具体的な要件は認証方式と技術スタック別の設計で定める。
- 併用する場合のアカウント連携、重複アカウントの扱い、認証手段の追加・解除等は、別途設計する。

#### C-13：認可の基本原則

- 認可はデフォルト拒否とし、明示的に許可した操作だけを実行できるようにする。認証不要で公開するAPIや機能は、その対象を明示する。
- 認証が必要なAPIでは、バックエンドが各リクエストで利用者と対象リソースに対する操作権限を確認する。
- フロントエンドで画面や操作ボタンを非表示にすることは、認可の代わりにならない。画面表示の制御とは別に、バックエンドで認可を強制する。

#### C-14：認可範囲の定義

- 認可要件では、誰が（主体）、何を（操作）、どのリソースに対して行えるかを定義する。必要に応じて、テナント・組織・所属・状態などの条件も含める。
- 認可条件には、認証済みであること、ロールやグループ、リソースの所有者・所属関係などを組み合わせて使える。全プロジェクト共通の「一般利用者」ロールや固定のロール名は必須にしない。
- 管理者ロールは全プロジェクトで必須とはしない。管理者向け機能を設ける場合は、機能要件ごとに管理者が行える操作と対象データの範囲を定義し、「管理者」を無制限の権限として扱わない。
- 複数人でアプリ内のデータや設定を作成・編集する機能では、機能要件に所有単位（個人・チーム・組織等）と、共同編集を許可する利用者の範囲・操作を定義する。作成者、所有者、共同編集者は同一とは限らないため、必要に応じてそれぞれ区別する。
- ログインしたことだけで、すべての機能やデータへのアクセスを許可してはならない。利用者ID・ロール・テナントID等の権限判断に使う値は、クライアントから送られた値をそのまま信用せず、認証済み主体やサーバー側の情報から取得・検証する。
- 権限の付与・変更・取り消しも保護対象の操作として扱い、機能要件で実行できる主体、対象者、変更可能な権限と範囲を定義する。権限管理者の階層や委任範囲はプロジェクトごとに定め、最上位の管理者だけが変更できる構成も、下位管理者が許可された範囲で管理できる構成も選べるようにする。
- 管理者が自分自身の権限を不正に引き上げたり、許可範囲を超えて他者へ権限を付与したりできないよう、バックエンドで現在の主体と委任範囲を検証する。
- 認証を要求する機能で認可範囲が要求に定義されていない場合は、権限の不足としてユーザーに確認する。確認が済むまでは、該当する保護対象の操作を拒否する。
- リソースIDを指定して取得・変更・削除する操作では、そのリソース単位で毎回権限を確認する。一覧取得では、利用者がアクセスできる範囲に結果を絞る。
- 認可テストでは、未認証、許可された主体、許可されていない主体、異なる所有者・所属のリソースを使い、閲覧・作成・更新・削除などの操作ごとに許可／拒否を確認する。共同編集機能では、所有者・許可された共同編集者・許可されていない利用者の境界を確認する。
- 権限管理機能がある場合は、許可された主体による権限変更に加え、自己昇格、委任範囲を超えた付与、上位管理者の権限変更など、要件上許可されない操作が拒否されることをテストする。

#### C-16：セッションとログアウトの範囲

- アプリケーションからログアウトするときは、認証方式にかかわらず、アプリケーション自身のセッションをクライアントとサーバーの両方で終了・無効化する。
- OIDCを利用する場合、アプリケーションのセッションと外部IdPのセッションは別のものとして扱う。アプリケーションからログアウトしてもIdP側のセッションが残り、次回ログイン時に利用者が再認証せずアプリケーションへ戻る場合があることを前提とする。
- IdP側のセッションも終了させるかどうかはプロジェクトごとに明示する。IdPからのログアウトは、同じIdPを使う他のアプリケーションの利用にも影響し得るため、アプリケーションのログアウトと常に一体の動作にしてはならない。
- OIDCのログアウト範囲を選択した場合は、ログアウト後の画面遷移、IdP側セッションの状態、次回ログイン時の再認証または自動ログインの挙動を確認し、テストする。利用者にとってログアウト完了の意味が分かるように案内する。
- アプリ独自認証とOIDCを併用する場合も、どの認証方法でログインしたかにかかわらずアプリケーション自身のセッションは終了する。IdP側セッションの終了は、OIDCログアウト方針に従って別途扱う。

#### C-17：アプリケーション発行トークンのライフサイクル

- アクセストークンとリフレッシュトークンの組み合わせは、アプリケーション独自認証で必須とはしない。サーバー側セッション等を含め、クライアント種別とシステム構成に適した方式を選ぶ。アプリケーションがこのトークン方式を採用する場合は、以下を適用する。
- アクセストークンは必要な用途・対象に限定し、漏えい時の悪用可能時間を抑える有効期間を設定する。リフレッシュトークンにはアイドル期限または最長有効期間を設け、具体的な期間はリスク、利用形態、クライアント種別を根拠に技術設計で決定する。
- リフレッシュトークンを発行する場合は、更新ごとに新しいトークンを発行して旧トークンを無効化するローテーションを行う。無効化済みトークンの再利用を検知した場合は、同一セッション／トークン系列を失効させ、再認証を要求する。複数タブ・同時リクエストで正当な更新が競合しないよう、更新処理を調整する。
- リフレッシュトークンの更新期限を延長する場合も、初回認証時に定めた最長有効期間を超えて無期限に延長してはならない。アイドル期限と最長有効期間をどのように組み合わせるかは、認証方式別の設計に記録する。
- ログアウト、アカウント停止、認証情報の変更・漏えい等でセッションを終了する際は、該当するリフレッシュトークンと関連セッションをサーバー側で失効させる。アクセストークンの有効期限が残る間の扱い（短い有効期間、失効照会等）も明示する。
- トークン方式を採用する場合、トークンの保存場所・送信方法をクライアント種別ごとに決める。ブラウザーでは、JavaScriptから読み取れるWeb Storageへ認証トークンを保存せず、BFFまたは適切なCookie等の保護策を検討する。
- アプリケーション発行トークンと外部IdP発行トークンは、発行者、用途、対象（audience）、署名鍵、更新・失効管理を分離する。外部IdPのIDトークンをアプリのAPI用アクセストークンとして扱わず、受信する各トークンの発行者・署名・対象・有効期限・用途を検証する。OIDCログイン後にアプリ独自のセッションまたはトークンを発行する場合は、そのライフサイクルをIdP側のトークンとは別に定義する。
- 権限変更の反映をトークン内の古いロール情報だけに依存させない。保護対象の操作ではC-13・C-14に従って権限を確認し、即時反映が難しい構成を採用する場合は、反映までの時間差と補完策を明示する。
- トークンの有効期限・更新成功／失敗・ローテーション・旧トークン再利用・ログアウト後の利用・アカウント停止後の利用・権限変更後の操作をテストする。期限切れ時の画面動作はC-15、ログアウトの範囲はC-16にも従う。

#### C-18：認証情報・認証要素の回復

- OIDCを利用する場合、IdPが管理するパスワード、MFA等の認証情報・認証要素の回復はIdPの手続きに委ねる。アプリケーションはIdPの回復機能を独自に代行・迂回しない。
- アプリ独自認証で管理するパスワードや認証要素の回復は、アプリケーションの責任として設計する。OIDCとアプリ独自認証を併用する場合は、どの認証手段を回復する手続きなのかを利用者に明示し、相互に取り違えない。
- アプリ独自のパスワード再設定では、アカウントの有無を第三者に推測されにくい応答とし、再設定用トークン／コードを推測困難・一回限り・期限付きにする。再設定の要求だけでアカウントを変更・停止せず、有効な再設定証明を確認してから変更する。
- 回復手続き完了後は利用者へ通知し、回復後の自動ログインを既定にしない。通常の認証手続きを行わせる。回復前のセッションやリフレッシュトークンを失効させる方針を定め、関連する挙動をテストする。
- MFA等の認証要素を回復・交換する場合は、既存要素を利用できない状況も想定した本人確認方法を設計する。回復手続きが通常の認証より弱い経路にならないようにし、変更後の通知とセッションの扱いを定める。
- OIDCの回復先、アプリ独自回復の手順・有効期限・試行制限・通知方法・セッション失効範囲は、認証方式と機能要件に応じて具体化し、正常系と不正・期限切れ・再利用等の拒否ケースをテストする。

#### C-19：ログイン試行制限とセキュリティ通知

- アプリ独自認証のログイン、パスワード再設定、認証要素の確認・回復など、オンラインで秘密を試せる処理には、総当たり・自動化された試行を抑えるレート制限を設ける。制限はアカウント単位を基本とし、IPアドレス・端末・挙動等の信号も組み合わせて回避と誤検知の両方を抑える。
- 失敗回数の閾値、観測期間、待ち時間、解除条件は一律の共通数値に固定せず、認証方式、利用者数、扱う情報の重要度、攻撃リスクに応じて技術スタック別に定める。失敗が続く場合は待ち時間を段階的に延ばす方法等を検討し、恒久的なアカウントロックを自動適用することを既定にしない。
- 制限の設計では、第三者が他人のアカウントを意図的にロックして利用を妨害できないようにする。登録アカウントの有無をログイン応答から推測されにくくし、試行制限によって正当な利用者が締め出された場合の安全な回復手段を用意する。
- 個人情報や重要データを扱うなどリスクが高いアプリでは、不審な試行の集中や強い制限の発動を、登録済みの連絡先等へ通知する方法を設ける。通知頻度を抑制・集約し、通知機能自体が大量送信攻撃に利用されないようにする。
- セキュリティ通知は不審な事象を知らせるものであり、それだけでログインを承認したり、本人確認を完了したり、制限を解除したりしてはならない。追加の本人確認やアカウント回復は、C-18に従う別の安全な手段で行う。通知には心当たりがない場合の次の行動を分かりやすく示す。
- OIDC認証のログイン試行制限は原則としてIdP側の機能・ポリシーに委ね、アプリ側で独自に迂回・重複した制限を設けない。アプリ独自認証を併用する場合は、アプリ独自認証の経路に本項を適用する。
- 試行制限の境界値、待ち時間、解除・回復、通知の発生条件と頻度、アカウント有無の秘匿、正当なログインへの影響をテストする。具体的な回数・期間・通知先・通知方法は技術スタック別の設計時に決定する。

#### C-20：多要素認証（MFA）と重要操作の再認証

- MFAを全利用者に必須とするか、任意とするか、特定の利用者・機能だけで要求するかは、扱う情報、操作による影響、想定される攻撃、利用者層および運用負荷を踏まえたリスク評価で決定する。簡易的なアプリであっても、MFAの適用要否を検討せずに省略してはならない。
- 管理者・高権限利用者については、アカウント乗っ取り時にできる操作と影響範囲を評価し、MFAを必須とするかを明示的に決定する。利用者やデータが広範囲に及ぶサービス、個人情報・金銭・設定変更等を扱うサービスでは、管理者MFAを原則として要求する方向で検討する。
- パスワードや認証要素、登録メールアドレス、権限、送金・公開・削除等の重要な操作では、現在のログイン状態だけで足りるかを評価し、必要に応じてMFAまたは再認証（step-up authentication）を求める。対象操作と必要な認証強度は機能要件で定義する。
- OIDCを利用する場合は、IdPで行われたMFAまたは再認証をどの条件で受け入れるか、アプリ側で追加確認が必要な条件は何かを定める。アプリ独自認証の場合は、採用するMFA方式、認証要素の追加・交換・回復をC-18に従って設計する。
- MFAや再認証の要求、失敗、認証要素の追加・変更・解除、回復をテストする。認証の強さが不足する場合は、重要操作を実行させない。

#### C-27：入力チェックとXSS対策

- 入力チェックは必ずバックエンドで行う。画面側のチェックは利用者の補助であり、代わりにならない
- SQLはライブラリのパラメータ機能（プレースホルダ）で組み立て、文字列の連結で作らない（詳しくはC-72）
- 画面への出力はフレームワークの自動エスケープに任せる。`dangerouslySetInnerHTML`などエスケープを外す書き方は原則禁止し、やむを得ず使う場合は信頼できるサニタイズ処理を通して、理由を記録する
- 利用者が入力したURLをリンク等に使う場合は、`http:`・`https:`など許可したスキームだけを受け付ける（`javascript:`等を拒否する）
- CSP（Content Security Policy）ヘッダーを設定し、読み込んでよいスクリプトの出どころを制限する。具体的な設定値は技術スタック別に定める

#### C-28：HTTPメソッドの安全性とCSRF対策

- GET・HEAD・OPTIONSでは、DBの更新・ログアウト・メール送信など、状態を変える処理をしない（RFC 9110の安全なメソッド）。状態を変える操作は、POST・PUT・PATCH・DELETEで行う
- 認証にCookieを使う場合は、`SameSite=Lax`を標準とし、あわせて`Secure`・`HttpOnly`を付ける。`SameSite=None`はクロスサイトでの利用が必要な場合に限り、理由を記録する
- `SameSite=Lax`は、別サイトからのリンクによるGETの画面遷移ではCookieを送るため、上記の「GETで状態を変えない」ルールとセットでCSRF対策として扱う
- SameSiteは同じサイトの別サブドメインからのリクエストを防げないため、状態を変えるリクエストでは`Origin`ヘッダー（またはCSRFトークン）も確認し、許可していない送信元からの要求を拒否する

##### 必須のテスト（結合テスト）

- **GETで状態が変わらないこと**：すべてのGETのAPIを呼び出し、呼ぶ前と後でDBの内容が変わっていないことを確認する。対象のAPIはテストコードに手で列挙せず、アプリのルーティング定義から取得して、APIの追加時にテストの漏れが出ないようにする
- **CSRF対策が効いていること**：状態を変えるAPIに、許可していない`Origin`や`Origin`なしで要求したときに拒否されること、許可した`Origin`からは成功することを確認する
- **Cookieの属性**：ログイン等で発行するCookieに`SameSite`・`Secure`・`HttpOnly`が意図どおり付いていることを確認する

#### C-29：CORSの設定

- 画面とAPIを同じオリジン（同じドメイン）から配信する構成を標準とする。この場合、CORSは許可しない
- 別のオリジンから呼び出す必要がある場合だけCORSを許可し、許可する送信元（Origin）を明示的に列挙する。次の設定は禁止する
  - 認証情報（Cookie等）を送る設定で、`Access-Control-Allow-Origin: *`を返す
  - 要求の`Origin`を確認せずに、そのまま`Access-Control-Allow-Origin`に返す
  - `null`のOriginを許可する

##### 必須のテスト（結合テスト）

- 許可したOrigin・許可していないOrigin・`null`・`Origin`なしのそれぞれで要求し、`Access-Control-Allow-Origin`・`Access-Control-Allow-Credentials`が意図どおりであることを確認する
- 事前確認（preflight、`OPTIONS`）の要求に対して、許可するメソッド・ヘッダーが必要最小限であることを確認する
- CORSを許可しない構成では、CORSを許可するヘッダーを返していないことを確認する
- 結合テストで確認できるのはアプリ側の設定だけである。Cloudflare等のインフラ側でヘッダーを追加・変更している場合は、デプロイした環境に対しても同じ確認を行う

#### C-63：ファイルのアップロードと保存

アプリに含める画像（ロゴ・アイコン等）はアプリと一緒にデプロイし、ここでは**利用者がアップロードするファイル**（写真・動画・文書等）を対象とする。

##### 公開範囲

- **MUST**：保存場所（R2のバケット等）とファイルは、**すべて非公開をデフォルト**とする
- **MUST**：ファイルを配信するときは、アプリが権限を確認してから配信するか、期限の短い一時的なURLを発行する（C-13）
- 公開にしたいファイルがある場合は、後から公開に切り替える。その場合は次を守る
  - 公開する理由と対象をADR（C-35）に記録し、承認を得る
  - 公開用と非公開用の保存場所を分け、同じ保存場所に混ぜない
  - 公開する場合も、書き込み・削除はアプリからだけ行えるようにする

##### アップロードの方法

| 方法 | 使うとき |
| --- | --- |
| アプリのサーバーを経由する（標準） | 画像など小さめのファイル。サーバーで中身を確認してから保存する |
| ブラウザからストレージへ直接送る | 動画など大きいファイル。サーバーが期限付きのアップロード用URLを発行し、ブラウザはそのURLへ直接送る。アップロードの完了後に、サーバーで中身を確認する |

- 実行環境が1回のリクエストで受け取れるサイズの上限（Cloudflare Workersは契約プランによって異なる）を超えるファイルは、直接送る方式にする。具体的な上限は技術スタック別に確認する

##### 安全対策

- **MUST**：ファイルの種類ごとにサイズの上限を決め、画面側とサーバー側の両方でチェックする（C-47）
- **MUST**：拡張子やブラウザが申告する形式を信用せず、ファイルの先頭の中身で形式を判定する。許可した形式だけを受け付ける
- **MUST**：利用者が付けたファイル名を、保存場所の名前に使わない。ランダムな名前を付ける
- **MUST**：写真の撮影場所などの情報（Exif）を削除してから保存する（C-09）
- **MUST NOT**：SVGなどスクリプトを含み得る形式を、原則として受け付けない。受け付ける場合は、画面に直接表示せずダウンロードさせる扱いにする（C-27）
- **MUST**：利用者ごとの保存容量の上限と、アップロードの回数の制限を設ける（C-59）
- **MUST**：データの削除時・退会時に、関係するファイルも削除する。DBとストレージの食い違い（どこからも参照されないファイル）を定期的に掃除する

##### 動画

- アップロードされた動画をそのまま再生するだけなら、通常の保存先（R2等）で扱う
- 再生用の形式への変換や、通信速度に合わせた画質の切り替えが必要な場合は、動画専用のサービス（Cloudflare Stream等）を使うかをプロジェクトごとに検討し、ADRに記録する

##### 必須のテスト

- 上限を超えるファイル、許可していない形式、拡張子を偽ったファイルが拒否されること
- 権限のない利用者・未ログインの利用者が、ファイルを取得できないこと
- 保存したファイルに位置情報が残っていないこと
- データの削除時に、関係するファイルも削除されること

#### C-58：セキュリティヘッダー

CSP（C-27）に加えて、すべての応答に次のヘッダーを付ける。

| ヘッダー | 値 | 目的 |
| --- | --- | --- |
| `Strict-Transport-Security` | `max-age=31536000; includeSubDomains` | 常にHTTPSで通信させる |
| `X-Content-Type-Options` | `nosniff` | ファイルの種類の勝手な推測を防ぐ |
| CSPの`frame-ancestors`と`X-Frame-Options` | `'none'`と`DENY` | ほかのサイトへの埋め込み（クリックジャッキング）を防ぐ |
| `Referrer-Policy` | `strict-origin-when-cross-origin` | 別のサイトへ移るときに、URLの詳細を渡さない |
| `Permissions-Policy` | 使わない機能（カメラ・マイク・位置情報等）を無効にする | 不要なブラウザの機能を使わせない |
| `Cache-Control`（認証が必要なAPI・個人向けのデータ） | `no-store` | 個人向けのデータをキャッシュに残さない（C-10） |

- 他のサイトへの埋め込みが必要な機能を作る場合は、許可する埋め込み元を明示し、理由をADR（C-35）に記録する

##### 必須のテスト（結合テスト）

- 主要な応答に、上記のヘッダーが意図どおりの値で付いていることを確認する
- Cloudflare等のインフラ側でヘッダーを追加・変更している場合は、デプロイした環境に対しても同じ確認を行う

#### C-59：APIのレート制限

ログイン等の認証の試行制限（C-19）に加えて、API全体にレート制限を設ける。

- **MUST**：公開するAPIすべてにレート制限を設ける。ログインしている場合は利用者ごと、ログインしていない場合はIPアドレスごとに数える
- **MUST**：重い処理（検索、データの書き出し、メール送信、ファイルのアップロード等）には、通常より厳しい制限を設ける
- **MUST**：制限を超えた場合は`429`と`Retry-After`ヘッダーを返し、利用者には「しばらく待ってから再試行する」ことを案内する（C-15）
- 制限の値は、プロジェクトの利用規模に応じて決める。インフラの入口（エッジ）で制限するか、アプリで制限するかは技術スタック別に定める
- **MUST**：制限の境界値（上限ちょうど・上限を超えた場合）と、制限が解除されることをテストする
- **MUST**：E2Eでは、レート制限のあるAPIの呼び出しを必要最小限にする。E2Eは同じ送信元から続けて実行されるため、途中で上限に達して失敗しやすい。レート制限そのものの検証は、バックエンドのテストで行う

#### C-72：SQLインジェクション対策

- **MUST**：SQLに値を入れるときは、必ずライブラリのパラメータ機能（プレースホルダ）で渡す。利用者の入力を、文字列の連結・テンプレート文字列でSQLに埋め込まない
- **MUST**：生SQL（C-03の`*.sql.ts`等）を書く場合も、値はパラメータで渡す。ライブラリが用意している、値をそのまま埋め込む機能（Drizzleの`sql.raw`等）に、利用者の入力を渡さない
- **MUST**：並び替えの列名・並び順（`ASC`／`DESC`）・テーブル名など、パラメータで渡せない部分を入力で変える場合は、許可した値の一覧（許可リスト）と照合し、一覧にある値だけを使う
- **MUST**：`LIKE`で検索する場合は、入力に含まれる`%`・`_`を無害化してから、パラメータで渡す
- **MUST**：`IN`の条件に複数の値を渡す場合も、値を1つずつパラメータで渡す
- **SHOULD**：アプリがDBに接続するユーザーの権限は、必要な操作だけに絞る（テーブルの削除等の権限を与えない）
- **MUST**：検索・並び替えなど入力をSQLに使う処理では、SQLインジェクションを狙った入力（`'`・`;`・`--`・`OR 1=1`等を含む値）を渡しても、意図しない結果にならないことをテストする

### 2.7 エラー応答

| ID | 内容 |
| --- | --- |
| C-15 | エラー応答は適切なHTTPステータスと識別可能なアプリケーションエラーコードを返し、利用者には理解しやすく次の行動が分かるメッセージを示す |
| C-71 | エラーをもみ消したり、ごまかしたりする実装をしない |
| C-73 | 予期しないエラーは、フロントエンド・バックエンドそれぞれのグローバル例外ハンドリングで1か所にまとめて処理する |

#### C-15：エラー応答と利用者への案内

- HTTPステータスコードはRFC 9110を参照して使い分ける。先頭の数字による分類は、`1xx`が処理継続中、`2xx`が成功、`3xx`が追加の処理・転送、`4xx`が要求内容や条件に関する問題、`5xx`がサーバー側で処理を完了できない状態を表す。
- APIでは、状況に応じて代表的なHTTPステータスを選ぶ。例として、`200`（成功して応答本文あり）、`201`（リソース作成）、`204`（成功して応答本文なし）、`400`（不正な要求）、`404`（リソースが見つからない、または存在を開示しない）、`409`（現在のリソース状態との競合）、`413`（要求内容が大きすぎる）、`415`（対応していないメディア形式）、`422`（形式は理解できるが内容を処理できない）、`429`（要求頻度の制限）、`500`（予期しないサーバー内部エラー）、`502`（中継先から不正な応答）、`503`（一時的にサービスを利用できない）、`504`（中継先から時間内に応答がない）を候補とする。機能・APIごとの適用ケースは要件とAPI仕様で決める。
- ステータスコードはエラーの大分類であり、細かな業務上の原因をすべて表すものではない。アプリケーション固有のエラーコードや応答本文を併用して原因を識別し、クライアントが安定して処理できるようにする。RFCに定義された名前や例だけから各機能の期待コードを推測せず、API仕様で明示する。
- APIのエラー応答では、HTTPステータスコードをエラーの種類に適したものにし、必要に応じてアプリケーション固有の安定したエラーコードを別途返す。HTTPステータスは通信上の分類、アプリケーションエラーコードは個別の原因を識別するために使い、両者を混同しない。
- 認証情報がない・無効で処理できない場合は401、認証済みだが許可されない操作は403を基本とする。権限不足をログイン切れとして扱わず、403を理由にログアウトやログイン画面への遷移を行わない。リソースの存在自体を開示しない必要がある場合の404応答は、機能・脅威要件で明示する。
- 利用者向けメッセージは、何が起きたかを理解でき、次に取れる行動（入力修正、再試行、再ログイン、管理者への問い合わせ等）が分かる表現にする。技術用語だけの表示や、原因・対処が分からない「エラーが発生しました」だけの表示を避ける。対処方法がない場合も、その旨と問い合わせ先等を機能に応じて案内する。
- 権限の変更・拒否によって、ユーザーが利用できる機能、データ、操作結果に予期しない変化が生じる場合は、変化に関係する画面や操作の近くで、その変化と次に取れる行動を通知する。すべての拒否で大きな警告を出すのではなく、ユーザーが気づく必要のある変化に応じた表示とする。通知は不要に繰り返さず、権限のない情報や内部の認可条件を漏らさない。
- サーバー内部の例外、スタックトレース、SQL、秘密情報、他利用者の情報などを利用者向けメッセージや公開API応答に含めない。調査に必要な詳細はアクセス制御されたログに記録し、利用者向けメッセージと分ける。
- 認証切れ・無効を示す401を受けた場合、選択した認証方式に更新手段があれば一度だけ更新を試す。更新に成功した場合も、元の要求の再送は二重実行されないことを確認できる場合に限り一度だけ行う。更新手段がない、または更新に失敗した場合は認証状態を解除し、ログイン画面へ一度だけ遷移して、可能であればセッション終了を説明する。複数要求が同時に401となっても、更新や遷移を重複させない。
- セッション期限切れ時は、可能な範囲で入力中データの扱いとログイン後の戻り先を明確にする。戻り先を引き継ぐ場合は、許可されたアプリ内遷移先に限定し、外部サイトへの不正な転送を防ぐ。
- エラー検証では、要件・入力条件・認証状態・権限状態ごとに、成功時と失敗時の期待HTTPステータス、アプリケーションエラーコード、利用者向け表示、データ変更の有無を定義する。自動テストで応答ステータス、エラーコード、応答形式、意図しない副作用がないことを確認する。代表的な画面・E2Eテストでは、メッセージが状況に合い、次の行動を案内することもレビューする。
- エラーコードのテストは、実装が返した値をそのまま期待値にするのではなく、要件やAPI仕様で定義した期待値と照合する。異なる原因が同じコードに誤って集約されていないこと、無関係な成功・失敗ケースで誤ったコードを返さないこと、クライアントがコードに応じた表示・動作をすることを確認する。エラー応答仕様を変更した場合は、API契約テストと該当する利用者向け表示のテストを更新する。
- HTTPステータスの使い分けはRFC 9110、技術的なセキュリティ要件はOWASP ASVS等を参照する。参照基準は個別機能の期待コード・文言・画面動作を自動的に決めるものではないため、これらは機能要件/API仕様で明示する。

#### C-71：エラーのもみ消しの禁止

フロントエンド・バックエンド・SQLのいずれでも、エラーをもみ消したり、ごまかしたりする実装をしない。エラーが隠れると、不具合に気づけず、原因の調査もできなくなる。

##### してはいけないこと

- **MUST NOT**：何もしない`catch`（空の`catch`、コメントだけの`catch`）を書かない
- **MUST NOT**：エラーを受け止めて、成功したように見える値（空の配列・`null`・既定値・`true`等）を返さない。例：取得に失敗したのに「データなし」として空の一覧を表示する
- **MUST NOT**：`Promise`の失敗（`reject`）を放置・無視しない。`await`し忘れや、`.catch(() => {})`で消さない
- **MUST NOT**：エラーをログに出すだけで、処理を成功として続けない
- **MUST NOT**：SQLのエラーや結果を無視しない。更新・削除した件数を確認すべき処理（楽観的ロック等、C-64）で件数を確かめずに成功扱いにしない。`INSERT OR IGNORE`・`ON CONFLICT DO NOTHING`など、失敗を黙って無視する書き方は、意図と理由を書いた場合だけ使う
- **MUST NOT**：型エラー・Lintのエラーを、無視の指定（`@ts-ignore`・`eslint-disable`等）で隠さない（C-53）
- **MUST NOT**：テストの失敗を、待ち時間の延長・再試行・期待値の変更でごまかさない（C-25）

##### 代わりにすること

- エラーを受け止めた場所で対処できる場合（再試行・代わりの処理等）だけ、そこで処理する。対処できない場合は、受け止めずに呼び出し元へ伝える
- エラーの種類を変えて伝える場合は、元のエラー（原因）を失わないように含める
- 最終的な処理は、グローバル例外ハンドリング（C-73）にまとめる
- 例外として、主の処理に付随する後始末の失敗は、主の処理の結果を変えずにログへ記録してよい（C-64）。この場合も、黙って消さずに必ずログに残す

#### C-73：グローバル例外ハンドリング

各所で個別に`try`〜`catch`を書くのではなく、処理しきれなかったエラーを1か所で受け止めて、ログと応答をそろえる。

##### バックエンド

- **MUST**：アプリ全体で1つのエラーハンドラ（Honoの`onError`・`notFound`等）を用意し、処理しきれなかったエラーはすべてここで受け止める
- **MUST**：業務上想定できるエラー（入力の誤り・権限不足・リソースなし・競合等）は、アプリ独自のエラーの型で投げ、エラーハンドラでHTTPステータスとアプリケーションエラーコード（C-15）に変換する
- **MUST**：想定していないエラーは、利用者には`500`と一般的なメッセージだけを返し、詳細（スタックトレース・SQL等）はリクエストIDと一緒にログへ記録する（C-15・C-30）
- **MUST**：エラー応答の形式（項目名・構造）をアプリ全体で統一し、API仕様（OpenAPI、C-31）に書く
- **SHOULD**：Controller・Serviceで、エラーハンドラと同じ変換を個別に書かない。各層はエラーを投げるだけにし、変換はエラーハンドラに任せる

##### フロントエンド

- **MUST**：API通信のエラーは、API層（C-46のインターセプター）で、アプリ内で扱う共通のエラーの形に変換する
- **MUST**：画面の表示中に起きたエラーは、React Error Boundary（C-48）で受け止め、代わりの表示を出す
- **MUST**：画面の外で起きたエラー（処理されなかった`Promise`の失敗・`window`のエラー）も、全体の受け止め口でログに記録する
- **MUST**：利用者に見せるメッセージとログは分ける（C-48）

##### テスト

- **MUST**：想定できるエラーごとに、期待するHTTPステータス・エラーコード・応答の形式になることをテストする
- **MUST**：想定していないエラーで、詳細が応答に含まれないこと、ログに記録されることをテストする

| C-38 | これまでの共通仕様を守ったうえで、**メンテナンス性**（後から読みやすく、変更しやすいこと）を考慮して設計する |
| C-53 | AIは既存のコードに合わせ、要求された範囲だけを変更し、エラーを隠さない |
| C-56 | 判断に迷う場面では知見（ヒューリスティクス）を参照する。知見より共通仕様を優先し、当てはまらない場合は根拠に基づいて判断する |
| C-57 | コードは自動整形ツールで整形し、ファイル・識別子・DBの名前は命名規則に従う |

#### C-38：メンテナンス性を考慮した設計

共通仕様（C-01〜）を守ることを前提に、次の基準で設計・実装する。「メンテナンス性」を感覚で判断せず、下の基準で確認する。

| 観点 | 基準 |
| --- | --- |
| 既存に合わせる | 新しく書くコードは、プロジェクト内の既存の書き方・命名・構成に合わせる。別の書き方を持ち込む場合は、理由をADR（C-35）に記録する |
| 単純さ | 要求を満たす一番単純な方法を選ぶ。今は必要のない将来の拡張のための仕組み（使われない設定・抽象化など）を作らない |
| 変更の影響範囲 | 1つの変更が、関係のない多くのファイルに波及しない構成にする。層の責務（C-03・C-06）を守ることで、変更を1つの層に閉じ込める |
| 重複 | 同じ処理・同じ知識（ルールや定数）を複数の場所に書かない。ただし、偶然似ているだけの処理を無理に共通化しない |
| 命名 | 名前だけで役割が分かるようにする。省略語や、`data`・`util`のような意味の広い名前を避ける |
| 大きさ | 1つの関数・ファイルが複数の役割を持ち始めたら分割する |
| 値の直書き | 環境によって変わる値や、意味のある定数をコードに直書きしない。設定や名前付きの定数にする |
| 不要なコード | 使われていないコード・コメントアウトしたコードを残さない（履歴はGitで追える） |
| コメント | コードを読めば分かる「何をしているか」は書かず、コードから読み取れない「なぜそうしたか」だけを書く |
| 依存関係 | ライブラリは必要なものだけに絞る（C-32）。標準機能や既存の依存関係で済む場合は、新しく追加しない |
| テストしやすさ | 外部サービス・時刻・乱数などへの依存は、テストで差し替えられる形にする（C-25） |

- 上記の基準は、レビュー（C-33）の観点にも使う

#### C-53：AIの作業ルール

フロントエンド・バックエンド・DB・IaCなど、すべての作業に適用する。ルールの強さの表記（MUST等）は2.4と同じ。

作業の進め方

- **MUST**：変更する前に、既存のコードの設計・命名・ディレクトリ構成を確認する
- **MUST**：変更の範囲は、要求された機能に必要な最小限にする
- **MUST NOT**：依頼されていない大規模なリファクタリングを、同時に行わない
- **MUST NOT**：既存の公開API・型・動作を、理由なく変更しない
- **MUST**：設計の選択肢が複数ある場合は、既存のパターンを優先する（C-38）
- **SHOULD**：既存のコードに同じような実装がある場合は、それを参照してそろえる

確認とエラーの扱い

- **MUST**：既存のテストがある場合は、変更後に実行する
- **MUST**：lint・型チェック・テストを通す
- **MUST NOT**：エラーを無視するために、`eslint-disable`や`@ts-ignore`を安易に追加しない
- **MUST**：失敗した場合は原因を修正する。エラーを隠して成功扱いにしない（C-25）

依存ライブラリの追加（C-32に加えて）

- **MUST NOT**：目的を達成するためだけに、新しいパッケージを無断で追加しない
- **MUST**：新しいライブラリを追加する前に、次を確認し、結果を承認の依頼に含める
  - 既存のライブラリで代わりにならないか
  - 言語・フレームワークの標準機能で実装できないか
  - メンテナンスが続いているか
  - セキュリティ上の問題がないか
  - バンドルサイズへの影響

#### C-56：知見（ヒューリスティクス）の使い方

使い方のルールは全分野で共通とし、知見の中身は分野ごとに`knowledge/`（F-18）に置く。

- **MUST**：判断に迷う場面（分割するか、共通化するか、どの構成にするか等）では、まず`knowledge/`の該当する分野の知見を確認する
- **MUST**：知見は絶対のルールではない。共通仕様（MUST・MUST NOT）が知見より優先する
- **MUST**：知見に当てはまらない場面では、実測や根拠に基づいて判断し、理由を記録する（C-35）
- **SHOULD**：知見が外れた例や、新しく得た判断基準は、F-18の流れで知見に反映する

#### C-57：コードの自動整形と命名規則

- **MUST**：自動整形ツール（TypeScriptならPrettier等）を使い、書式について人やAIが判断しない
- **MUST**：品質チェック（F-16）で整形済みかを確認し、整形されていなければ失敗とする

| 対象 | 規則 | 例 |
| --- | --- | --- |
| Reactコンポーネントのファイル | PascalCase | `UserList.tsx` |
| Custom Hookのファイル | `use`＋camelCase | `useUserList.ts` |
| その他のTypeScriptファイル | kebab-case | `date-format.ts` |
| ディレクトリ | kebab-case | `user-profile/` |
| テスト | 対象と同じ場所に置き、`.test`を付ける | `UserList.test.tsx` |
| DAOの生SQL | `.sql.ts` | `sales-report.sql.ts` |
| マイグレーション | 番号＋snake_case | `0003_add_users_email_index.sql` |
| 変数・関数 | camelCase | `fetchUsers` |
| 型・コンポーネント | PascalCase | `UserResponse` |
| 定数 | UPPER_SNAKE_CASE | `MAX_PAGE_SIZE` |
| 環境変数 | UPPER_SNAKE_CASE | `DATABASE_URL` |
| DBのテーブル・カラム | snake_case。テーブルは複数形 | `users`、`created_at` |

## 3. 機能要件

| ID | 機能 | 優先度 | 概要 |
| --- | --- | --- | --- |
| F-01 | 対話形式でのハーネス生成 | MUST | プロジェクトを作るときに質問に答えると、条件に合ったハーネス一式が生成される |

| F-17 | Superpowers利用案内 | MUST | Claude Code・Codex向けの生成設定にSuperpowersの作業フローを反映し、READMEに環境別の導入・利用確認手順を含める |
| F-18 | 知見の蓄積と配布 | MUST | SQLの書き分けやインデックス設計などの判断基準（ヒューリスティクス）をハーネスのリポジトリに蓄積し、選んだ技術スタックに関係するものを生成するプロジェクトへ配布する |
| F-19 | バージョンの調査と選定理由の記録 | MUST | 選んだ技術について、最新の安定版などを調べたうえで採用するバージョンを決め、なぜそのバージョンにしたかを記録する |
| F-20 | ファイル保存の選択 | MUST | 利用者がアップロードするファイルを扱うかと、ファイルの種類を選べる。扱う場合は、非公開の保存先（初回はCloudflare R2）とアップロード処理のひな形を生成する |
| F-21 | AI向け設定ファイルの構成 | MUST | 共通ルールの核を`AGENTS.md`に、分野別の詳細をSkillに分けて生成し、役割ごとのエージェントの定義から必要なSkillだけを読み込ませる |

### F-08：回答の整合性チェック

##### チェック結果の段階

| 段階 | 意味 | CLIの動き |
| --- | --- | --- |
| エラー | 技術的に成り立たない | 理由を示し、選び直してもらう |
| 警告 | 成り立つが、推奨しない | 理由とリスクを示す。そのまま続行できる |
| 情報 | 問題はないが、知っておくべきこと | 表示だけする |

- 警告を承知で続行した場合は、その内容を生成するプロジェクトのADRに自動で記録する（C-35）
- ルールはCLIのプログラムに直接書かず、一覧のデータファイルとして管理し、技術スタックや種別を追加したときにルールを足すだけで済むようにする（C-38）

##### 初回のルール

| # | 条件 | 段階 | 理由 |
| --- | --- | --- | --- |
| 1 | 認証が「アプリ独自認証」または「併用」で、DBが「なし」 | エラー | 利用者の情報を保存する場所がない |
| 2 | ファイルのアップロードを使い、DBが「なし」 | エラー | ファイルの持ち主を記録できず、権限の確認と削除時の後始末（C-63）ができない |
| 3 | ファイルのアップロードを使い、認証が「なし」 | 警告 | 誰でもアップロードでき、いたずらや容量の浪費につながる。公開のファイルとして扱う場合（C-63の公開の手順）に限って成り立つ |
| 4 | 開発人数が「複数人」で、品質チェックの実行場所が「ローカルのみ」 | 警告 | マージの前に、他の人の変更も含めた品質チェックが自動で行われない |
| 5 | リポジトリが「公開」で、品質チェックの実行場所が「ローカルのみ」 | 警告 | 外部からのPRを自動でチェックできない |
| 6 | DBが「PostgreSQL」 | 情報 | 外部のDBサービスの契約が必要になり、D1より構成と費用が増える |
| 7 | バージョンで「最新の安定版」を選び、検証済みより新しい | 警告 | ハーネスでの動作を確認していない（F-19） |
| 8 | このPCに必要なツールがない、またはバージョンが足りない | 警告 | 生成はできるが、そのままでは起動・テストできない。導入手順を表示する（F-19） |
| 9 | アプリ名が命名規則（英小文字・数字・ハイフン）に合わない | エラー | コンテナ名等に使えない（C-36） |
| 10 | 生成先のフォルダが既に存在し、中身がある | エラー | 既存のファイルを上書きしてしまう |

##### 後から追加するルールの例

- モバイルアプリなのに、フロントエンドにWeb専用の技術を選んだ（警告）
- バックエンドにSpring Bootを選び、デプロイ先にCloudflare Workersを選んだ（エラー：Workersでは動かない）

### F-15：コンフリクト防止の手順

`git status`は手元の状態しか分からないため、リモートの最新状態を取得して比較する。

| タイミング | やること | 使うコマンド（例） |
| --- | --- | --- |
| 作業開始前 | リモートの最新状態を取得し、最新の`main`からブランチを作る | `git fetch`、`git switch -c` |
| 作業開始前 | 他の人が同じファイルを触っているオープン中のPRがないか確認する | `gh pr list`、`gh pr diff` |
| push前 | 最新の`main`を取り込み、コンフリクトがないか確認する | `git fetch` → `git merge-tree` |
| マージ前 | PRがコンフリクトなしでマージ可能か確認する | `gh pr view --json mergeable` |

### F-16：技術スタックに応じた品質チェック

- 品質チェックは、フロントエンド共通プロファイルとバックエンド別プロファイルに分け、選択した技術スタックに応じて組み合わせる。
- 品質チェックの実行場所を「ローカルのみ」「GitHub Actions」「ローカルとGitHub Actionsの両方」から選べるようにする。GitHub Actionsを利用できない案件では、ローカルのみを選べる。
- GitHub Actionsを実行場所に選んだ場合は、CIを利用する設定とし、CIの種類はGitHub Actionsに整合させる。ローカルのみを選んだ場合は、品質チェックのためのGitHub Actionsワークフローを生成しない。
- 選んだ実行場所に応じて、ローカル実行用スクリプト、GitHub Actionsワークフロー、または両方を生成する。ローカル実行用スクリプトは、GitHub Actionsを選んだ場合に必ず生成するとは限らない。
- 現時点の候補構成は次のとおりとする。記載したツールは候補であり、確定した採用決定ではない。

| プロファイル | チェック領域 | ツール候補 |
| --- | --- | --- |
| React／TypeScript共通 | Lint・React規約 | ESLint、TypeScript／React用プラグイン |
| React／TypeScript共通 | 型チェック | TypeScript compiler（`tsc`） |
| Hono（TypeScript） | Lint・型チェック・バグ検出等 | フロントエンドと共通のTypeScript系ツール |
| Spring Boot（Java） | Lint・命名・書式・import | Checkstyle |
| Spring Boot（Java） | 型チェック | Java compiler |
| Spring Boot（Java） | バグ・null・並行処理 | SpotBugs |
| Spring Boot（Java） | 複雑度・設計上の問題 | PMD |
| Python | Lint・書式・import・複雑度 | Ruff |
| Python | 型チェック | Pyright |
| 各プロファイル | セキュリティ静的解析 | ツール候補と適用方法は未決定 |

- 静的解析、テスト、ビルドはそれぞれ別のチェック領域として定義する。
- テストには単体テスト・結合テスト・E2Eテストを含める。技術スタックに応じてテストフレームワークと実行方法を定義する。
- テストの設計と信頼性の確保（テストオラクル、要求との照合、ミューテーションテスト、再現性の確認等）はC-25に従う。
- GitHub Actionsを利用する場合、選択した品質チェックをワークフローに反映し、必要なチェックをマージ条件に含める。
- 各ツールの詳細設定（ルールセット、厳しさ、閾値、除外対象、警告とエラーの扱い等）、ツールのバージョン、実行順序、合格条件は、プロファイルごとの設計時に決定する。CLIの質問で個々の設定を利用者に選ばせるか、標準設定を自動生成するかも未決定とする。

### F-17：Superpowers利用案内

- 選択されたAI環境向けの設定ファイルに、C-11のSuperpowers利用フローと適用する場面を反映する。
- READMEにはClaude Code・Codexそれぞれの導入手順、導入後の利用確認方法、プラグインを利用できない場合の対応を記載する。

### F-18：知見の蓄積と配布

経験から来る判断基準（ヒューリスティクス）を、全プロジェクトで参照できるようにする。

#### 貯める

- 知見は、このハーネスのリポジトリの`knowledge/`に、分野別のフォルダ・テーマごとのファイルで置く（例：`knowledge/db/sql-complexity.md`）

```text
knowledge/
├─ frontend/   例：コンポーネントを分割する目安、useMemoを使う目安
├─ backend/    例：Repository／DAOのどちらにするかの目安
├─ db/         例：SQLの書き分け、インデックス設計
└─ general/    分野をまたぐもの。例：共通化するか、しないかの目安
```

- 知見の使い方のルールはC-56に従う
- 知見はハーネスと一緒にバージョン管理し（C-08）、追加・変更はPRで行う
- 1件ごとに、次の項目をそろえて書く。書き方の見本は`knowledge/README.md`に置く

| 項目 | 内容 |
| --- | --- |
| 状態 | 仮説／検証中／確立／廃止（下記） |
| 種類 | 性能／設計 |
| 基準 | 判断のルール |
| 理由 | その基準にした理由 |
| 例外 | 当てはまらない場面 |
| 確かめ方 | 何を、どの道具で測って確かめるか |
| 根拠 | 実測値や、きっかけになった事例（ADRへのリンク等） |
| 対象 | 実測・適用した条件の範囲（DB・ライブラリとバージョン、データ量、実行環境等） |
| 適用の記録 | 適用した日付・プロジェクト・結果を1行ずつ追記する |

- 知見は絶対のルールではない。当てはまらない場面では、C-10と同じく実測に基づいて判断し、その結果を根拠として知見に反映する

#### 知見の種類と確かめ方

| 種類 | 対象の例 | 確かめ方 |
| --- | --- | --- |
| 性能 | SQLの書き方、useMemoの使い方、リストの仮想化、ページング | 知見に従った場合・従わない場合を、同じ条件で実測して比べる（実行計画、再描画の回数と時間、表示速度、応答時間、バンドルサイズ等） |
| 設計 | コンポーネントの分割、共通化の判断、Repository／DAOの構成 | 1回の測定では確かめられないため、代わりの指標（同じ種類の変更で触ったファイル数、不具合の数、複雑度、重複、依存の違反、レビューの指摘の回数等）を、複数のプロジェクト・長い期間で集めて傾向を見る |

- 設計の知見は、証明ではなく「複数の実績で反する結果が出ていない」という確からしさで扱う
- 自動で測れる指標（バンドルサイズ、複雑度、重複、依存の違反、SQLの発行数、実行計画等）は、CIで毎回測って結果をファイルとして保存し、根拠として参照できるようにする
- 具体的な計測の道具は、技術スタック別に定める

#### 実測を根拠として使うときのルール

実測で言えるのは「その条件の下では効率が良い」までであり、ほかの条件でも成り立つとは限らない。実測を根拠にするときは、次を守る。

- **MUST**：実測の結果には、測った条件（データ量、端末・ブラウザ、ライブラリのバージョン、実行環境等）を一緒に記録する
- **MUST**：何を良くしたいのか（速さ・メモリ・通信量・費用等）を、測る前に決める
- **MUST**：「意味のある差」の基準（例：何ms以上の差なら効果ありとするか）を、測る前に決める
- **MUST**：比べる対象どうしは、同じ条件・同じ実行の中で複数回測り、中央値とばらつき（95パーセンタイル等）を記録する。1回だけの結果で判断しない
- **SHOULD**：準備運転（ウォームアップ）の後に測る。起動直後・キャッシュなしの状態の速さを知りたい場合は、分けて測る
- **SHOULD**：実験用の環境の結果に加えて、可能なら本番の実測値（利用者の実際の表示速度等）でも確かめる
- **MUST**：知見の「対象」は、実測した条件の範囲で書く。範囲を広げるには、別の条件での実測を追加する

#### 知見の状態

| 状態 | 意味 | 次の状態へ進む条件 |
| --- | --- | --- |
| 仮説 | 考えとしてはあるが、まだ検証していない | 1つのプロジェクトで適用し、結果を記録した |
| 検証中 | 1件以上の実績がある | 2つ以上のプロジェクトで結果が一致した、または実測データで裏付けられた |
| 確立 | 繰り返し確かめられ、反する結果が出ていない | — |
| 廃止 | 当てはまらない例が多く、使わなくなった | — |

- 状態を変えるときは、根拠（適用の記録・実測データ）を示す
- 廃止した知見は消さずに残し、廃止の理由を書く

#### 配る

- CLIは、選んだ技術スタックに関係する知見だけを、生成するプロジェクトにSkill等の形で出力する
- AIが常に読むルールには含めず、「SQLを書くとき」「インデックスを追加するとき」など、必要な場面でだけ読み込ませる
- 生成済みプロジェクトへの反映方法は、ハーネスの更新方法（Issue #7）で決める

##### 記録するきっかけ

実装の流れの中で、次の場面を知見の記録のきっかけにする。

| きっかけ | 例 | 関係するルール |
| --- | --- | --- |
| 知見に当てはまらない判断をした | 3テーブルのJOINだが、Repositoryに書いた | C-56 |
| 実測の結果が出た | N+1の検証、実行計画、SQLの発行数、表示速度 | C-10 |
| レビューで指摘を受けた | 別のAIから同じ種類の指摘が繰り返される | C-33 |
| 不具合の原因を突き止めた | E2Eテストの失敗を調べて分かった原因 | C-24 |
| 手戻りが起きた | 設計を途中でやり直した | — |

##### 記録の方法

- **MUST**：生成するプロジェクトのPRテンプレートに「知見」の欄を設け、PRごとに必ず記入する。AIがPRを作るときも必ず記入する。該当しない項目は「なし」と書く
  - 参照した知見
  - 当てはまらなかった知見と、その理由・根拠
  - 新しい気づき（知見の候補）
- 大きな判断や実測の詳細は、そのプロジェクトのADR（C-35）に記録し、PRからリンクする
- 個人の下書き（`tech-notes`等）に残した知見も、固まったものは同じ流れでハーネスへ移す

##### 見直し

- 次の2つのタイミングで、知見を見直す
  - ハーネスの新しいバージョンを出すとき
  - 月に1回
- 見直しでは、AIが各プロジェクトのPRの「知見」の欄・ADR・CIに保存した計測結果を集め、次の案を出す
  - 知見の状態を進める・廃止する
  - 新しい知見を登録する
  - 既存の知見の「対象」「例外」を更新する
- 知見の登録・状態の変更は、AIが勝手に行わず、人の承認を得てからハーネスへPRで反映する

### F-19：バージョンの調査と選定理由の記録

##### 目的

最新の安定版などを調べたうえで採用するバージョンを決め、**なぜそのバージョンにしたかを明確にする**。決めたバージョンはC-62に従って固定する。

##### 流れ

1. 質問では技術（React・Hono等）だけを選び、バージョンは聞かない
2. CLIが、選んだ技術のバージョンを調べる
   - ライブラリ・ツール：最新の安定版（開発版・試験版は選ばない）
   - Node.js等の実行環境：長期サポート版（LTS）
   - あわせて、ハーネスのリリースごとに動作を確認した**検証済みのバージョン**を示す
3. このPCで必要なツール（Node.js・Docker・wrangler等）が使えるか、バージョンが足りているかを確認する。足りない場合は導入手順を表示する（CLIが勝手にインストールしない）
4. 検証済みのバージョンと最新の安定版を並べて表示し、どちらを採用するか選ばせる。最新の安定版が検証済みより新しい場合は、「動作を確認していない」という注意書きを出す（F-08と同じく、止めずに警告だけ出す）
5. 決まったバージョンの一覧を表示し、承認されてから生成する

##### 記録

- 生成するプロジェクトの`docs/tech-stack.md`に、技術ごとに次を記録する
  - 採用したバージョン
  - 選定理由（例：「2026-09-29時点の最新の安定版」「ハーネス検証済み」「LTS」）
  - 調べた日と、そのとき確認した最新の安定版・検証済みのバージョン
- 以後のバージョンの更新は、C-62の手順で行い、同じ文書を更新する

### 認証・認可・セキュリティ関連

| 用語 | 意味 |
| --- | --- |
| 認証 | 「あなたは誰か」を確かめること。ログインが代表例 |
| 認可 | 「あなたはこの操作をしてよいか」を判定すること。認証の後に行う |
| デフォルト拒否 | 明示的に許可したもの以外は、すべて拒否する考え方 |
| ロール | 「管理者」「編集者」など、権限をまとめた役割 |

| OIDC | OpenID Connect の略。IdPを使って安全にログインするための標準の仕組み |
| セッション | ログインしてからログアウトするまでの「ログイン中」という状態を、サーバーとブラウザで保持する仕組み |
| アクセストークン | APIを呼び出すときに提示する「通行証」。有効期間を短くする |
| リフレッシュトークン | 期限切れになったアクセストークンを新しく発行してもらうための、長めの有効期間を持つ引換券 |
| ローテーション | リフレッシュトークンを使うたびに新しいものへ交換し、古いものを使えなくすること |
| BFF | Backend For Frontend の略。画面専用の中継サーバー。トークンをブラウザに持たせずに済む |
| MFA | 多要素認証。パスワードに加えて、スマホのコードなど別の要素でも本人確認すること |
| 再認証（step-up authentication） | ログイン中でも、重要な操作の直前にもう一度本人確認を求めること |
| XSS | クロスサイトスクリプティング。悪意のあるスクリプトを画面に埋め込ませ、他の利用者のブラウザで実行させる攻撃 |
| CSP | Content Security Policy。ブラウザに「このサイトで実行してよいスクリプトの出どころ」を伝えるヘッダー。XSSの被害を抑える |
| サニタイズ | 入力の中から危険な部分を取り除いたり無害化したりすること |
| 例外 | プログラムの実行中に起きたエラーを知らせる仕組み。受け止めない（`catch`しない）と、呼び出し元へ伝わっていく |
| グローバル例外ハンドリング | 処理しきれなかったエラーを、アプリ全体で1か所にまとめて受け止め、ログと応答をそろえる仕組み |
| エラーのもみ消し | エラーを受け止めて何もしない、または成功したように見せかけること |
| Axios | JavaScriptでHTTP通信を行うためのライブラリ |
| インターセプター | すべての要求・応答の前後に、共通の処理を挟む仕組み |
| 許可リスト | 使ってよい値の一覧。一覧にない値はすべて拒否する |
| SQLインジェクション | 入力にSQLの一部を紛れ込ませ、意図しないDB操作をさせる攻撃 |
| CSRF | クロスサイトリクエストフォージェリ。利用者がログイン中のサイトに対し、別のサイトから勝手に操作の要求を送らせる攻撃 |
| SameSite | Cookieの属性。別サイトからの要求にCookieを付けるかを決める。`Strict`・`Lax`・`None`がある |
| Origin | 「スキーム＋ドメイン＋ポート」の組（例：`https://example.com`）。要求の送信元を表すヘッダーとしても使われる |
| CORS | Cross-Origin Resource Sharing。別のOriginの画面から、APIを呼び出すことを許可する仕組み |
| preflight | CORSで、本番の要求の前にブラウザが`OPTIONS`で「この要求を送ってよいか」を確認する事前の問い合わせ |
| 安全なメソッド | GET・HEADなど、サーバーの状態を変えないと決められているHTTPメソッド |
| HSTS（`Strict-Transport-Security`） | ブラウザに「このサイトには常にHTTPSで接続する」と覚えさせるヘッダー |
| クリックジャッキング | 自分のサイトを透明にしてほかのサイトに埋め込み、利用者に意図しない操作をさせる攻撃 |
| 429 | 「要求が多すぎる」ことを示すHTTPステータスコード。`Retry-After`で再試行してよい時期を伝える |
| レート制限 | 一定時間内に試せる回数を制限すること。パスワードの総当たりを防ぐ |
| OWASP ASVS | Webアプリのセキュリティ要件を一覧にした国際的なチェックリスト。求める厳しさに応じてレベル1〜3がある |
| 個人情報保護法 | 個人情報を扱う事業者が守るべき日本の法律 |

### HTTP・通信関連

| 用語 | 意味 |
| --- | --- |
| HTTPステータスコード | サーバーが返す3桁の結果番号。`200`は成功、`404`は見つからない、`500`はサーバーの内部エラーなど |

| OpenTelemetry | ログ・計測データの項目名や送り方を定めた、特定の製品に依存しない業界標準 |
| 監査ログ | ログインや権限変更など、「誰が何をしたか」を後から確認するための記録 |
| ログインジェクション | 入力に改行などを紛れ込ませて、偽のログ行を書き込む攻撃 |
| 標準出力 | プログラムが結果を書き出す標準の出口。実行環境がこれを集めてログとして保存する |
| オブジェクトストレージ | ファイルを大量に安く保存できるサービス。Cloudflare R2・Amazon S3など |
| Docker Compose | 複数のDockerコンテナ（バックエンド・DB等）を、1つの設定ファイルでまとめて起動する仕組み |
| ロールバック（切り戻し） | 不具合が出たときに、前の正常なバージョンに戻すこと |
| Blue-Greenデプロイメント | 本番と同じ環境をもう1つ用意して新バージョンを置き、切り替えで入れ替える方法。問題があればすぐ元に戻せる |
| カナリアリリース | 新バージョンを一部の利用者だけに先に公開し、問題がないことを確かめながら広げる方法 |
| 後方互換性 | 新しい変更を入れても、古いバージョンがそのまま動くこと |
| 破壊的変更 | カラムの削除など、古いバージョンが動かなくなる変更 |
| Time Travel | Cloudflare D1の機能。過去の時点のDBの状態に戻せる |
| ブランチ保護 | GitHubの設定で、特定のブランチへの直接のpushなどを禁止する仕組み |
| IaC | Infrastructure as Code。サーバーやDBなどの環境を、手作業ではなくコードで作る方法 |
| Terraform | 代表的なIaCのツール。コードに書いた環境を作成・変更し、実際の環境との差分も確認できる |
| 状態ファイル（tfstate） | Terraformが「今どんな環境を作ったか」を記録するファイル。秘密情報を含み得る |
| メンテナンス性 | 後から読みやすく、直しやすく、変更しても壊れにくいこと |
| wrangler | Cloudflare Workersの開発・デプロイ用のツール。ローカルでWorkersやD1を再現して動かせる |
| workerd | Cloudflare Workersの実行エンジン。本番と同じものがローカルでも動く |
| ボリューム | Dockerコンテナを作り直しても消えないように、データを保存しておく場所 |
| リクエストID | 1つのリクエストに振る識別番号。関係するログをまとめてたどるために使う |
| RFC 9110 | HTTPの意味（ステータスコード等）を定めた標準仕様 |
| アプリケーションエラーコード | HTTPステータスとは別に、アプリが独自に決める細かいエラーの識別番号 |
| キャッシュ | 一度取得したデータを近くに保存しておき、次回の取得を速く・安くする仕組み |
| CDN | Content Delivery Network の略。画像などを利用者の近くのサーバーから配信する仕組み |

### Git・GitHub関連

| 用語 | 意味 |
| --- | --- |
| Issue | GitHub上の「やることリスト」の1項目。作業内容や完了条件を書く |

| 親Issue・子Issue | 大きな作業（親）を、小さな作業（子）に分けて管理する仕組み。GitHubでは子Issueを「sub-issue」と呼ぶ |
| ブランチ | 本流（`main`）から枝分かれした作業場所。他の作業に影響を与えずに変更できる |

| モノレポ | フロントエンド・バックエンドなど複数の部分を、1つのリポジトリで管理する構成 |
| CI | Continuous Integration の略。PRを作るたびにテスト・Lint・ビルドを自動で実行する仕組み。GitHub Actionsが代表例 |
| セマンティックバージョニング | `MAJOR.MINOR.PATCH`の3つの数字で、変更の大きさが分かるようにバージョンを付けるルール |

### バックエンドの層

| 用語 | 意味 |
| --- | --- |
| 層（レイヤー） | プログラムを役割ごとに分けたまとまり。1つの層は1つの役割だけを持つ |
| 責務の分離 | 1つのクラス・ファイルに複数の役割を持たせないこと。どこに何が書いてあるか分かりやすくなる |
| Controller | 外部からのリクエストを受け取り、結果を返す窓口 |
| Service | 業務のルール（計算・判定など）を実行する層 |
| Repository／DAO | DBへの読み書きを担当する層。DAOは Data Access Object の略 |
| DTO | Data Transfer Object の略。層の間やAPIでデータを運ぶための入れ物 |
| Entity | DBのテーブルの1行に対応するデータ |
| Mapper | EntityとDTOを相互に変換する部分 |
| ORM | Object-Relational Mapping の略。SQLを書かずに、プログラムのオブジェクトとしてDBを操作できる仕組み。JPA・Prismaなど |
| SQLマッパー | 自分で書いたSQLの結果を、プログラムのオブジェクトに対応づける仕組み。MyBatisなど |
| プロジェクション | DBから必要な列だけを取り出すこと。不要なデータを読まずに済む |
| マイグレーション | DBのテーブル構造の変更を、ファイルとして順番に記録・適用する仕組み |
| Flyway | DBのマイグレーションを管理する代表的なツール。番号付きのSQLファイルを順番に適用し、適用済みの記録をDBに残す |
| スキーマ | DBのテーブル・カラム・インデックスなどの構造の定義 |
| トランザクション | 複数のDB操作を「全部成功」か「全部取り消し」のどちらかにまとめる仕組み |
| Drizzle ORM | TypeScript用のDBライブラリ。SQLに近い書き方ができ、D1とPostgreSQLの両方に対応している |
| 生SQL | ライブラリの書き方を使わず、SQL文をそのまま書くこと |
| 集計関数 | `SUM`・`COUNT`・`AVG`など、複数の行をまとめて1つの値にする関数 |
| ウィンドウ関数 | 行をまとめずに、順位や前の行との差などを計算する関数（`ROW_NUMBER`・`LAG`等） |
| CTE（`WITH`句） | SQLの中で、名前を付けた中間結果を作ってから使う書き方。再帰CTEは親子関係をたどるのに使う |
| べき等性 | 同じ処理を何回実行しても、結果が同じになる性質 |
| 楽観的ロック | 更新の衝突を、保存するときにバージョン番号などで検知する方法 |
| チャンク | 大量のデータを処理するときに、小分けにした1つのまとまり |
| Cron Triggers | Cloudflare Workersを決まった時刻に起動する機能 |
| Queues | Cloudflareの、処理を小分けにして順番に実行するための仕組み |
| Workflows | Cloudflareの、途中で失敗しても再開できる複数の手順からなる処理の仕組み |
| CRUD | Create（作成）・Read（取得）・Update（更新）・Delete（削除）の基本的な4つの操作 |
| ドメインモデル | 業務の概念（注文・会員など）をそのまま表したクラス。DBのテーブル構造とは必ずしも一致しない |
| N+1問題 | 一覧を1回取得した後、各行ごとに追加のSQLを1回ずつ発行してしまい、SQLの回数が件数に比例して増える問題 |
| インデックス | DBの「索引」。検索を速くするが、書き込みが遅くなり容量も使う |
| 実行計画 | DBがSQLをどういう手順で処理するかの予定表。`EXPLAIN`で確認できる |
| 全件走査 | インデックスを使わず、テーブルの全行を読んで検索すること |

### フロントエンドの層

| 用語 | 意味 |
| --- | --- |
| Pages | URLごとの画面 |
| Components | ボタンや入力欄など、画面を組み立てる部品 |

| 状態管理 | 画面に表示するデータを、どこで保持し、どう更新するかの管理 |
| Props | 親コンポーネントから子コンポーネントへ渡すデータ |

| TanStack Query | Server Stateの取得・キャッシュ・更新を管理するライブラリ |
| Zustand | 複数の画面で共有する状態を管理する、軽量なライブラリ |
| Zod | データの形をスキーマとして定義し、実行時に検証できるライブラリ。TypeScriptの型も作れる |
| React Hook Form | フォームの入力値や入力チェックを扱うライブラリ |
| Error Boundary | 画面の一部でエラーが起きたとき、画面全体を壊さずに代わりの表示を出すReactの仕組み |
| 型ガード | 値が特定の型かどうかを実行時に確かめ、TypeScriptに型を伝える書き方 |
| `strict` | TypeScriptの厳しい型チェックをまとめて有効にする設定 |
| 仮想化（virtualization） | 大量のリストのうち、画面に見えている部分だけを描画して軽くする方法 |
| Testing Library | 利用者の操作（クリック・入力等）に近い形でコンポーネントをテストするライブラリ |
| アクセシビリティ | 障害の有無や利用環境にかかわらず、誰でも使えるようにすること |
| ファビコン | ブラウザのタブなどに表示される、サイトの小さなアイコン |
| Web App Manifest | アプリ名やアイコンなど、Webアプリをホーム画面に追加するときの情報を書くファイル |

### テスト・環境関連

| 用語 | 意味 |
| --- | --- |
| 単体テスト | 関数やクラス1つ単位で動作を確かめるテスト |
| 結合テスト | 複数の部品を組み合わせて動作を確かめるテスト。APIからDBまで通すなど |
| E2Eテスト | End to End の略。実際にブラウザを操作して、画面からDBまで通しで確かめるテスト |
| ブラックボックステスト | 中身を見ずに、仕様どおりの入力と出力になるかで確かめるテスト |
| ホワイトボックステスト | コードの構造（分岐など）を見て、すべての経路を通るように作るテスト |
| テストオラクル | テストの「正解」を決める根拠。仕様書や、別の方法で計算した結果など |
| サンドボックス | 外部サービスが用意している、本番に影響しないテスト用の環境 |
| mock・fixture | mockはテスト用の偽物の部品、fixtureはテスト用にあらかじめ用意するデータや状態 |
| ミューテーションテスト | コードをわざと少し壊して、テストがそれを見つけられるかを確かめる、テスト自体の検査 |
| Core Web Vitals | Googleが公開している、Webページの利用体験を測る3つの指標（LCP・INP・CLS） |
| パーセンタイル | 値を小さい順に並べたときの位置。75パーセンタイルは「全体の75%がこの値以下」という意味 |
| p95 | 95パーセンタイル。遅い方の5%を除いた中で一番遅い値 |
| Prettier | コードの書式（インデント・改行等）を自動でそろえるツール |
| Playwright | ブラウザを自動で操作してE2Eテストを行うツール |
| Appium | iOS・Androidのモバイルアプリを自動で操作してテストするツール |
| エミュレーター・シミュレーター | PC上でスマートフォンを再現して、モバイルアプリを動かす仕組み |
| Chrome DevTools | Chromeに組み込まれた開発者向けの調査機能。コンソール・通信・性能などを確認できる。AIからも操作できる |
| ポートの競合 | 同じポート番号を複数のプログラムが使おうとして、後から起動したものが動かなくなること |
| Orcaブラウザ | AIの作業環境Orcaに組み込まれたブラウザ。AIが画面を操作し、表示・コンソール・通信を確認できる |
| トレース | Playwrightがテスト中の操作・画面・通信を記録したもの。失敗時に後から再生して調べられる |
| 不安定なテスト（flaky test） | 同じ条件でも成功したり失敗したりするテスト |
| シード | テストや開発用に、DBへ最初に入れておくデータ |
| Lint | コードの書き方の誤りや規約違反を自動で見つけるツール |
| `.env` | パスワード等の秘密情報を書くファイル。GitHubには上げない |
| `.env.example` | `.env`の書き方の見本。実際の値は書かずにGitHubへ上げる |
| Docker | アプリやDBを「コンテナ」という箱に入れて、どのPCでも同じ環境で動かせる仕組み |
