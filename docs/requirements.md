| 項目 | 内容 |

| バージョン | なし（ハーネスの初回完成時に`0.0.0`を付ける） |

文書中の専門用語は、末尾の「付録：用語集」で説明している。

## 1. プロジェクト概要

| 項目 | 内容 |
| --- | --- |
| プロジェクト名 | ハーネス設計 |
| 目的 | AIが機能を実装するときに、構成・実装方法・GitHubフロー・テスト機構などがブレないようにする |
| 想定ユーザー | 本人と身内（少人数・内部利用） |
| 成果物の形 | **CLIツール**。コマンドを実行して質問に答えると、ハーネス一式（AI向け設定ファイル・ルール・テンプレート等）が生成される |
| 実装言語 | **TypeScript（Node.js）**。`npx`で実行できる形で配布する |

### 成果物の形をCLIツールにした理由

- AIがなくても動き、同じ回答なら毎回同じハーネスが生成される（AIによるブレをなくすというこのプロジェクトの目的に合う）
- 質問の分岐・整合性チェックのルールがコードとして明文化される

### 進め方の方針

- 最初は言語に依存しない**共通部分**から決める
- 言語ごとの差分は、共通部分が固まってから追加する

### スコープ外事項

- 現時点ではなし

## 2. 共通仕様（全プロジェクトに適用するルール）

全プロジェクトに適用する設計・開発のルール。多くは対話で質問しない固定ルールだが、C-12（認証方式）のように、CLIの質問で選んだ内容に応じて適用範囲が変わるものも含む。

番号（C-xx）は項目の識別子であり、見出しの中では番号順に並ばない。項目を追加するときは、次の番号を振って該当する見出しに入れる。

### 2.1 開発フロー・GitHub運用

| ID | 内容 |
| --- | --- |
| C-01 | 開発フローは**Issue駆動**とする |
| C-07 | Issueは**親Issue＋子Issue**の構成にする。親Issueで「何を作るか」を定義し、子Issueで「そのために何が必要か」を作業領域ごとに分ける |
| C-21 | ブランチ名は `<種類>/<Issue番号>-<内容>` の形式にする |
| C-22 | コミットメッセージは Conventional Commits（種類は英語、説明は日本語）に従う |
| C-23 | PRには `Closes #<子Issue番号>` を書き、Squashでマージする |
| C-08 | バージョンは**セマンティックバージョニング**（`MAJOR.MINOR.PATCH`）で管理する。初回完成時に`0.0.0`を付け、それまではバージョンを上げない |
| C-11 | Claude Code・Codexを使う開発では、Superpowersの設計・計画・実装・レビューのワークフローを適用する |

#### C-07：Issueの分け方

1つの機能・1つの文書を**親Issue**とし、必要な作業を**子Issue**（GitHubのsub-issue）に分ける。子Issueごとにブランチ・PRを作成し、親Issueは全体の進み具合と完了条件を管理する。

##### 機能実装の場合

| 階層 | 内容 | 例 |
| --- | --- | --- |
| 親Issue | 実装する機能と、その完了条件 | ログイン機能を実装する |
| 子Issue | 機能に必要な作業を、作業領域ごとに分けたもの | 下表を参照 |

| 作業領域 | 子Issueにする条件 | 例 |
| --- | --- | --- |
| DB | テーブル・カラムの追加や変更がある | ユーザーテーブルのマイグレーション |
| バックエンド | APIや業務ロジックの追加・変更がある | ログインAPI（Controller／Service／Repository） |
| フロントエンド | 画面や部品の追加・変更がある | ログイン画面（PasswordFieldを含む） |
| その他 | CI・インフラ・設定の変更がある | 認証用の環境変数の追加 |

- 必要のない作業領域の子Issueは作らない（例：画面のないAPIのみの機能ではフロントエンドの子Issueを作らない）
- 子Issueの間に依存関係がある場合は本文に明記する（例：バックエンドのIssueはDBのIssueの完了後に着手する）
- 各子Issueには、その作業領域での完了条件を書く

##### 文書作成の場合

親Issueを文書全体とし、子Issueを章（タイトル）ごとに分ける。この要件定義書もこの方式で管理する（親Issue #1）。

#### C-21：ブランチ名

`<種類>/<Issue番号>-<内容>` の形式にする。内容は英小文字とハイフンで短く書く。

| 種類 | 使うとき | 例 |
| --- | --- | --- |
| `feature` | 機能の追加 | `feature/12-login-api` |
| `fix` | 不具合の修正 | `fix/15-password-toggle` |
| `docs` | 文書の追加・修正 | `docs/3-common-spec` |
| `refactor` | 動作を変えないコードの整理 | `refactor/20-split-user-service` |
| `chore` | 設定・依存関係・CIなどの変更 | `chore/8-add-eslint` |

#### C-22：コミットメッセージ

Conventional Commits に従い、`<種類>: <説明>` の形式にする。種類は英語、説明は日本語で書く。

| 種類 | 使うとき | 例 |
| --- | --- | --- |
| `feat` | 機能の追加 | `feat: ログインAPIを追加` |
| `fix` | 不具合の修正 | `fix: パスワード表示トグルが動かない問題を修正` |
| `docs` | 文書のみの変更 | `docs: 共通仕様にブランチ名のルールを追加` |
| `refactor` | 動作を変えないコードの整理 | `refactor: UserServiceを分割` |
| `test` | テストの追加・修正のみ | `test: ログインAPIの認可テストを追加` |
| `chore` | 設定・依存関係・CIなどの変更 | `chore: ESLintを導入` |

- 以前の内容と両立しない変更には、種類の後ろに`!`を付ける（例：`feat!: APIのレスポンス形式を変更`）。初回完成後は、C-08のバージョンを上げる判断に使う

#### C-23：PR

- 本文に `Closes #<子Issue番号>` を書き、マージと同時に子Issueが自動でクローズされるようにする。親Issueは `Refs #<親Issue番号>` で参照し、クローズしない
- マージは **Squash** で行い、PR1つが`main`上のコミット1つになるようにする。Squash後のコミットメッセージもC-22に従う
- マージ前に、C-24のテストと品質チェック（F-16）が通っていることを確認する

#### C-08：バージョンの付け方

##### 初回完成まで

- バージョンは付けない。Issueを解決しても、バージョンは上げない
- ハーネスが一通り完成した時点で`0.0.0`を付ける

##### 初回完成後

| 桁 | 上げるとき | 例 |
| --- | --- | --- |
| MAJOR | 以前の内容と両立しない大きな変更をしたとき | `0.4.2` → `1.0.0` |
| MINOR | 項目の追加・仕様の決定など、内容が増えたとき | `0.0.3` → `0.1.0` |
| PATCH | 誤字の修正・表現の調整など、意味が変わらない修正をしたとき | `0.1.0` → `0.1.1` |

- 下の桁は、上の桁を上げたときに`0`へ戻す
- 要件定義書と、ハーネスが生成するプロジェクト・CLIツール本体のすべてに同じルールを適用する

#### C-11：Superpowersを使ったAI開発フロー

- Claude CodeまたはCodexを利用する開発では、Superpowersプラグインを利用可能な状態にする。プラグインは各AI環境に個別に導入する。
- 要件整理・設計では`brainstorming`を使い、ユーザーへの質問、選択肢とトレードオフの整理、合意した設計の記録を行う。設計の合意前に実装へ進まない。
- 設計合意後は`writing-plans`で作業を実行可能な単位へ分解し、実装では`test-driven-development`、`requesting-code-review`、`verification-before-completion`等の該当スキルを使う。
- Superpowersの手順・成果物は日本語を基本とし、スキル名やコマンド名は識別できるよう原文のまま記載してよい。
- プラグインが利用できない場合は、その旨をユーザーに伝え、必要な導入手順を案内する。プラグインを前提とする作業を、利用できないまま黙って進めない。
- プラグインの導入はユーザーのAI環境に対して行い、生成したアプリケーションの実行時依存には含めない。プラグインを自動インストールするスクリプトは生成しない。
- Superpowersの指示は、ユーザーの指示とプロジェクト固有ルールに従う。

### 2.3 バックエンド

| ID | 内容 |
| --- | --- |
| C-03 | バックエンドは**責務の分離を徹底**し、決められた層に分ける |
| C-04 | データアクセス層は**必要最低限の列だけをDTOで取得する**。Entityを丸ごと取得して画面やAPIに渡すことを禁止する |
| C-10 | バックエンドのDBアクセスと静的メディア配信は、不要なアクセス・転送を避けつつ、正確性・安全性・実測した費用を踏まえて設計する |

#### C-03：バックエンドの層構成

層の分け方と責務は言語共通とし、ディレクトリ名や使うライブラリだけを言語ごとの差分とする。

| 層 | 責務 | してはいけないこと |
| --- | --- | --- |
| Controller | リクエストの受付・入力チェック・レスポンスの返却 | 業務ロジックを書く、データアクセス層を直接呼ぶ |
| Service | 業務ロジック・トランザクション管理 | HTTPに関する処理を書く |
| Repository | Serviceから見たデータの出し入れ。DBの実装方式をServiceから隠す | 業務ロジックを書く |
| DAO | SQLの実行に専念する（下記の条件に当てはまる場合のみ置く） | 業務ロジックを書く、Serviceから直接呼ばれる（Repositoryを置く構成の場合） |
| DTO | 層の間・API間でやり取りするデータの入れ物 | ロジックを持つ |
| Entity | DBのテーブルに対応するデータ | Controllerより外（画面・API）に出す |
| Mapper | Entity ⇔ DTO の変換 | 変換以外の処理を書く |

##### RepositoryとDAOの使い分け

一律に決めず、状況に応じて構成を選ぶ。

| 状況 | 構成 |
| --- | --- |
| 単純なCRUDのみ | Service → Repository（DAOは作らない） |
| 複雑なSQLだけを扱う | Service → DAO |
| ドメインモデルとDBモデルを分離したい（クライアントの要望等） | Service → Repository → DAO |
| 複数のDAOをまとめて1つのデータとして扱いたい | Service → Repository → 複数のDAO |
| DBの実装方式をServiceから隠したい | Service → Repository → DAO |

- 同じ機能の中で、単純なCRUDと複雑なSQLが混在する場合は、機能ごとに上表から選ぶ
- どの構成を選んだかと、その理由を設計（Issueや計画）に記録する

#### C-10：DBアクセスと静的メディア配信の効率

- DBアクセスはN+1問題を避け、ユースケースで必要なデータを把握したうえで、JOIN、まとめて取得するクエリ、バッチ取得などから適切な方法を選ぶ。必要な列だけを取得するC-04を守る。
- DBへの往復を減らすことを意識する。ただし、通信回数を減らすためだけに巨大で複雑なSQLへ一本化してはならない。ページング、取得件数、JOINによる行数の増加、読みやすさと保守性を考慮して設計する。
- 一覧・検索などN+1が起こりやすい代表的な処理では、実行SQL数や取得件数を確認して検証する。
- N+1の検証では、同一条件で親データの件数を変えて代表APIまたは画面操作を実行し、SQL発行数とSQL内容を収集する。件数の増加に対してSQL発行数が線形に増加していないことを確認する。ページング用の件数取得やバッチ取得など、増加に合理的な理由がある場合は記録してレビューする。
- 検索・一覧・結合を行う代表的な処理では、実運用を想定したテストデータで実行計画（`EXPLAIN`またはDBごとの同等機能）を取得し、絞り込み、結合、並び順、取得件数に対して適切なインデックスが利用できるかを確認する。不要な全件走査、大量の行読み込み、不要なソート、重複したインデックスなどの兆候を検出した場合は、警告または品質チェックの失敗として扱う。
- N+1検証と実行計画・インデックス確認は、テスト用DBの初期状態から自動実行できるDBアクセス回帰テストとして生成し、選択した実行場所に応じてローカルまたはCIで実行する。SQL発行数の計測、実行計画の取得と解析、結果の判定は技術スタック・DB別の実装にする。
- 全件走査やインデックス未使用を一律に不具合と断定してはならない。テーブル規模、データ分布、選択性、更新コスト、ストレージ容量、実行時間などを根拠に、実行計画と実測値をレビューして最終判断する。

##### インデックス設計方針

- インデックスは、実際に想定する検索条件（`WHERE`）、結合条件（`JOIN`）、並び順（`ORDER BY`）、一意性制約およびアクセス頻度を根拠に設計する。根拠のない一律付与や、問題が起きてからの場当たり的な追加はしない。
- 複合インデックスは、対象クエリの絞り込み条件と並び順に合わせて列の順序を設計する。単一列インデックスを複数作れば同じ効果になるとはみなさない。
- 主キー・一意性制約・外部キー参照のためのインデックスは、DBの自動作成の有無と、結合・削除・更新時のアクセスパターンを確認して判断する。
- 似た役割の重複インデックス、使用されないインデックス、選択性が低く効果の乏しいインデックスは追加しない。インデックス追加時は、読み取り性能だけでなく、書き込み性能、ストレージ使用量、バックアップ・移行時間への影響も評価する。
- インデックスの追加・変更・削除は、スキーマ変更としてマイグレーションに含める。各変更には、対象クエリ、想定データ量、期待する改善、実行計画または計測結果を記録する。
- 検索・結合・並び順を変更する機能では、既存インデックスの妥当性を再確認する。利用規模やデータ分布が大きく変化した場合も、実測値に基づいて見直す。

- 画像・動画などの静的メディアは、更新頻度、再利用可能性、アクセス制御を考慮して、ブラウザーキャッシュやCDNキャッシュを利用する。キャッシュの利用は利用者への転送をなくすものではなく、オリジンストレージやアプリへの再取得を減らすための手段として扱う。
- 認証が必要なデータや個人向けのデータを、他者が取得できる共有キャッシュに保存してはならない。HTTPキャッシュ制御は、データの公開範囲と更新要件に応じて設定する。
- キャッシュの導入・保持・削除を一律のコスト削減策として扱わない。アクセス量、転送量、キャッシュヒット率、ストレージ・CDN・アプリの各費用と負荷を実測して判断する。
- 具体的な取得方法、インデックス、キャッシュ期間、配信構成、費用基準および計測方法は、技術スタック、DB、クラウド・ストレージサービス、利用規模を決定した後に、技術スタック別の設計として定める。SQL発行数の上限、テストデータ量、実行計画の警告・失敗基準も同時に決定する。

#### C-06：フロントエンドの層構成

| 層 | 責務 | してはいけないこと |
| --- | --- | --- |
| Pages（画面） | URLに対応する画面。必要な部品とロジックを組み合わせる | APIを直接呼ぶ、細かい見た目を直接書き込む |
| Components（部品） | 見た目の表示。受け取ったデータを表示し、操作をイベントとして親に伝える | APIを呼ぶ、業務ロジックを持つ |
| Hooks／状態管理 | 画面の状態管理、API呼び出し結果の保持、画面側のロジック | 見た目（HTML・スタイル）を持つ |
| API（通信） | バックエンドとの通信。HTTP処理はここに集約する | 画面の状態を持つ |
| Types（型） | APIのリクエスト・レスポンスの型。バックエンドのDTOと対応させる | ロジックを持つ |
| Utils（共通処理） | 日付の整形など、画面に依存しない純粋な処理 | 状態やAPI呼び出しを持つ |

データの流れは **Pages → Hooks → API → バックエンド** の一方向とし、Componentsは表示に専念させる。Webアプリ・モバイルアプリの両方で同じ考え方を使う。

### 2.5 品質チェック・テスト

| ID | 内容 |
| --- | --- |
| C-24 | 単体テスト・結合テスト・E2Eテストは、該当する場合はすべて必須とする |
| C-25 | テストは要求に基づいて設計し、テストを通すこと自体を目的にしない。検出力と再現性を確認する |

#### C-24：テストの必須範囲

次の3種類のテストを、**該当する場合はすべて必須**とする。

| テスト | 必須になる条件 | 対象 |
| --- | --- | --- |
| 単体テスト | 常に必須 | Service・Mapper・Hooks・Utilsなどのロジック |
| 結合テスト | バックエンドがある場合 | ControllerからDBまで通したAPIの動作（認可・エラー応答を含む） |
| E2Eテスト | フロントエンド（Web画面またはモバイルアプリ）がある場合 | 画面からバックエンドまで通した主要な利用の流れ（ログイン等） |

- 「該当しない」と判断して省略する場合は、その理由をIssueまたはPRに記録する
- テストの設計はC-25、ツールと実行方法はF-16に従う

##### E2Eテストの実行と不具合調査

E2Eテストのツールは、画面の種類によって使い分ける。

| 画面の種類 | ツール | 理由 |
| --- | --- | --- |
| Web画面 | **Playwright** | 主要ブラウザを操作でき、トレース等の調査機能がそろっている |
| モバイルアプリ | **Appium** | iOS・Androidの両方に対応して汎用性が高く、複雑な操作のテストも行える |

Webとモバイルの両方がある場合は、それぞれのツールでテストする。

###### Web画面の不具合調査

- E2Eテストが失敗した場合や、動作の不具合が見つかった場合は、**Orcaブラウザ**で同じ操作を再現して動作を確認し、エラーの原因を突き止める
  - 画面の表示・コンソールのエラー・通信（リクエストとレスポンス）を確認し、原因がフロントエンド・バックエンド・テストコード・テストデータのどこにあるかを切り分ける
  - 原因を特定してから修正する。原因が分からないままテストの待ち時間を延ばす・再試行させる・期待結果を変える等でテストを通してはならない（C-25）
  - 突き止めた原因と修正内容をIssueまたはPRに記録する
- Orcaを使えない環境では、Playwrightのトレース・スクリーンショット・画面表示ありの実行（headed）で代わりに調査する

###### モバイルアプリの不具合調査

- エミュレーター・シミュレーター（または実機）で同じ操作を再現し、Appiumのログ・画面の要素の状態・アプリのログ・通信を確認して原因を切り分ける
- 原因を特定してから修正すること、原因と修正内容を記録することは、Web画面と同じとする
- 具体的な調査ツール（Appium Inspector等）と実行環境は、モバイルの技術スタックを決めるときに定める

#### C-25：テストの設計と信頼性

- テスト設計では、外部仕様や入出力に基づくブラックボックステストと、実装構造や制御の流れに基づくホワイトボックステストの両方を参照し、テスト対象と目的に応じて使い分ける。テストレベルとテスト設計技法を一対一には固定しない。
- 各テストでは、テスト対象・観点・入力または前提条件・期待結果を明確にする。期待結果はテストオラクル（仕様、受け入れ条件、独立して算出した結果、信頼できる参照データ等）に基づいて定め、本番実装と同じ処理から導出しない。期待する振る舞いを決められないほど要求が曖昧な場合は、テストを作り込む前に要求を明確にする。
- テスト実行前に、実装対象のIssueや受け入れ条件などの要求とテストケースを照合し、要求された振る舞いをテストが検証していること、テストのない要求がないことを確認する。各テストには要求・設計・不具合の再発防止などの目的を持たせる。対応に漏れや曖昧さがあれば、解消してからテストを実行する。
- 要求とテストの対応は追跡可能な形で記録する。自動化ツールは対応関係の記録や未対応項目の検出に使えるが、テスト内容が意図した振る舞いを正しく検証しているかは、要求・テスト内容をレビューして判断する。
- テストを通すこと自体を目的に、本番コードを要求と異なる振る舞いに変更したり、テストを無効化・スキップしたり、アサーションや期待結果を根拠なく弱めたり変更したりしてはならない。テストが失敗した場合は、要求に照らして実装とテストのどちらに問題があるかを確認し、根拠に基づいて修正する。
- テスト用のfixture・mock・依存注入などは利用できるが、検証対象の機能を通らないテスト専用分岐を本番コードに追加するなど、テスト結果だけをよく見せる変更をしてはならない。テストが成功していることとは別に、実装が要求された機能を満たすことをレビューする。
- テスト自体の検出力を確かめるため、ミューテーションテストを行う。全コードへの一律適用は必須とせず、認証・認可、個人情報の取扱い、重要な業務ルールなど影響の大きい処理を既定の対象とする。検出されなかった変更（生存ミュータント）を確認し、必要なテストを追加する。ツールと数値の合格閾値は技術スタック別に定める。
- テストの再現性確認では、同じコミットと依存関係、初期状態から実行したときに結果が安定することを確認する。テストデータと外部依存を分離し、テスト間の実行順序や前回実行の状態に依存させず、時刻・乱数などの環境要因は必要に応じて固定または記録する。
- 既定では通常の品質チェックでテストを1回実行し、自動再試行は行わない。再現性を確認する専用実行では、クリーンな状態から3回実行する。再実行で成功しても初回の失敗を成功扱いにせず、不安定なテストとして原因を調査する。実行コスト等に応じた変更は技術スタック別に設定できる。

#### C-05：プロジェクトに書き込む標準ルール

ハーネスを使う人（身内を含む）のPCには、作成者個人のグローバル設定（`~/.claude/CLAUDE.md`等）が存在しない。そのため、次の標準ルールは生成するプロジェクトのAI向け設定ファイルに直接含める。F-04に従い、ルールの本体は共通ルールとして1か所で管理し、`CLAUDE.md`・`AGENTS.md`等の各ファイルへはアダプタで出力する。

各ルールの文面は、別途「生成するAI向け設定ファイルの内容」として詰める（未決定事項を参照）。以下は含める内容の骨子である。

##### テストデータ（実データ・個人情報の使用禁止）

- 本番・ステージングの実データを、匿名化せずにテストへ持ち込まない
- 実在の個人名、実在しうるメールアドレス・電話番号・住所・カード番号等、本物の認証情報を使わない
- メールアドレス・ドメインは`example.com`等の予約ドメインを使う。氏名は`testuser_001`等の明らかな架空名、パスワードは`TestPass123!`のようなテスト専用の固定値を使う
- テストデータには`testuser_%`などの接頭辞や`[E2E_TEST]`などのタグを付けて識別できるようにし、識別子だけを条件に削除する後始末用スクリプトをセットで用意する
- 本番DBに接続しうる設定でテストを実行しない

##### 秘密情報

- DB認証情報・APIキー・トークン等の実際の値は、`.gitignore`で除外したファイル（`.env`等）にだけ置く
- コミットするファイルでは、環境変数展開やプレースホルダで参照する。値の例は`.env.example`にプレースホルダだけを書く
- 「テスト用・開発用だから安全」と判断しない。`password`・`admin`のような推測しやすい値を使わない
- 秘密情報の値は、チャット・コミットメッセージ・PR・Issueの本文にも書かない
- 作業対象外のファイルで秘密情報の直書きを見つけた場合は、勝手に直さず、別のIssueにしてユーザーに知らせる

##### ログインUI（アプリ独自認証を選んだ場合）

- パスワード入力欄には、入力内容の表示・非表示を切り替えるボタンを付ける
- 新規登録・パスワード再設定など新しいパスワードを決める画面には確認用の再入力欄を設け、一致しない場合は画面側でエラーを表示してAPIを呼ばない（ログイン画面には確認欄を付けない）

#### C-09：個人情報の取扱いとアプリケーションセキュリティ

- 個人情報保護法および個人情報保護委員会ガイドラインを法令・規制上の基準として扱い、JIS Q 15001:2023とISO/IEC 27701:2025を個人情報保護マネジメントの参照基準として活用する。
- アプリケーションの技術的なセキュリティ要件と検証にはOWASP ASVSを参照する。ASVSのレベルは、プロジェクトに関するチェックリストへの回答から判定する。
- チェックリストには、各項目の回答と、その回答がレベル判定にどう影響したかを記録できるようにする。具体的な質問、判定基準、該当しない項目の扱いは別途定める。
- 参照する法令・ガイドライン・規格・ASVSの版を明記し、法令や参照資料が改定された場合に見直せるようにする。
- これらの基準を参照して要件を生成することは、法令適合、規格適合または認証取得を保証するものではない。

#### C-12：認証方式の選択

- 認証方式は「認証なし」「アプリ独自認証」「外部IdPによるOIDC認証」「アプリ独自認証とOIDC認証の併用」から選択できるようにする。
- 認証なしを選ぶ場合は、認証を必要としない公開対象を明示する。
- 外部IdPを利用できる場合はOIDC認証を推奨する。アプリ独自認証を選ぶ場合は、パスワードや認証情報の保護、ログイン試行への対策、認証情報の再設定、セッション管理等の追加要件を適用する。具体的な要件は認証方式と技術スタック別の設計で定める。
- 併用する場合のアカウント連携、重複アカウントの扱い、認証手段の追加・解除等は、別途設計する。

#### C-13：認可の基本原則

- 認可はデフォルト拒否とし、明示的に許可した操作だけを実行できるようにする。認証不要で公開するAPIや機能は、その対象を明示する。
- 認証が必要なAPIでは、バックエンドが各リクエストで利用者と対象リソースに対する操作権限を確認する。
- フロントエンドで画面や操作ボタンを非表示にすることは、認可の代わりにならない。画面表示の制御とは別に、バックエンドで認可を強制する。

#### C-14：認可範囲の定義

- 認可要件では、誰が（主体）、何を（操作）、どのリソースに対して行えるかを定義する。必要に応じて、テナント・組織・所属・状態などの条件も含める。
- 認可条件には、認証済みであること、ロールやグループ、リソースの所有者・所属関係などを組み合わせて使える。全プロジェクト共通の「一般利用者」ロールや固定のロール名は必須にしない。
- 管理者ロールは全プロジェクトで必須とはしない。管理者向け機能を設ける場合は、機能要件ごとに管理者が行える操作と対象データの範囲を定義し、「管理者」を無制限の権限として扱わない。
- 複数人でアプリ内のデータや設定を作成・編集する機能では、機能要件に所有単位（個人・チーム・組織等）と、共同編集を許可する利用者の範囲・操作を定義する。作成者、所有者、共同編集者は同一とは限らないため、必要に応じてそれぞれ区別する。
- ログインしたことだけで、すべての機能やデータへのアクセスを許可してはならない。利用者ID・ロール・テナントID等の権限判断に使う値は、クライアントから送られた値をそのまま信用せず、認証済み主体やサーバー側の情報から取得・検証する。
- 権限の付与・変更・取り消しも保護対象の操作として扱い、機能要件で実行できる主体、対象者、変更可能な権限と範囲を定義する。権限管理者の階層や委任範囲はプロジェクトごとに定め、最上位の管理者だけが変更できる構成も、下位管理者が許可された範囲で管理できる構成も選べるようにする。
- 管理者が自分自身の権限を不正に引き上げたり、許可範囲を超えて他者へ権限を付与したりできないよう、バックエンドで現在の主体と委任範囲を検証する。
- 認証を要求する機能で認可範囲が要求に定義されていない場合は、権限の不足としてユーザーに確認する。確認が済むまでは、該当する保護対象の操作を拒否する。
- リソースIDを指定して取得・変更・削除する操作では、そのリソース単位で毎回権限を確認する。一覧取得では、利用者がアクセスできる範囲に結果を絞る。
- 認可テストでは、未認証、許可された主体、許可されていない主体、異なる所有者・所属のリソースを使い、閲覧・作成・更新・削除などの操作ごとに許可／拒否を確認する。共同編集機能では、所有者・許可された共同編集者・許可されていない利用者の境界を確認する。
- 権限管理機能がある場合は、許可された主体による権限変更に加え、自己昇格、委任範囲を超えた付与、上位管理者の権限変更など、要件上許可されない操作が拒否されることをテストする。

#### C-16：セッションとログアウトの範囲

- アプリケーションからログアウトするときは、認証方式にかかわらず、アプリケーション自身のセッションをクライアントとサーバーの両方で終了・無効化する。
- OIDCを利用する場合、アプリケーションのセッションと外部IdPのセッションは別のものとして扱う。アプリケーションからログアウトしてもIdP側のセッションが残り、次回ログイン時に利用者が再認証せずアプリケーションへ戻る場合があることを前提とする。
- IdP側のセッションも終了させるかどうかはプロジェクトごとに明示する。IdPからのログアウトは、同じIdPを使う他のアプリケーションの利用にも影響し得るため、アプリケーションのログアウトと常に一体の動作にしてはならない。
- OIDCのログアウト範囲を選択した場合は、ログアウト後の画面遷移、IdP側セッションの状態、次回ログイン時の再認証または自動ログインの挙動を確認し、テストする。利用者にとってログアウト完了の意味が分かるように案内する。
- アプリ独自認証とOIDCを併用する場合も、どの認証方法でログインしたかにかかわらずアプリケーション自身のセッションは終了する。IdP側セッションの終了は、OIDCログアウト方針に従って別途扱う。

#### C-17：アプリケーション発行トークンのライフサイクル

- アクセストークンとリフレッシュトークンの組み合わせは、アプリケーション独自認証で必須とはしない。サーバー側セッション等を含め、クライアント種別とシステム構成に適した方式を選ぶ。アプリケーションがこのトークン方式を採用する場合は、以下を適用する。
- アクセストークンは必要な用途・対象に限定し、漏えい時の悪用可能時間を抑える有効期間を設定する。リフレッシュトークンにはアイドル期限または最長有効期間を設け、具体的な期間はリスク、利用形態、クライアント種別を根拠に技術設計で決定する。
- リフレッシュトークンを発行する場合は、更新ごとに新しいトークンを発行して旧トークンを無効化するローテーションを行う。無効化済みトークンの再利用を検知した場合は、同一セッション／トークン系列を失効させ、再認証を要求する。複数タブ・同時リクエストで正当な更新が競合しないよう、更新処理を調整する。
- リフレッシュトークンの更新期限を延長する場合も、初回認証時に定めた最長有効期間を超えて無期限に延長してはならない。アイドル期限と最長有効期間をどのように組み合わせるかは、認証方式別の設計に記録する。
- ログアウト、アカウント停止、認証情報の変更・漏えい等でセッションを終了する際は、該当するリフレッシュトークンと関連セッションをサーバー側で失効させる。アクセストークンの有効期限が残る間の扱い（短い有効期間、失効照会等）も明示する。
- トークン方式を採用する場合、トークンの保存場所・送信方法をクライアント種別ごとに決める。ブラウザーでは、JavaScriptから読み取れるWeb Storageへ認証トークンを保存せず、BFFまたは適切なCookie等の保護策を検討する。
- アプリケーション発行トークンと外部IdP発行トークンは、発行者、用途、対象（audience）、署名鍵、更新・失効管理を分離する。外部IdPのIDトークンをアプリのAPI用アクセストークンとして扱わず、受信する各トークンの発行者・署名・対象・有効期限・用途を検証する。OIDCログイン後にアプリ独自のセッションまたはトークンを発行する場合は、そのライフサイクルをIdP側のトークンとは別に定義する。
- 権限変更の反映をトークン内の古いロール情報だけに依存させない。保護対象の操作ではC-13・C-14に従って権限を確認し、即時反映が難しい構成を採用する場合は、反映までの時間差と補完策を明示する。
- トークンの有効期限・更新成功／失敗・ローテーション・旧トークン再利用・ログアウト後の利用・アカウント停止後の利用・権限変更後の操作をテストする。期限切れ時の画面動作はC-15、ログアウトの範囲はC-16にも従う。

#### C-18：認証情報・認証要素の回復

- OIDCを利用する場合、IdPが管理するパスワード、MFA等の認証情報・認証要素の回復はIdPの手続きに委ねる。アプリケーションはIdPの回復機能を独自に代行・迂回しない。
- アプリ独自認証で管理するパスワードや認証要素の回復は、アプリケーションの責任として設計する。OIDCとアプリ独自認証を併用する場合は、どの認証手段を回復する手続きなのかを利用者に明示し、相互に取り違えない。
- アプリ独自のパスワード再設定では、アカウントの有無を第三者に推測されにくい応答とし、再設定用トークン／コードを推測困難・一回限り・期限付きにする。再設定の要求だけでアカウントを変更・停止せず、有効な再設定証明を確認してから変更する。
- 回復手続き完了後は利用者へ通知し、回復後の自動ログインを既定にしない。通常の認証手続きを行わせる。回復前のセッションやリフレッシュトークンを失効させる方針を定め、関連する挙動をテストする。
- MFA等の認証要素を回復・交換する場合は、既存要素を利用できない状況も想定した本人確認方法を設計する。回復手続きが通常の認証より弱い経路にならないようにし、変更後の通知とセッションの扱いを定める。
- OIDCの回復先、アプリ独自回復の手順・有効期限・試行制限・通知方法・セッション失効範囲は、認証方式と機能要件に応じて具体化し、正常系と不正・期限切れ・再利用等の拒否ケースをテストする。

#### C-19：ログイン試行制限とセキュリティ通知

- アプリ独自認証のログイン、パスワード再設定、認証要素の確認・回復など、オンラインで秘密を試せる処理には、総当たり・自動化された試行を抑えるレート制限を設ける。制限はアカウント単位を基本とし、IPアドレス・端末・挙動等の信号も組み合わせて回避と誤検知の両方を抑える。
- 失敗回数の閾値、観測期間、待ち時間、解除条件は一律の共通数値に固定せず、認証方式、利用者数、扱う情報の重要度、攻撃リスクに応じて技術スタック別に定める。失敗が続く場合は待ち時間を段階的に延ばす方法等を検討し、恒久的なアカウントロックを自動適用することを既定にしない。
- 制限の設計では、第三者が他人のアカウントを意図的にロックして利用を妨害できないようにする。登録アカウントの有無をログイン応答から推測されにくくし、試行制限によって正当な利用者が締め出された場合の安全な回復手段を用意する。
- 個人情報や重要データを扱うなどリスクが高いアプリでは、不審な試行の集中や強い制限の発動を、登録済みの連絡先等へ通知する方法を設ける。通知頻度を抑制・集約し、通知機能自体が大量送信攻撃に利用されないようにする。
- セキュリティ通知は不審な事象を知らせるものであり、それだけでログインを承認したり、本人確認を完了したり、制限を解除したりしてはならない。追加の本人確認やアカウント回復は、C-18に従う別の安全な手段で行う。通知には心当たりがない場合の次の行動を分かりやすく示す。
- OIDC認証のログイン試行制限は原則としてIdP側の機能・ポリシーに委ね、アプリ側で独自に迂回・重複した制限を設けない。アプリ独自認証を併用する場合は、アプリ独自認証の経路に本項を適用する。
- 試行制限の境界値、待ち時間、解除・回復、通知の発生条件と頻度、アカウント有無の秘匿、正当なログインへの影響をテストする。具体的な回数・期間・通知先・通知方法は技術スタック別の設計時に決定する。

#### C-20：多要素認証（MFA）と重要操作の再認証

- MFAを全利用者に必須とするか、任意とするか、特定の利用者・機能だけで要求するかは、扱う情報、操作による影響、想定される攻撃、利用者層および運用負荷を踏まえたリスク評価で決定する。簡易的なアプリであっても、MFAの適用要否を検討せずに省略してはならない。
- 管理者・高権限利用者については、アカウント乗っ取り時にできる操作と影響範囲を評価し、MFAを必須とするかを明示的に決定する。利用者やデータが広範囲に及ぶサービス、個人情報・金銭・設定変更等を扱うサービスでは、管理者MFAを原則として要求する方向で検討する。
- パスワードや認証要素、登録メールアドレス、権限、送金・公開・削除等の重要な操作では、現在のログイン状態だけで足りるかを評価し、必要に応じてMFAまたは再認証（step-up authentication）を求める。対象操作と必要な認証強度は機能要件で定義する。
- OIDCを利用する場合は、IdPで行われたMFAまたは再認証をどの条件で受け入れるか、アプリ側で追加確認が必要な条件は何かを定める。アプリ独自認証の場合は、採用するMFA方式、認証要素の追加・交換・回復をC-18に従って設計する。
- MFAや再認証の要求、失敗、認証要素の追加・変更・解除、回復をテストする。認証の強さが不足する場合は、重要操作を実行させない。

#### C-15：エラー応答と利用者への案内

- HTTPステータスコードはRFC 9110を参照して使い分ける。先頭の数字による分類は、`1xx`が処理継続中、`2xx`が成功、`3xx`が追加の処理・転送、`4xx`が要求内容や条件に関する問題、`5xx`がサーバー側で処理を完了できない状態を表す。
- APIでは、状況に応じて代表的なHTTPステータスを選ぶ。例として、`200`（成功して応答本文あり）、`201`（リソース作成）、`204`（成功して応答本文なし）、`400`（不正な要求）、`404`（リソースが見つからない、または存在を開示しない）、`409`（現在のリソース状態との競合）、`413`（要求内容が大きすぎる）、`415`（対応していないメディア形式）、`422`（形式は理解できるが内容を処理できない）、`429`（要求頻度の制限）、`500`（予期しないサーバー内部エラー）、`502`（中継先から不正な応答）、`503`（一時的にサービスを利用できない）、`504`（中継先から時間内に応答がない）を候補とする。機能・APIごとの適用ケースは要件とAPI仕様で決める。
- ステータスコードはエラーの大分類であり、細かな業務上の原因をすべて表すものではない。アプリケーション固有のエラーコードや応答本文を併用して原因を識別し、クライアントが安定して処理できるようにする。RFCに定義された名前や例だけから各機能の期待コードを推測せず、API仕様で明示する。
- APIのエラー応答では、HTTPステータスコードをエラーの種類に適したものにし、必要に応じてアプリケーション固有の安定したエラーコードを別途返す。HTTPステータスは通信上の分類、アプリケーションエラーコードは個別の原因を識別するために使い、両者を混同しない。
- 認証情報がない・無効で処理できない場合は401、認証済みだが許可されない操作は403を基本とする。権限不足をログイン切れとして扱わず、403を理由にログアウトやログイン画面への遷移を行わない。リソースの存在自体を開示しない必要がある場合の404応答は、機能・脅威要件で明示する。
- 利用者向けメッセージは、何が起きたかを理解でき、次に取れる行動（入力修正、再試行、再ログイン、管理者への問い合わせ等）が分かる表現にする。技術用語だけの表示や、原因・対処が分からない「エラーが発生しました」だけの表示を避ける。対処方法がない場合も、その旨と問い合わせ先等を機能に応じて案内する。
- 権限の変更・拒否によって、ユーザーが利用できる機能、データ、操作結果に予期しない変化が生じる場合は、変化に関係する画面や操作の近くで、その変化と次に取れる行動を通知する。すべての拒否で大きな警告を出すのではなく、ユーザーが気づく必要のある変化に応じた表示とする。通知は不要に繰り返さず、権限のない情報や内部の認可条件を漏らさない。
- サーバー内部の例外、スタックトレース、SQL、秘密情報、他利用者の情報などを利用者向けメッセージや公開API応答に含めない。調査に必要な詳細はアクセス制御されたログに記録し、利用者向けメッセージと分ける。
- 認証切れ・無効を示す401を受けた場合、選択した認証方式に更新手段があれば一度だけ更新を試す。更新に成功した場合も、元の要求の再送は二重実行されないことを確認できる場合に限り一度だけ行う。更新手段がない、または更新に失敗した場合は認証状態を解除し、ログイン画面へ一度だけ遷移して、可能であればセッション終了を説明する。複数要求が同時に401となっても、更新や遷移を重複させない。
- セッション期限切れ時は、可能な範囲で入力中データの扱いとログイン後の戻り先を明確にする。戻り先を引き継ぐ場合は、許可されたアプリ内遷移先に限定し、外部サイトへの不正な転送を防ぐ。
- エラー検証では、要件・入力条件・認証状態・権限状態ごとに、成功時と失敗時の期待HTTPステータス、アプリケーションエラーコード、利用者向け表示、データ変更の有無を定義する。自動テストで応答ステータス、エラーコード、応答形式、意図しない副作用がないことを確認する。代表的な画面・E2Eテストでは、メッセージが状況に合い、次の行動を案内することもレビューする。
- エラーコードのテストは、実装が返した値をそのまま期待値にするのではなく、要件やAPI仕様で定義した期待値と照合する。異なる原因が同じコードに誤って集約されていないこと、無関係な成功・失敗ケースで誤ったコードを返さないこと、クライアントがコードに応じた表示・動作をすることを確認する。エラー応答仕様を変更した場合は、API契約テストと該当する利用者向け表示のテストを更新する。
- HTTPステータスの使い分けはRFC 9110、技術的なセキュリティ要件はOWASP ASVS等を参照する。参照基準は個別機能の期待コード・文言・画面動作を自動的に決めるものではないため、これらは機能要件/API仕様で明示する。

### F-15：コンフリクト防止の手順

`git status`は手元の状態しか分からないため、リモートの最新状態を取得して比較する。

| タイミング | やること | 使うコマンド（例） |
| --- | --- | --- |
| 作業開始前 | リモートの最新状態を取得し、最新の`main`からブランチを作る | `git fetch`、`git switch -c` |
| 作業開始前 | 他の人が同じファイルを触っているオープン中のPRがないか確認する | `gh pr list`、`gh pr diff` |
| push前 | 最新の`main`を取り込み、コンフリクトがないか確認する | `git fetch` → `git merge-tree` |
| マージ前 | PRがコンフリクトなしでマージ可能か確認する | `gh pr view --json mergeable` |

### F-16：技術スタックに応じた品質チェック

- 品質チェックは、フロントエンド共通プロファイルとバックエンド別プロファイルに分け、選択した技術スタックに応じて組み合わせる。
- 品質チェックの実行場所を「ローカルのみ」「GitHub Actions」「ローカルとGitHub Actionsの両方」から選べるようにする。GitHub Actionsを利用できない案件では、ローカルのみを選べる。
- GitHub Actionsを実行場所に選んだ場合は、CIを利用する設定とし、CIの種類はGitHub Actionsに整合させる。ローカルのみを選んだ場合は、品質チェックのためのGitHub Actionsワークフローを生成しない。
- 選んだ実行場所に応じて、ローカル実行用スクリプト、GitHub Actionsワークフロー、または両方を生成する。ローカル実行用スクリプトは、GitHub Actionsを選んだ場合に必ず生成するとは限らない。
- 現時点の候補構成は次のとおりとする。記載したツールは候補であり、確定した採用決定ではない。

| プロファイル | チェック領域 | ツール候補 |
| --- | --- | --- |
| React／TypeScript共通 | Lint・React規約 | ESLint、TypeScript／React用プラグイン |
| React／TypeScript共通 | 型チェック | TypeScript compiler（`tsc`） |
| Hono（TypeScript） | Lint・型チェック・バグ検出等 | フロントエンドと共通のTypeScript系ツール |
| Spring Boot（Java） | Lint・命名・書式・import | Checkstyle |
| Spring Boot（Java） | 型チェック | Java compiler |
| Spring Boot（Java） | バグ・null・並行処理 | SpotBugs |
| Spring Boot（Java） | 複雑度・設計上の問題 | PMD |
| Python | Lint・書式・import・複雑度 | Ruff |
| Python | 型チェック | Pyright |
| 各プロファイル | セキュリティ静的解析 | ツール候補と適用方法は未決定 |

- 静的解析、テスト、ビルドはそれぞれ別のチェック領域として定義する。
- テストには単体テスト・結合テスト・E2Eテストを含める。技術スタックに応じてテストフレームワークと実行方法を定義する。
- テストの設計と信頼性の確保（テストオラクル、要求との照合、ミューテーションテスト、再現性の確認等）はC-25に従う。
- GitHub Actionsを利用する場合、選択した品質チェックをワークフローに反映し、必要なチェックをマージ条件に含める。
- 各ツールの詳細設定（ルールセット、厳しさ、閾値、除外対象、警告とエラーの扱い等）、ツールのバージョン、実行順序、合格条件は、プロファイルごとの設計時に決定する。CLIの質問で個々の設定を利用者に選ばせるか、標準設定を自動生成するかも未決定とする。

### 認証・認可・セキュリティ関連

| 用語 | 意味 |
| --- | --- |
| 認証 | 「あなたは誰か」を確かめること。ログインが代表例 |
| 認可 | 「あなたはこの操作をしてよいか」を判定すること。認証の後に行う |
| デフォルト拒否 | 明示的に許可したもの以外は、すべて拒否する考え方 |
| ロール | 「管理者」「編集者」など、権限をまとめた役割 |
| IdP | Identity Provider の略。Google・Microsoftなど、ログインの仕組みを提供する外部サービス |
| OIDC | OpenID Connect の略。IdPを使って安全にログインするための標準の仕組み |
| セッション | ログインしてからログアウトするまでの「ログイン中」という状態を、サーバーとブラウザで保持する仕組み |
| アクセストークン | APIを呼び出すときに提示する「通行証」。有効期間を短くする |
| リフレッシュトークン | 期限切れになったアクセストークンを新しく発行してもらうための、長めの有効期間を持つ引換券 |
| ローテーション | リフレッシュトークンを使うたびに新しいものへ交換し、古いものを使えなくすること |
| BFF | Backend For Frontend の略。画面専用の中継サーバー。トークンをブラウザに持たせずに済む |
| MFA | 多要素認証。パスワードに加えて、スマホのコードなど別の要素でも本人確認すること |
| 再認証（step-up authentication） | ログイン中でも、重要な操作の直前にもう一度本人確認を求めること |
| レート制限 | 一定時間内に試せる回数を制限すること。パスワードの総当たりを防ぐ |
| OWASP ASVS | Webアプリのセキュリティ要件を一覧にした国際的なチェックリスト。求める厳しさに応じてレベル1〜3がある |
| 個人情報保護法 | 個人情報を扱う事業者が守るべき日本の法律 |
| JIS Q 15001 | 個人情報を保護する体制づくりの日本の規格（プライバシーマークの基準） |
| ISO/IEC 27701 | 個人情報（プライバシー情報）を管理する体制づくりの国際規格 |

### HTTP・通信関連

| 用語 | 意味 |
| --- | --- |
| HTTPステータスコード | サーバーが返す3桁の結果番号。`200`は成功、`404`は見つからない、`500`はサーバーの内部エラーなど |
| 401／403 | `401`は「ログインしていない・ログインが無効」、`403`は「ログインしているが権限がない」 |
| RFC 9110 | HTTPの意味（ステータスコード等）を定めた標準仕様 |
| アプリケーションエラーコード | HTTPステータスとは別に、アプリが独自に決める細かいエラーの識別番号 |
| キャッシュ | 一度取得したデータを近くに保存しておき、次回の取得を速く・安くする仕組み |
| CDN | Content Delivery Network の略。画像などを利用者の近くのサーバーから配信する仕組み |

### Git・GitHub関連

| 用語 | 意味 |
| --- | --- |
| Issue | GitHub上の「やることリスト」の1項目。作業内容や完了条件を書く |
| Issue駆動 | 作業を始める前に必ずIssueを作り、Issue → ブランチ → PR の順で進める開発のやり方 |
| 親Issue・子Issue | 大きな作業（親）を、小さな作業（子）に分けて管理する仕組み。GitHubでは子Issueを「sub-issue」と呼ぶ |
| ブランチ | 本流（`main`）から枝分かれした作業場所。他の作業に影響を与えずに変更できる |
| PR（プルリクエスト） | 「このブランチの変更を`main`に取り込んでください」という依頼。変更内容の確認とマージをここで行う |
| マージ | ブランチの変更を別のブランチ（主に`main`）に取り込むこと |
| コンフリクト | 複数の人が同じファイルの同じ箇所を別々に変更し、自動では取り込めなくなった状態 |
| リモート | GitHubなど、ネットワーク上にあるリポジトリ。手元のリポジトリは「ローカル」と呼ぶ |
| fetch | リモートの最新状態を手元に取得すること。手元のファイルは書き換えない |
| モノレポ | フロントエンド・バックエンドなど複数の部分を、1つのリポジトリで管理する構成 |
| CI | Continuous Integration の略。PRを作るたびにテスト・Lint・ビルドを自動で実行する仕組み。GitHub Actionsが代表例 |
| セマンティックバージョニング | `MAJOR.MINOR.PATCH`の3つの数字で、変更の大きさが分かるようにバージョンを付けるルール |

### バックエンドの層

| 用語 | 意味 |
| --- | --- |
| 層（レイヤー） | プログラムを役割ごとに分けたまとまり。1つの層は1つの役割だけを持つ |
| 責務の分離 | 1つのクラス・ファイルに複数の役割を持たせないこと。どこに何が書いてあるか分かりやすくなる |
| Controller | 外部からのリクエストを受け取り、結果を返す窓口 |
| Service | 業務のルール（計算・判定など）を実行する層 |
| Repository／DAO | DBへの読み書きを担当する層。DAOは Data Access Object の略 |
| DTO | Data Transfer Object の略。層の間やAPIでデータを運ぶための入れ物 |
| Entity | DBのテーブルの1行に対応するデータ |
| Mapper | EntityとDTOを相互に変換する部分 |
| ORM | Object-Relational Mapping の略。SQLを書かずに、プログラムのオブジェクトとしてDBを操作できる仕組み。JPA・Prismaなど |
| SQLマッパー | 自分で書いたSQLの結果を、プログラムのオブジェクトに対応づける仕組み。MyBatisなど |
| プロジェクション | DBから必要な列だけを取り出すこと。不要なデータを読まずに済む |
| マイグレーション | DBのテーブル構造の変更を、ファイルとして順番に記録・適用する仕組み |
| トランザクション | 複数のDB操作を「全部成功」か「全部取り消し」のどちらかにまとめる仕組み |
| CRUD | Create（作成）・Read（取得）・Update（更新）・Delete（削除）の基本的な4つの操作 |
| ドメインモデル | 業務の概念（注文・会員など）をそのまま表したクラス。DBのテーブル構造とは必ずしも一致しない |
| N+1問題 | 一覧を1回取得した後、各行ごとに追加のSQLを1回ずつ発行してしまい、SQLの回数が件数に比例して増える問題 |
| インデックス | DBの「索引」。検索を速くするが、書き込みが遅くなり容量も使う |
| 実行計画 | DBがSQLをどういう手順で処理するかの予定表。`EXPLAIN`で確認できる |
| 全件走査 | インデックスを使わず、テーブルの全行を読んで検索すること |

### フロントエンドの層

| 用語 | 意味 |
| --- | --- |
| Pages | URLごとの画面 |
| Components | ボタンや入力欄など、画面を組み立てる部品 |
| Hooks | 画面の状態（入力中の値、読み込み中かどうか等）とロジックをまとめたもの。Reactの仕組み |
| 状態管理 | 画面に表示するデータを、どこで保持し、どう更新するかの管理 |

### テスト・環境関連

| 用語 | 意味 |
| --- | --- |
| 単体テスト | 関数やクラス1つ単位で動作を確かめるテスト |
| 結合テスト | 複数の部品を組み合わせて動作を確かめるテスト。APIからDBまで通すなど |
| E2Eテスト | End to End の略。実際にブラウザを操作して、画面からDBまで通しで確かめるテスト |
| ブラックボックステスト | 中身を見ずに、仕様どおりの入力と出力になるかで確かめるテスト |
| ホワイトボックステスト | コードの構造（分岐など）を見て、すべての経路を通るように作るテスト |
| テストオラクル | テストの「正解」を決める根拠。仕様書や、別の方法で計算した結果など |
| mock・fixture | mockはテスト用の偽物の部品、fixtureはテスト用にあらかじめ用意するデータや状態 |
| ミューテーションテスト | コードをわざと少し壊して、テストがそれを見つけられるかを確かめる、テスト自体の検査 |
| Playwright | ブラウザを自動で操作してE2Eテストを行うツール |
| Appium | iOS・Androidのモバイルアプリを自動で操作してテストするツール |
| エミュレーター・シミュレーター | PC上でスマートフォンを再現して、モバイルアプリを動かす仕組み |
| Orcaブラウザ | AIの作業環境Orcaに組み込まれたブラウザ。AIが画面を操作し、表示・コンソール・通信を確認できる |
| トレース | Playwrightがテスト中の操作・画面・通信を記録したもの。失敗時に後から再生して調べられる |
| 不安定なテスト（flaky test） | 同じ条件でも成功したり失敗したりするテスト |
| シード | テストや開発用に、DBへ最初に入れておくデータ |
| Lint | コードの書き方の誤りや規約違反を自動で見つけるツール |
| `.env` | パスワード等の秘密情報を書くファイル。GitHubには上げない |
| `.env.example` | `.env`の書き方の見本。実際の値は書かずにGitHubへ上げる |
| Docker | アプリやDBを「コンテナ」という箱に入れて、どのPCでも同じ環境で動かせる仕組み |
