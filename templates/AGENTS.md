# {{app_name}} — AIエージェント作業ルール

## 最初に守ること：日本語で書く

- 作業中の説明・途中経過・報告・計画・レビュー結果・質問は、**すべて日本語**で書く。英語を混ぜない
- Issue・PR・コミットメッセージの説明部分も日本語で書く
- 関数名・ファイル名・コマンド・エラーメッセージの原文・ライブラリ名など、識別に必要なものは原文のまま書いてよい
- サブエージェントや別のAIに作業を頼むときも、日本語で出力するよう指示に含める。英語で返ってきた結果は、日本語にしてから利用者に見せる

## このファイルの位置づけ

- このファイルは、すべてのAIが常に守る**核のルール**である。分野別の詳しいルールは、下の「Skill」を必要な作業のときに読み込む
- 優先順位：利用者の指示 ＞ このファイル ＞ Skill ＞ 知見（Skill「知見」）
- 仕様の正は `docs/requirements.md` とする。このファイルと食い違う場合は、作業を止めて利用者に確認する

## 作業の流れ

すべての変更（コード・ドキュメント・設定）は、次の順で進める。

1. **Issueを作る**：Issueなしで作業を始めない。機能は親Issue、作業領域（DB・バックエンド・フロントエンド・その他）ごとに子Issueに分ける
2. **ブランチを作る**：最新の`main`から `<種類>/<Issue番号>-<内容>` の名前で作る
   - 種類：`feature`（機能追加）・`fix`（不具合修正）・`docs`（文書）・`refactor`（整理）・`chore`（設定・依存関係・CI）
   - 例：`feature/12-login-api`
3. **実装する**：下の「実装の進め方」に従う
4. **コミットする**：`<種類>: <説明>`（種類は英語、説明は日本語）。例：`feat: ログインAPIを追加`
   - 種類：`feat`・`fix`・`docs`・`refactor`・`test`・`chore`。以前と両立しない変更は `feat!:` のように`!`を付ける
5. **PRを作る**：本文に `Closes #<子Issue番号>`、親Issueは `Refs #<親Issue番号>` を書く。PRテンプレートの「知見」の欄は必ず埋める
6. **マージする**：テストと品質チェックが通っていることを確かめ、**Squash**でマージする
7. **後片付け**：ローカルの`main`を最新にし、統合済みの作業ブランチを削除する。別のworktreeで使用中・未コミットの変更があるブランチは削除せず、状態を報告する

- **`main`へ直接pushしない**。変更はすべてPR経由で取り込む
- 複数人で開発している場合は、作業開始前・push前・マージ前に、リモートの最新状態と比べてコンフリクトがないかを確認する

## 実装の進め方

Issue 1件を、役割に分けて進める。詳しくはSkill「実装の進め方」を読む。

| 役割 | やること |
| --- | --- |
| 統括 | 全体の進行、成果物の受け渡し、完了の判定 |
| 計画 | 受け入れ条件から、変更するファイル・手順・テストケースを決める |
| 計画レビュー | 計画の漏れ・退行・テスト不足を指摘する |
| テスト | 受け入れ条件からテストを**実装より先に**書く |
| 実装 | テストが通るように実装する。**テストは変更しない** |
| 品質チェック | Lint・型・テスト・E2E等を実行し、結果を報告する |
| コードレビュー | 実装とは**別のAI**でレビューする |
| ドキュメント | 関係する文書を更新し、PRの「知見」の欄を書く |

- 変更の大きさ（小・通常・影響大）で、起動する役割を変える。判断した大きさと理由をIssueに書く
- 計画・レビュー結果・品質チェックの結果・計画の変更は、Issueのコメントに残す
- レビューは最大3回。3回目でも重大な指摘が残る場合は、止まって利用者に判断を求める。ただし、データ破損・認証の回避・情報漏えいにつながる指摘は、解消するまで続ける
- 品質チェックとコードレビューが終わったら、コミットの前に止まり、利用者に動作確認を依頼する

## 必ず立ち止まって、利用者に確認すること

- 利用者による動作確認が必要な工程に着いた
- 文書と実装の食い違いを見つけた
- 新しいライブラリの追加など、共通のルールに影響する変更が必要になった
- 「要調査」「未検証」とされている項目に着手する
- レビューを重ねて、Issueが単独でレビュー・マージできる大きさを明らかに超えた
- デプロイ、本番DBへのマイグレーション、`terraform apply`、本番での手動実行など、本番環境に影響する操作

## 絶対にしないこと

### 秘密情報

- パスワード・APIキー・トークン等の実際の値を、`.gitignore`で除外していないファイルに書かない。実際の値は`.env`等だけに置き、コミットするファイルでは環境変数やプレースホルダで参照する
- 秘密情報の値を、チャット・コミットメッセージ・PR・Issueに書かない
- 作業と関係のないファイルで秘密情報の直書きを見つけても、勝手に直さず、別のIssueにして知らせる

### テストデータ

- 本番・検証環境の実データを、匿名化せずにテストに使わない
- 実在の人名・実在しうるメールアドレス・電話番号・住所・カード番号、本物の認証情報を使わない。メールアドレスは`example.com`等、名前は`testuser_001`等の架空のものを使う
- テストデータには識別用の接頭辞・タグを付け、削除用のスクリプトとセットにする
- 本番DBに接続しうる設定でテストを実行しない。本物の外部APIをテストで呼ばず、モックを使う

### テストと品質

- テストを通すことだけを目的に、実装を要求と違う動作に変えたり、テストを無効化・スキップしたり、期待結果を根拠なく変えたりしない
- エラーを隠すために`eslint-disable`・`@ts-ignore`等を安易に追加しない。失敗は原因を直し、成功扱いにしない

### 変更の範囲

- 依頼されていない大規模なリファクタリングを同時に行わない
- 既存の公開API・型・動作を、理由なく変えない
- 新しいライブラリを、利用者の承認なしに追加しない。バージョンは必ず固定する（`^`・`~`・`latest`を使わない）

## 作業するときの心がけ

- 変更の前に、既存のコードの設計・命名・ディレクトリ構成を確認し、既存のやり方に合わせる
- 変更の範囲は、要求された機能に必要な最小限にする
- 判断に迷ったら、Skill「知見」で該当する分野の知見を確認する。知見はルールより優先しない。当てはまらない場合は、根拠を示して判断し、記録する

## 完了の定義

次のすべてを満たすまで、完了と報告しない。

1. Issueの受け入れ条件をすべて満たしている
2. 該当するテストと品質チェックが、プロジェクト全体に対して通っている
3. 変更に関係する文書（要件定義書・API仕様・`docs/tech-stack.md`・ADR・README）を更新している
4. PRにIssueを紐付けている

## Skill（必要なときに読み込む）

| Skill | 読み込むとき |
| --- | --- |
| 実装の進め方 | Issueの実装を始めるとき |
| バックエンド | バックエンドの設計・実装・レビュー |
| フロントエンド | フロントエンドの設計・実装・レビュー |
| テスト | テストの作成・実行、テスト環境の構築、E2Eの不具合調査 |
| セキュリティ | 認証・認可・個人情報・入力チェック・ファイルのアップロードを扱うとき |
| エラー応答・API | APIの設計、エラー応答の実装 |
| 環境・デプロイ | Docker・IaC・デプロイ・本番DBの変更を扱うとき |
| レビュー | 計画レビュー・コードレビュー |
| 知見 | 判断に迷ったとき、PRの「知見」の欄を書くとき |
