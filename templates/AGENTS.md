# {{app_name}} — AIエージェント作業ルール

## 最初に守ること：日本語で書く

- 作業中の説明・途中経過・報告・計画・レビュー結果・質問は、**すべて日本語**で書く。英語を混ぜない
- Issue・PR・コミットメッセージの説明部分も日本語で書く
- 関数名・ファイル名・コマンド・エラーメッセージの原文・ライブラリ名など、識別に必要なものは原文のまま書いてよい
- サブエージェントや別のAIに作業を頼むときも、日本語で出力するよう指示に含める。英語で返ってきた結果は、日本語にしてから利用者に見せる

## このファイルの位置づけ

- このファイルは、すべてのAIが常に守る**核のルール**である。分野別の詳しいルールは、下の「Skill」を必要な作業のときに読み込む
- 優先順位：利用者の指示 ＞ このファイル ＞ Skill ＞ 知見（Skill「知見」）
- 仕様の正は `docs/requirements.md` とする。このファイルと食い違う場合は、作業を止めて利用者に確認する

## 作業の流れ

すべての変更（コード・ドキュメント・設定）は、次の順で進める。

1. **Issueを作る**：Issueなしで作業を始めない。機能は親Issue、作業領域（DB・バックエンド・フロントエンド・その他）ごとに子Issueに分ける
2. **ブランチを作る**：最新の`main`から `<種類>/<Issue番号>-<内容>` の名前で作る
   - 種類：`feature`（機能追加）・`fix`（不具合修正）・`docs`（文書）・`refactor`（整理）・`chore`（設定・依存関係・CI）
   - 例：`feature/12-login-api`
3. **実装する**：下の「実装の進め方」に従う
4. **コミットする**：`<種類>: <説明>`（種類は英語、説明は日本語）。例：`feat: ログインAPIを追加`
   - 種類：`feat`・`fix`・`docs`・`refactor`・`test`・`chore`。以前と両立しない変更は `feat!:` のように`!`を付ける
5. **PRを作る**：本文に `Closes #<子Issue番号>`、親Issueは `Refs #<親Issue番号>` を書く。PRテンプレートの「知見」の欄は必ず埋める
6. **マージする**：テストと品質チェックが通っていることを確かめ、**Squash**でマージする
7. **Issueのクローズを確かめる**：`Closes`で指定したIssueが自動でクローズされたかを確かめる。されていなければ、PRの番号を書いたコメントを付けて手動でクローズする
8. **後片付け**：ローカルの`main`を最新にし、統合済みの作業ブランチを削除する。別のworktreeで使用中・未コミットの変更があるブランチは削除せず、状態を報告する

- **`main`へ直接pushしない**。変更はすべてPR経由で取り込む
- 複数人で開発している場合は、作業開始前・push前・マージ前に、リモートの最新状態と比べてコンフリクトがないかを確認する

## 要件定義とIssueへの分割

実装の前に、次の2つの段階を行う。どちらも利用者との対話が必要なため、役割ごとのエージェントではなく、**統括（メインの会話）が担当する**。詳しくはSkill「実装の進め方」を読む。

1. **要件定義**：利用者と対話しながら、目的・機能・範囲・受け入れ条件を決め、要件定義書に書く（Superpowersの`brainstorming`を使う。ただし成果物は`docs/requirements.md`に書き、承認の後は`writing-plans`ではなくプロトタイプに進む）。個人情報・管理者の機能などの判定の項目（Skill「実装の進め方」）も確かめる。決まっていないことは推測で埋めず「未決定」と書く。合意を得るまで実装に進まない
2. **プロトタイプ**：画面があるプロジェクトでは、要件定義書の合意の後に、HTML・CSS・JavaScriptだけで画面の動きを再現したプロトタイプを`prototype/`に作り、利用者と確かめる。画面の洗い出しは統括が行い、作成はエージェント`prototyper`が行う。気づいた点は要件定義書に反映する。プロトタイプは本番のコードに流用しない
3. **Issueへの分割**：要件定義書から親Issue・子Issueに分ける。子Issueには、作業領域・参照する文書・番号付きの受け入れ条件（`AC-1`…）・依存するIssueを書く。作成する前に、分割の一覧を利用者に示して承認を得る

実装中に要件の変更が必要になったら、実装を止めて要件定義に戻る。

## 実装の進め方

Issue 1件を、役割に分けて進める。詳しくはSkill「実装の進め方」を読む。

| 役割 | やること |
| --- | --- |
| 統括 | 全体の進行、成果物の受け渡し、完了の判定 |
| プロトタイプの作成 | 洗い出した画面の動きを、HTML・CSS・JavaScriptで再現する |
| 計画 | 受け入れ条件から、変更するファイル・手順・テストケースを決める |
| 計画レビュー | 計画の漏れ・退行・テスト不足を指摘する |
| テスト | 受け入れ条件からテストを**実装より先に**書く（テスト駆動開発のRed） |
| 実装 | テストが通るように実装し（Green）、テストが通る状態を保って整理する（Refactor）。**テストは変更しない** |
| 品質チェック | Lint・型・テスト・E2E等を実行し、結果を報告する |
| コードレビュー | 実装とは**別のAI**でレビューする |
| ドキュメント | 関係する文書を更新し、PRの「知見」の欄を書く |

- 変更の大きさ（小・通常・影響大）で、起動する役割を変える。判断した大きさと理由をIssueに書く
- 計画・レビュー結果・品質チェックの結果・計画の変更は、Issueのコメントに残す
- レビューは最大3回。3回目でも重大な指摘が残る場合は、止まって利用者に判断を求める。ただし、データ破損・認証の回避・情報漏えいにつながる指摘は、解消するまで続ける
- 品質チェックとコードレビューが終わったら、コミットの前に止まり、利用者に動作確認を依頼する

## 必ず立ち止まって、利用者に確認すること

- 利用者による動作確認が必要な工程に着いた
- 文書と実装の食い違いを見つけた
- 新しいライブラリの追加など、共通のルールに影響する変更が必要になった
- 「要調査」「未検証」とされている項目に着手する
- レビューを重ねて、Issueが単独でレビュー・マージできる大きさを明らかに超えた
- デプロイ、本番DBへのマイグレーション、`terraform apply`、本番での手動実行など、本番環境に影響する操作

## 破壊的な操作は、必ず利用者の判断を仰ぐ

取り消しが難しい操作や、ほかの人の作業・環境に影響する操作は、実行する前に止まり、**何を・なぜ・どの範囲で行うか**と、取り消す方法を示して、利用者の判断を仰ぐ。利用者が一度承認しても、別の場面では改めて確認する。

判断を仰ぐ操作の例：

- ファイル・フォルダの削除（作業の範囲外のもの、まとめての削除）
- Gitの履歴や変更を失う操作：`git reset --hard`、`git push --force`、`git branch -D`、`git clean`、`git checkout`・`git restore`による未コミットの変更の破棄、リベース、コミットの書き換え
- DBのデータや構造を消す操作：テーブル・データの削除、DBの作り直し（テスト用DBをテストの手順どおりに作り直す場合を除く）
- 自分が起動したか分からないプロセスの停止
- 依存ライブラリの削除・バージョンを下げること
- 本番環境・共有の環境に影響する操作：デプロイ、本番DBへのマイグレーション、`terraform apply`、設定の変更
- GitHub等、ほかの人から見える場所への操作：PRのクローズ、Issueの削除、ブランチの削除

確認する前に、`git status`等で失われるものがないかを確かめる。迷った場合は、削除ではなく、移動・名前の変更・一時的な退避など、元に戻せる方法を選ぶ。

## 絶対にしないこと

### 秘密情報

- パスワード・APIキー・トークン等の実際の値を、`.gitignore`で除外していないファイルに書かない。実際の値は`.env`等だけに置き、コミットするファイルでは環境変数やプレースホルダで参照する
- 秘密情報の値を、チャット・コミットメッセージ・PR・Issueに書かない
- 実際の値が入った秘密情報のファイル（`.env`・`.env.development`・`.env.test`・`.env.production`等）を直接読まない。値の見本の`.env.example`は読んでよい
- 足りない項目を聞かれたら、`npm run env:check`を実行し、**項目の名前だけ**で答える
- 秘密情報の値は利用者が入力する。AIは`docs/secrets.md`の手順とコマンドを案内するだけにし、値を入力するコマンド（`wrangler secret put`・`gh secret set`等）は実行しない
- 作業と関係のないファイルで秘密情報の直書きを見つけても、勝手に直さず、別のIssueにして知らせる

### テストデータ

- 本番・検証環境の実データを、匿名化せずにテストに使わない
- 実在の人名・実在しうるメールアドレス・電話番号・住所・カード番号、本物の認証情報を使わない。メールアドレスは`example.com`等、名前は`testuser_001`等の架空のものを使う
- テストデータには識別用の接頭辞・タグを付け、削除用のスクリプトとセットにする
- 本番DBに接続しうる設定でテストを実行しない。本物の外部APIをテストで呼ばず、モックを使う

### テストと品質

- テストを通すことだけを目的に、実装を要求と違う動作に変えたり、テストを無効化・スキップしたり、期待結果を根拠なく変えたりしない
- エラーを隠すために`eslint-disable`・`@ts-ignore`等を安易に追加しない。失敗は原因を直し、成功扱いにしない
- テストのために起動したもの（サーバー・ブラウザ・コンテナ等）は、テストの工程が完了したらすべて止め、ポートを解放する。原因の調査中は起動したままでよいが、利用者に引き渡すときは何が動いているかを報告する。自分が起動したか分からないプロセスは、確認せずに止めない

### エラーの扱い

- エラーをもみ消したり、ごまかしたりしない（フロントエンド・バックエンド・SQLのすべてで）
  - 何もしない`catch`を書かない
  - エラーを受け止めて、空の配列・`null`・既定値など、成功したように見える値を返さない
  - `Promise`の失敗を放置・無視しない
  - エラーをログに出すだけで、処理を成功として続けない
- その場で対処できないエラーは受け止めずに呼び出し元へ伝え、最終的な処理はグローバル例外ハンドリングにまとめる（Skill「エラー応答・API」）
- 例外は、主の処理に付随する後始末の失敗だけ。その場合も、主の処理の結果を変えずに、必ずログに残す

### 変更の範囲

- 依頼されていない大規模なリファクタリングを同時に行わない
- 既存の公開API・型・動作を、理由なく変えない
- 新しいライブラリを、利用者の承認なしに追加しない。バージョンは必ず固定する（`^`・`~`・`latest`を使わない）

## 作業するときの心がけ

- 変更の前に、既存のコードの設計・命名・ディレクトリ構成を確認し、既存のやり方に合わせる
- 変更の範囲は、要求された機能に必要な最小限にする
- 要求を満たす一番単純な方法を選び、今は必要のない将来のための仕組みを作らない。同じ処理・知識を複数の場所に書かないが、偶然似ているだけの処理を無理に共通化しない
- コメントは「なぜそうしたか」だけを書き、使われていないコードやコメントアウトしたコードを残さない
- 判断に迷ったら、Skill「知見」で該当する分野の知見を確認する。知見はルールより優先しない。当てはまらない場合は、根拠を示して判断し、記録する

## プロジェクト固有のルール

- このプロジェクト固有のルールは`docs/project-rules.md`にある。作業を始める前に読む
- このファイル（`AGENTS.md`）やSkillなど、ハーネスが管理するファイルに、プロジェクト固有のルールを書き足さない。ハーネスを更新したときに消えるため
- 新しいルールが必要になったら、次の問いで分ける。迷ったら`docs/project-rules.md`に書く
  1. このアプリの業務や中身を知らないと書けないルール → `docs/project-rules.md`
  2. 特定の技術を使うときにだけ必要なルール → ハーネス（技術プロファイル）への提案
  3. どのアプリでも守るべきルール → ハーネス（共通仕様）への提案
- ハーネスのルールより緩めるルールは、理由をADRに記録し、利用者の承認を得てから`docs/project-rules.md`に書く

## ハーネスの改善の提案

作業の中で、このハーネス（`AGENTS.md`・Skill・テンプレート）の改善点に気づいた場合（ルールの食い違い、ルールに従った結果の手戻り、ルールの不足、分かりにくい書き方、動かない手順等）は、次のようにする。

- ハーネスのルール・Skill・テンプレートを**自分で直さない**。改善の提案として記録するだけにする
- `.harness/config.yaml`の`feedback_target`で決めた場所に、`harness-feedback`のラベルを付けたIssueを、Issueテンプレート「ハーネスの改善の提案」で作る。`harness`（ハーネスのリポジトリ）の場合は、作る前に利用者の承認を得る
- プロジェクト固有の機密・秘密情報・個人情報を書かず、事象を一般化して書く
- 記録したことを、作業の報告の中で利用者に伝える

## 完了の定義

次のすべてを満たすまで、完了と報告しない。

1. Issueの受け入れ条件をすべて満たしている
2. 該当するテストと品質チェックが、プロジェクト全体に対して通っている
3. 変更に関係する文書（要件定義書・API仕様・`docs/tech-stack.md`・ADR・README）を更新している
4. PRにIssueを紐付けている

## Skill（必要なときに読み込む）

Skillの置き場所：Claude Codeは`.claude/skills/<フォルダ>/`、Codexは`.agents/skills/<フォルダ>/`（中身は同じ）。役割ごとのエージェントは、Claude Codeは`.claude/agents/`、Codexは`.codex/agents/`にある。

| Skill | フォルダ | 読み込むとき |
| --- | --- | --- |
| 実装の進め方 | `implementation-process` | 要件定義・Issueへの分割・Issueの実装を始めるとき |
| バックエンド | `backend` | バックエンドの設計・実装・レビュー、DB・トランザクション・バッチ処理、外部APIの呼び出し |
| フロントエンド | `frontend` | フロントエンドの設計・実装・レビュー、API通信（Axios） |
| テスト | `testing` | テストの作成・実行、テスト環境の構築と後始末、E2Eの不具合調査、外部APIのモック |
| セキュリティ | `security` | 認証・認可・個人情報・入力チェック・SQLの組み立て・ファイルのアップロードを扱うとき |
| エラー応答・API | `error-api` | APIの設計、エラー応答・例外処理の実装 |
| 環境・デプロイ | `env-deploy` | Docker・IaC・デプロイ・本番DBの変更を扱うとき |
| レビュー | `review` | 計画レビュー・コードレビュー |
| 知見 | `knowledge` | 判断に迷ったとき、PRの「知見」の欄を書くとき |
