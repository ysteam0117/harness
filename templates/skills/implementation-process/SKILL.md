# 実装の進め方

作業の過程と結果は、すべて日本語で書く。

## 全体の流れ

| 段階 | 担当 | 成果物 |
| --- | --- | --- |
| 1. 要件定義 | 統括（利用者と対話） | 要件定義書 |
| 2. プロトタイプ | 統括（洗い出し）・`prototyper`（作成） | 画面の動きを再現したプロトタイプ |
| 3. Issueへの分割 | 統括 | 親Issue・子Issue（受け入れ条件付き） |
| 4. Issueごとの実装 | 役割ごとのエージェント | 実装・{{implement_deliverable}} |

要件定義とIssueへの分割は、利用者との対話が必要なため、統括が担当する。エージェントは途中で利用者に質問できないため、これらを任せない。

## 1. 要件定義

- Superpowersの`brainstorming`を使い、利用者と対話しながら、目的・想定する利用者・機能・範囲（作らないもの）・受け入れ条件を決める
- 質問は一度に多くせず、選択肢と推奨案・その理由を示して、利用者に決めてもらう
- 決まっていないことは推測で埋めず、「未決定」として要件定義書に書く
- 技術・ライブラリの選定は利用者が決める。AIは候補・理由・バージョンを示す
- 要件定義書に書いて合意を得るまで、実装に進まない

### brainstormingを使うときの注意

Superpowersの`brainstorming`を使ってよいが、次の2点はこのプロジェクトの決まりを優先する。

- 成果物（設計書）は、`docs/superpowers/specs/`ではなく、要件定義書（`docs/requirements.md`）に書く
- 設計の承認の後は、`writing-plans`に進まない。次は「2. プロトタイプ」に進む。`writing-plans`は、Issueごとの実装の計画で使う

### 判定の確認項目

要件定義の中で、次の項目を必ず確かめる。CLIはこれらを聞かずに「未定」として生成するため、`.harness/config.yaml`の回答が「未定」のものは、ここで利用者に質問して決める。質問するときは、下の例のように、このアプリに当てはめた具体例を示す。決まっているものも、要件と食い違っていないかを確かめ、変わった場合は`.harness/config.yaml`と要件定義書の「このプロジェクトの判定結果」を更新する。

| # | 確かめること | 回答によって必要になること |
| --- | --- | --- |
| A | 個人情報を扱うか（特に配慮が必要な情報を含むか） | ASVSのレベル、ログの保存期間、不審な試行の通知 |
| B | 管理者の機能があるか | 管理者のMFAの要否、権限の管理、監査ログ |
| C | 取り消しにくい重要な操作（決済・公開範囲を広げる・データの削除・権限の変更）があるか。公開範囲を広げるとは、資料・記事・ファイル等を、今より広い範囲（ほかの部署・社外・誰でも）に見せる操作（社内アプリで他部署に見せる場合も含む） | 重要な操作の前の再認証、「影響大」として扱う範囲 |
| D | 複数の人が同じデータを編集するか | 所有者・共同編集者の権限、更新の衝突の検知 |
| E | 組織の単位でデータを分けるか | 組織をまたいで見えないことのテスト |
| F | ほかの利用者の変更をすぐ届ける必要があるか | 方式（WebSocket等）をADRで決める |
| G | 止まってはいけないか | 冗長な構成・カオステスト・バックアップの頻度をADRで決める |

- 決まるまでは、安全側（扱う・ある・する）として扱う
- 決まったら、`.harness/config.yaml`と要件定義書を更新し、`harness update`で、有効にするルール・Skillに反映する
- ASVSのレベル：個人情報・管理者の機能・重要な操作がすべてない → レベル1。いずれかがある → レベル2。特に配慮が必要な情報または決済がある → レベル3を検討してADRに記録する
- 大きな判断は、背景と理由をADR（`docs/adr/`）に残す

### 機能に付随する項目の確認（認証・アップロード）

認証方式とファイルのアップロードは、機能要件に付随するため、CLIは聞かずに「未定」として生成する（認証のひな形・R2の設定も出さない）。要件定義の中で、次を利用者に確かめて決める。要件定義書の「要件定義で決める機能の項目」にも、同じ項目を載せている。

| 確かめること | 決めるときに従う共通仕様 |
| --- | --- |
| 認証方式（なし・アプリ独自認証・OIDC・併用）。OIDC・併用のときは外部IdP | C-12〜C-20（Skill「セキュリティ」）。認証の有無で、管理者の機能（B）・共同編集（D）の判定も変わるため、F-26のASVSのレベルの判定を見直す |
| ファイルのアップロードを使うか。使うときはファイルの種類（画像・動画・文書） | C-63（非公開をデフォルトにし、サイズ・形式・名前・位置情報の安全対策を行う） |

- 決まったら、`.harness/config.yaml`の`answers`（`auth`・`idp`・`file_upload`・`file_kinds`）と要件定義書を更新し、判定・ルールの記録を正しく保つ。F-26の判定の見直しも、同じときに行う
- 実装は、ひな形を生成し直さず、アプリの中で、Skill「セキュリティ」などのルール（C-12〜C-20、ASVS、C-63）に沿って行う
- 認証を使うときは、利用者とセッションを保存するDBが必要になる（C-16）。DBなしの場合は、要件定義でDBも決める

## 2. プロトタイプ

画面のあるプロジェクトでは、要件定義書の合意の後、Issueへの分割の前に、動きを確かめるプロトタイプを作る。

1. **洗い出し**（統括、上位のモデル）：要件定義書から、画面の一覧・画面の移り変わり・画面ごとの状態（読み込み中・データあり・データなし・エラー）と操作を洗い出し、利用者に承認を得る
2. **作成**（`prototyper`）：洗い出しに沿って、`prototype/`にHTML・CSS・JavaScriptだけで作る
3. **確認**：利用者がブラウザで動かして確かめる
4. **反映**：気づいた点で要件定義書を更新し、必要ならプロトタイプを直す。利用者が承認するまで3〜4を繰り返す

- ビルドの道具・フレームワーク・外部のライブラリは使わず、ファイルを開くだけで動くようにする
- バックエンドには接続せず、架空のデータで再現する。秘密情報・実在の個人情報を含めない
- 操作の後に、再読み込みせずに表示が変わることも再現する
- プロトタイプは使い捨てとし、本番のコードに流用しない

## 3. Issueへの分割

- 機能ごとに親Issueを作り、作業領域（DB・バックエンド・フロントエンド・その他）ごとに子Issueに分ける。必要のない作業領域の子Issueは作らない
- 子Issueには次を書く
  - 対象の作業領域
  - 参照する要件定義書の箇所・文書
  - 番号付きの受け入れ条件（`AC-1`、`AC-2`…）
  - 依存するIssueの番号と、着手の順番
- 1つの子Issueは、単独でレビュー・マージできる最小の単位にする
- 作成する前に、分割の一覧を利用者に示して承認を得る

## 4. Issueごとの実装

### 役割

| 役割 | エージェント | 触ってよいもの |
| --- | --- | --- |
| 統括 | このセッション | — |
| プロトタイプの作成 | `prototyper` | `prototype/`のみ |
| 計画 | `planner` | 読み取りのみ |
| 計画レビュー | Codex、または`plan-reviewer` | 読み取りのみ |
| テスト | `test-writer` | テストのファイルのみ |
| 実装 | `implementer` | 計画にあるファイルのみ。テストは変更しない |
| 品質チェック | `quality-checker` | 読み取りと実行のみ |
| コードレビュー | Codex、または`code-reviewer` | 読み取りのみ |
| ドキュメント | `doc-writer` | 文書のみ |

### 変更の大きさと起動する役割

| 大きさ | 基準 | 起動する役割 |
| --- | --- | --- |
| 小 | 誤字の修正・文書だけの変更・設定値1か所の変更など、動作のロジックを変えないもの | 実装 → 品質チェック → コードレビュー |
| 通常 | 小・影響大のどちらにも当たらないもの | すべての役割 |
| 影響大 | 認証・認可・個人情報・データ移行・DBスキーマの破壊的変更に関わるもの | すべての役割。テストの設計とコードレビューは上位のモデルで行う |

どの大きさでも、完了の定義と、テスト・品質チェックが通ることは省略しない。判断した大きさと理由を、{{issue_record_place}}に書く。

### 手順

1. **着手の前に**：Issueの依存関係を確認する。最新の`main`からブランチを作る
2. **計画**：`planner`に、Issueの受け入れ条件・参照する文書・制約を渡して、計画を作らせる。計画には「従うルール」（`AGENTS.md`の表で該当するSkillと、守るルール）を必ず含める。欠けていれば作り直させる
3. **計画レビュー**：計画を、実装とは別のAIでレビューする（Skill「レビュー」）。重大な指摘があれば計画を直して再レビューする
4. **テスト**：`test-writer`に、確定した計画と受け入れ条件を渡して、テストを先に書かせる
5. **実装**：`implementer`に、計画とテストの一覧を渡して実装させる。実装はテスト駆動開発（Red → Green → Refactor）で進める
   - Red：手順4で、テストが実装がないために失敗することを確かめ済み
   - Green：テストが通る最小限の実装をする
   - Refactor：テストが通る状態を保ったまま整理し、テストを実行し直す
6. **品質チェック**：`quality-checker`に実行させる。失敗したら、原因の見立てを`implementer`に渡して直させる
7. **コードレビュー**：別のAIでレビューする（Skill「レビュー」）。指摘は妥当性を確認してから`implementer`に直させ、品質チェックをやり直す
8. **ドキュメント**：`doc-writer`に、関係する文書の更新と{{knowledge_record_place}}の案を作らせる
9. **動作確認**：コミットの前に止まり、利用者に動作確認を依頼する。確認の手順と、確認してほしい受け入れ条件を示す。大きさが「小」の場合は、省略してよいかを確認する
10. {{commit_merge_step}}

### エージェントの呼び出し方

| AI | エージェントの定義 | 呼び出し方 |
| --- | --- | --- |
| Claude Code | `.claude/agents/<名前>.md`（`planner`・`plan-reviewer`等） | `Agent`ツールで、エージェントの名前を指定して呼び出す |
| Codex | `.codex/agents/<名前>.toml`（`planner`・`plan_reviewer`等） | Codexは、明示的に頼まないとエージェントを起動しない。「`planner`エージェントを起動して、…を計画させる」のように、名前を指定して起動を指示する |

### エージェントへの渡し方

- 会話全体ではなく、目的・対象のファイル・制約・完了条件など、必要な情報だけを渡す
- レビューの役割には、実装の経緯を渡さない
- 指示の最後に「作業の過程と結果は、すべて日本語で書くこと」を入れる

### レビューの回数

- 計画レビュー・コードレビューとも最大3回。1回目は全体、2回目以降は指摘した箇所とその関連部分に絞る
- 3回目でも重大な指摘が残る場合は、止まって利用者に判断を求める
- ただし、データ破損・認証の回避・情報漏えいにつながる指摘は、解消するまで続ける
- 合意済みの設計判断（ADR等）が再び指摘された場合は、回数に数えず、コードも変えない

### 上位のモデルへの切り替え

| 条件 | 対応 |
| --- | --- |
| 認証・認可・個人情報・データ移行・重要な業務ルールに関わる | テストの設計・コードレビューを上位のモデルで行う |
| 複雑な新規設計や、重大な設計判断が必要 | 計画を上位のモデルで行う |
| 同じ失敗を2回直しても解消しない | 上位のモデルに切り替える。または計画に戻る |

### 記録（{{issue_record_place}}に残す）

- 実装計画
- 計画レビュー・コードレビューの結果（指摘の数・採用した数・採用しなかった指摘と理由・どのAIでレビューしたか）
- 品質チェックの結果
- 実装中に計画を変えた場合は、変えた内容と理由（その都度）

## 立ち止まる条件

次の場合は、必ず止まって利用者の判断を仰ぐ。

- 利用者による動作確認が必要な工程に着いた
- 文書と実装の食い違いを見つけた
- 新しいライブラリの追加など、共通のルールに影響する変更が必要になった
- Skillのルールに従えない、またはルールが決まっていない書き方が必要になった
- 「要調査」「未検証」とされている項目に着手する
- レビューを重ねて、Issueが単独でレビュー・マージできる大きさを明らかに超えた。この場合は「厳密にやる／範囲を縮める／後回しにする」の選択肢と、範囲を縮めた場合に何を名乗れなくなるかを示す
- 実装中に要件の追加・変更が必要になった（要件定義に戻る）
- Claude Codeが使えなくなった（Codexに切り替え、Issueに記録する。GPT-6 Solを主に使う）
- 破壊的な操作が必要になった

## 複数のIssueを続けて進める条件
