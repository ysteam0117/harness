# テスト

作業の過程と結果は、すべて日本語で書く。

## 必須のテスト

| テスト | 必須になる条件 | 対象 |
| --- | --- | --- |
| 単体テスト | 常に必須 | Service・Mapper・Hooks・Utilsなどのロジック |
| 結合テスト | バックエンドがある場合 | ControllerからDBまで通したAPIの動作（認可・エラー応答を含む） |
| E2E | 画面がある場合 | 画面からバックエンドまで通した主要な利用の流れ |

- 該当しないと判断して省略する場合は、理由を{{issue_or_pr_record}}に書く
- 機能の変更には対応するテストを追加・更新し、不具合の修正には再発を防ぐテストを追加する

## テストの設計

- 期待する結果は、受け入れ条件・仕様（テストオラクル）から決める。実装と同じ処理から導き出さない
- 受け入れ条件が曖昧で期待する結果を決められない場合は、テストを作り込む前に確認する
- テスト名または説明に、Issue番号と受け入れ条件の番号を書く（例：`#12 AC-2: 誤ったパスワードでは401を返す`）。{{test_list_place}}に、受け入れ条件ごとの対応するテストの一覧を載せる
- 成功だけでなく、境界値・異常系・認可（許可されない主体）・エラー応答を含める
- Reactのコンポーネントは、Testing Libraryで利用者の操作に基づいて検証する。内部の実装だけを検証するテストに頼らない
- 認証・認可・個人情報・重要な業務ルールでは、ミューテーションテストでテストの検出力を確かめる

## してはいけないこと

- テストを通すことだけを目的に、実装を要求と違う動作に変えない
- テストを無効化・スキップしない。期待結果を根拠なく弱めたり変えたりしない
- 原因が分からないまま、待ち時間の延長・再試行でテストを通さない
- テスト結果だけをよく見せる、テスト専用の分岐を本番のコードに入れない

## 再現性

- 同じコミット・依存関係・初期状態から実行したとき、結果が安定するようにする
- テストの実行順序や、前回の実行の状態に依存させない。時刻・乱数は必要に応じて固定する
- 通常の品質チェックではテストを1回実行し、自動で再試行しない。再実行で成功しても、初回の失敗を成功扱いにせず、不安定なテストとして原因を調べる

## テストデータ

- 架空のデータだけを使う（メールアドレスは`example.com`、名前は`testuser_001`等）。実データ・実在の個人情報・本物の認証情報を使わない
- 識別用の接頭辞・タグ（`testuser_%`、`[E2E_TEST]`等）を付け、それを条件に削除するスクリプトとセットにする
- 本番DBに接続しうる設定でテストを実行しない
- 結合テスト：各テストはシード投入直後の状態から始め、テスト中に変えたデータは終わったら元に戻す
- E2E：実行を始めるときにテスト用DBを空にして作り直す。シナリオで使うデータは、シナリオ用のシードデータとしてファイル（`e2e/seeds/<シナリオ名>`）に固定値で書き、シナリオの準備の中でAPI等を使って入れる。共通のシードはシナリオの中で書き換えない

## 外部APIのモック

- どのテストでも、本物の外部APIを呼ばずにモックを使う。E2Eでは、モックのサーバーに接続先を設定で切り替える
- モックの応答は公式の仕様に沿って作り、エラー・`429`・時間切れも再現する
- 本物との食い違いの確認は、提供元のテスト用環境がある場合に限り、利用者の承認を得て、最小限の回数で行う
- 性能試験・負荷試験で本物の外部APIを呼ばない

## E2E

- Playwrightで実行する
- 今回の変更を検証するE2Eが実在するかを、シナリオ名ではなく中身で確かめる。無ければ追加し、追加できない場合は理由と代わりの担保を報告する。画面がまだ無い場合は、API層のE2E（動いているAPIを直接呼ぶ）で代替する
- Web E2Eでは、エラーレベルのコンソール出力と、処理されなかった例外があればテストを失敗にする。意図した異常は、そのテストの中だけで対象を絞って許可する
- データを変える操作の後は、**再読み込みせずに**、関係する表示（一覧・詳細・件数・ステータス等）が変わっていることを確かめる
- 画像は、実際に読み込めたか（幅が0より大きいか等）で確かめる
- レート制限のあるAPIの呼び出しは最小限にし、レート制限そのものはバックエンドのテストで確かめる

### E2Eが失敗したときの調べ方

1. Playwrightのトレース・スクリーンショット・コンソールの出力を確認する
2. Chrome DevToolsで同じ操作を再現し、コンソールのエラー・通信の中身から原因を突き止める
3. 画面の見た目や操作の流れを利用者と確かめる必要がある場合は、Orcaブラウザを使う

- 原因が、フロントエンド・バックエンド・テストコード・テストデータ・テスト環境のどこにあるかを切り分ける
- 原因を特定してから直す。突き止めた原因と修正の内容を{{issue_or_pr_record}}に書く
- Chrome DevToolsやOrcaを使えない場合は、Playwrightのトレースと画面表示ありの実行（headed）で調べる

## テスト環境の構築と後始末

- 環境別の起動は `npm run test` と `npm run dev:test` を使う。手元の `.env.test` と `APP_ENV=test` が選ばれ、親プロセスの接続設定は引き継がれない
- PostgreSQLの検証DBはループバック上の接続先かつ名前が `_test` で終わるものを使う。D1/R2のローカル状態は開発用から分離される。これは任意の外部接続やOS権限を含む安全保証ではない
- テスト用PostgreSQL/Composeの起動・停止は `npm run docker:up:test`・`npm run docker:down:test`、DB操作は `db:*:test` のscriptsを使う。Vitest WorkersのD1は一時的な隔離状態を使う

- 手順は`docs/testing/`に、テストの種類ごとに書いてある（必要なもの・構築の手順・確認の方法・実行方法・後始末・よくある失敗と対処）
- 構築はスクリプトで1つのコマンドで行い、CIでも同じスクリプトを使う
- 始める前に、使うポートが空いているかを確かめる。使われている場合は別のポートで続けず、何が使っているかを確かめる
- テストが失敗したら、まず環境が原因でないかを切り分けてから、実装を調べる。環境が原因の失敗は「よくある失敗と対処」に追記する
- テストの工程が完了したら、起動したもの（サーバー・ブラウザ・エミュレーター・コンテナ等）をすべて止め、ポートが解放されたことを確かめる。原因の調査中は起動したままでよい。利用者に引き渡すときは、何が動いているかを報告する
- 起動したもの（プロセス・コンテナ・ポート）を記録しておき、作業が途切れても自分が残したものだと分かるようにする
- 自分が起動したか分からないプロセスは、確認せずに止めない

## 品質チェック

- 品質チェックとテストは、手元とCIで共通の1つのコマンド（{{check_command}}）で、プロジェクト全体に対して実行する
- テストを追加・変更した後にも、品質チェックをやり直す
- CIでも、開発環境と同じコンテナ・同じバージョンを使う

## 性能の目標

| 対象 | 目標 | 補足 |
| --- | --- | --- |
| LCP（読み込みの速さ） | 2.5秒以下 | Core Web Vitalsの「良好」。75パーセンタイル、モバイルとデスクトップを分けて判定 |
| INP（操作への反応） | 200ミリ秒以下 | 同上 |
| CLS（表示のずれ） | 0.1以下 | 同上 |
| APIの応答時間 | p95で500ミリ秒以下 | 目安（知見の仮説）。重い処理は個別に決める |
| 初回に読み込むJavaScript | 圧縮後200KB以下 | 目安（知見の仮説） |

- 測り方は、Skill「知見」の「実測を根拠にするとき」に従う。目標を満たしているかを検証環境で定期的に測る

## 壊すことを目的としたテスト

| 種類 | 内容 | 道具 | 時期 |
| --- | --- | --- | --- |
| 異常な入力 | ランダムな大量の入力で、落ちないこと・エラー応答が正しいことを確かめる | fast-check | 毎回 |
| 同時実行 | 同じ操作を同時に何回も送り、二重登録・数値の食い違いが起きないことを確かめる | テストの道具 | 毎回（重要な操作） |
| 障害を起こす | 外部API・DBの失敗・遅れ・停止をモックで作り、データが壊れないことを確かめる | MSW等 | 毎回 |
| 負荷・限界 | アクセスを増やし、遅くなる点・壊れる点と、戻るかを調べる | k6 | リリース前（検証環境） |
| セキュリティ | 下の「セキュリティのテスト」を参照 | — | — |

- 負荷・セキュリティのテストは、本番に対して行わない。検証環境だけで、利用者の承認を得てから行う
- 外部API・外部のサービスに、負荷や攻撃を向けない
- 見つかった弱点は、再発を防ぐテストとして毎回のテストに加える
- カオステスト（わざと一部を止めるテスト）は、可用性の要件があり、自分たちで冗長な構成を組んでいる場合だけ検討する。Cloudflare Workers・D1では行わない

## セキュリティのテスト

| 種類 | 道具 | 時期 | 合否 |
| --- | --- | --- | --- |
| コードを見るテスト | Semgrep | 毎回（品質チェック） | 重大度が高い指摘が0件 |
| 秘密情報の混入 | gitleaks | 毎回（品質チェック） | 検出が0件 |
| 依存関係の脆弱性 | `npm audit`、OSV-Scanner | 毎回（品質チェック） | 本番の依存で高・重大が0件 |
{{dependency_update_row}}
| 攻撃を試す | OWASP ZAP | リリース前（検証環境） | 高リスクの指摘が0件 |
| APIの異常な入力 | Schemathesis | リリース前（検証環境）。ローカルでも可 | 500エラー・仕様と違う応答が0件 |
| ペネトレーションテスト | 手動（OWASP ZAPの手動の機能等） | {{pentest_requirement}} | 見つかった問題がすべて直り、再テスト済み |

- 攻撃を試すテストとペネトレーションテストは、本番に対して行わない。検証環境だけで、利用者の承認を得てから行う
- 外部API・外部のサービスに攻撃を向けない
- 誤検知と判断した指摘は、除外の設定に理由を書いて除外し、{{pr_equivalent}}に記録する。理由のない除外はしない
- 見つかった弱点はIssueにして直し、再発を防ぐテストを毎回のテストに加える

### ペネトレーションテストの進め方

1. `docs/testing/pentest-plan.md`に、範囲・観点・道具・期間・止める条件・テスト用の利用者を書き、利用者の承認を得る
2. シナリオは、要件・API仕様・権限の表・観点の一覧と、実装のコードをすべて見て作る。攻撃者の立場で、利用者の種類ごとに許されない操作ができないか、要件の制約（回数・期限・1回限り等）を破れないか、すべての入力（パス・クエリ・本文・ヘッダー・Cookie）を変えられる前提で考える
3. ASVSのレベル（{{asvs_level}}）の項目に沿って、認証・認可・セッション・入力の確認・ファイルのアップロード等を確かめる。特に、他人のデータが見える・操作できる、組織をまたいでデータが見える、といった認可の不備を中心に見る
4. 道具の実行は、利用者の承認を得てから行う。実行の判断は利用者が行う
5. 結果を手順書に記録し、見つかった問題はIssueにする。直した後に、同じ手順で再テストする
