# 環境・デプロイ

作業の過程と結果は、すべて日本語で書く。

## 開発環境（Docker）

- バックエンドとDBの開発環境は、Docker Composeのコンテナで動かす
- Docker Composeのプロジェクト名はアプリ名（`{{app_name}}`）、コンテナ名は`{{app_name}}-<役割>`（例：`{{app_name}}-backend`）にする
- DBの認証情報などは`docker-compose.yml`に書かず、`.env`から読み込む
- {{dev_env_notes}}

## 環境の分け方

| 環境 | 使うとき |
| --- | --- |
| 開発 | 実装中の動作確認 |
| 検証 | テスト（本番と同じ構成での確認、受け入れ確認） |
| 本番 | クライアント・利用者が実際に使う |

- 3つの環境は同じIaCのコードから作り、設定値だけを分ける
- DB・秘密情報・ドメインは環境ごとに分ける。開発・検証から本番のDBに接続しない
- 本番のデータを開発・検証に持ち込まない

## IaC（Terraform）

- 本番環境は、管理画面での手作業ではなく、`infra/`のTerraformのコードで作る
- 管理画面で直接設定を変えない。緊急で変えた場合は、同じ変更をコードに反映する
- 秘密情報はコードに書かず、環境変数や秘密情報の管理機能から渡す。状態ファイル（`terraform.tfstate`）はコミットしない
- 変更はPRで`terraform plan`の結果を確認し、**利用者の承認を得てから**`terraform apply`する

## デプロイ

- デプロイは自動化せず、開発リーダー（個人開発の場合はその個人）の承認を得てから行う。AIは承認なしにデプロイしない
- 承認を依頼するときは、次を示す
  - デプロイする内容（バージョン・含まれるPR）
  - DBの変更の有無と内容
  - 切り戻しの方法
- 本番へは、検証環境で確認済みの同じバージョンをデプロイする
- デプロイしたバージョンを記録し、前のバージョンをすぐに再デプロイできる状態を保つ

## バージョンの付け方

- アプリのバージョンは`MAJOR.MINOR.PATCH`で付ける。以前と両立しない変更はMAJOR、機能の追加はMINOR、意味の変わらない修正はPATCHを上げ、下の桁は`0`に戻す
- コミットメッセージの`feat!:`（両立しない変更）・`feat:`・`fix:`を、上げる桁の判断に使う

## 切り戻し

- 不具合が出た場合は、前のバージョンを再デプロイすることを基本とする

## 本番DBの変更

前のバージョンに切り戻しても動くように、次の3段階に分ける。

1. **追加**：新しいカラム・テーブルを追加する
2. **移行**：新しいバージョンをデプロイし、データを移す。古い構造も残す
3. **削除**：切り戻す可能性がなくなったことを確かめてから、別のデプロイで古い構造を削除する

- カラムの削除・名前の変更・型の変更を、1回のデプロイで行わない
- 本番DBにマイグレーションを適用する前に、その時点に戻せること（復元ポイント・バックアップ）を確かめ、利用者の承認を得る

## バックアップと復元

- DBのバックアップは、使うサービスで可能な限り行う（{{backup_notes}}）
- 復元の手順を文書にし、検証環境で実際に復元できることを確かめておく

## バッチの手動実行

- 本番でバッチを手動で実行・再実行する場合は、利用者の承認を得る
