## 層構成

| 層 | 責務 | してはいけないこと |
| --- | --- | --- |
| Controller | リクエストの受付・入力チェック・レスポンスの返却 | 業務ロジックを書く、データアクセス層を直接呼ぶ |
| Service | 業務ロジック・トランザクションの範囲の決定 | HTTPに関する処理を書く |
| Repository | Serviceから見たデータの出し入れ。DBの実装方式をServiceから隠す | 業務ロジックを書く |
| DAO | SQLの実行に専念する（下記の条件の場合だけ置く） | 業務ロジックを書く |
| DTO | 層の間・APIでやり取りするデータの入れ物 | ロジックを持つ |
| Entity | DBのテーブルに対応するデータ | Controllerより外（画面・API）に出す |
| Mapper | Entity ⇔ DTO の変換 | 変換以外の処理を書く |
| Gateway | 外部APIの呼び出し（下記「外部API」） | 業務ロジックを書く |

### RepositoryとDAOの使い分け

| 状況 | 構成 |
| --- | --- |
| 単純なCRUDのみ | Service → Repository |
| 複雑なSQLだけを扱う | Service → DAO |
| ドメインモデルとDBモデルを分離したい | Service → Repository → DAO |
| 複数のDAOをまとめて扱いたい | Service → Repository → 複数のDAO |
| DBの実装方式をServiceから隠したい | Service → Repository → DAO |

選んだ構成と理由を、計画（{{issue_record_place}}）に書く。

## 命名と整形

- 整形は自動整形ツールに任せ、書式を人やAIが判断しない
- ファイル・ディレクトリは`kebab-case`、DAOの生SQLは`*.sql.ts`、マイグレーションは`番号_snake_case.sql`（例：`0003_add_users_email_index.sql`）
- 変数・関数は`camelCase`、型は`PascalCase`、定数・環境変数は`UPPER_SNAKE_CASE`
- DBのテーブル・カラムは`snake_case`で、テーブルは複数形（例：`users`、`created_at`）

## DBアクセス

- 必要な列だけをDTOで取得する。Entityを丸ごと取得して画面やAPIに渡さない
- N+1を避ける。一覧・検索では、SQLの発行数が件数に比例して増えないことを確かめる
- 通信回数を減らすためだけに、巨大で複雑なSQLに一本化しない
- 検索・一覧・結合を行う代表的な処理は、実行計画（`EXPLAIN`等）でインデックスが使われているかを確かめる。全件走査を一律に不具合と断定せず、実測で判断する
- インデックスは、実際の検索条件・結合条件・並び順を根拠に設計し、変更はマイグレーションに含める
- SQLに値を入れるときは、必ずパラメータで渡す（Skill「セキュリティ」）

## マイグレーションとテスト用DB

- スキーマの変更は、すべてマイグレーションファイルで行う。DBを直接操作して変えない
- 一度適用したマイグレーションファイルは書き換えない。修正は新しいファイルを追加する
- ORMのスキーマ定義とマイグレーションの内容を食い違わせない
- 本番DBの変更は後方互換を保ち、「追加 → 移行 → 削除」の段階に分ける。削除などの破壊的変更を1回のデプロイで行わない
- テスト・CIは「空のDBを用意 → マイグレーションを最初から適用 → シードを投入 → テスト」の順で行う。シードは必要最低限・固定値にする

## トランザクション

- 範囲はService層で決める。Repository／DAOは自分でトランザクションを始めない
- トランザクションは短くし、中で外部APIの呼び出し・メール送信・ファイルのアップロードを行わない
- DBと外部の処理をまたぐ場合は、「処理中で記録 → 外部の処理 → 完了に更新」のように順番と失敗時の後始末を決める
- 複数の人が同じデータを更新し得る場合は、バージョン番号等で衝突を検知し、`409`を返す
- 二重に実行されると困る処理は、同じ要求を2回受けても結果が変わらないようにする
- 主の処理に付随する後始末の失敗は、主の処理の結果を変えずにログに残す
- デッドロックを起きにくくする：複数の行・テーブルは、いつも同じ順番（主キーの小さい順等）で更新する。条件に使う列にインデックスを付ける。ロックを待つ時間の上限を設定する
- デッドロック（またはトランザクションの衝突・混み合いのエラー）で失敗した場合は、トランザクション全体を最初から、回数の上限と少しずつ延ばした待ち時間を付けてやり直す。上限を超えたらエラーをもみ消さず`503`等で案内し、`WARN`でログに残す
- {{transaction_notes}}

## バッチ処理

- 何度実行しても結果が同じになるようにする（べき等性）
- 大量のデータは小分けにして処理し、途中から再開できるようにする
- 同じバッチを同時に2つ動かさない
- 開始・終了の日時、処理件数・成功件数・失敗件数をログとDBの実行履歴に残す
- 失敗は回数の上限と間隔を決めて再試行し、上限を超えたものは失敗の一覧に残して通知する
- 定期実行の時刻は設定上はUTCで書き、日本時間を文書に併記する
- 本番での手動の再実行は、利用者の承認を得て行う
- {{batch_notes}}

## ログ

- パスワード・トークン・セッションID・`Cookie`・`Authorization`の値・秘密情報・個人情報をログに出さない。共通のロガーで自動的に伏せ字にする
- JSON形式で1行1件、日時はUTCのISO 8601、リクエストIDを含める
- 各層から直接`console.log`を呼ばず、共通のロガーを使う
- ログイン・権限の変更・認可の拒否・管理者の操作などは監査ログ（`log_type: audit`）として記録する
- 利用者の入力をログに書くときは、改行などの制御文字を無害化する

## API設計

- URLは複数形の名詞（`/users/{id}`）で表し、操作はHTTPメソッドで表す
- GET・HEAD・OPTIONSで状態を変えない
- 日時はISO 8601（UTC）でやり取りする
- 一覧を返すAPIはページングを必須とする
- API仕様はOpenAPIで書く
- エラー応答はSkill「エラー応答・API」に従う

## 外部API

- 外部APIの呼び出しは、専用の層（`gateways/`）に集め、応答はアプリ用の型に変換してから使う
- 使うAPIのバージョンを明示して呼び出す。バージョンを指定しない呼び出しをしない
- 使っている外部API・APIとSDKのバージョン・仕様書へのリンクを`docs/tech-stack.md`に記録する
- 応答はZod等で検証し、想定外の形はエラーとして扱う
- バージョンを上げるときは専用の{{issue_and_pr}}で行い、モックを新しい仕様に合わせてからテストする
