# 知見

作業の過程と結果は、すべて日本語で書く。

## 知見とは

経験から来る「たいていはこうするとうまくいく」という判断基準。絶対のルールではない。

- `AGENTS.md`やSkillのルール（MUST・MUST NOT）が、知見より優先する
- 知見に当てはまらない場面では、実測や根拠に基づいて判断し、理由をADR（`docs/adr/`）に記録する

## 使い方

1. 判断に迷ったら、下の一覧から該当する分野の知見を読む
2. 知見の「状態」を確かめる（仮説／検証中／確立／廃止）。「仮説」は、まだ検証されていない考えとして扱う
3. 「対象」の条件（DB・ライブラリのバージョン・データ量等）が今回と合っているかを確かめる
4. 当てはまる場合は、知見に従う。当てはまらない場合は、根拠を示して判断し、記録する

## 実測を根拠にするとき

実測で言えるのは「その条件の下では効率が良い」までである。

- 何を良くしたいのか（速さ・メモリ・通信量・費用等）と、「意味のある差」の基準を、測る前に決める
- 比べる対象どうしは、同じ条件・同じ実行の中で複数回測り、中央値とばらつきを記録する。1回だけの結果で判断しない
- 測った条件（データ量・端末・ライブラリのバージョン・実行環境）を、結果と一緒に記録する
- 設計の知見（分割・共通化等）は、1回の測定では確かめられない。変更時に触ったファイル数・不具合の数・複雑度などの傾向で確かめる

## 記録するきっかけ

次の場面では、{{knowledge_record_place}}に記録する。

| きっかけ | 例 |
| --- | --- |
| 知見に当てはまらない判断をした | 3テーブルのJOINだが、Repositoryに書いた |
| 実測の結果が出た | SQLの発行数、実行計画、表示速度 |
| レビューで同じ種類の指摘が繰り返された | 別のAIから同じ指摘が続いた |
| 不具合の原因を突き止めた | E2Eの失敗の原因 |
| 手戻りが起きた | 設計を途中でやり直した |

## {{knowledge_record_place}}の書き方

該当しない項目は「なし」と書く。

```markdown
## 知見
- 参照した知見：db/sql-complexity（集計はDAOに分けた）
- 当てはまらなかった知見と、その理由・根拠：なし
- 新しい気づき（知見の候補）：一覧APIで、件数が1万件を超えるとページングなしでは応答が2秒を超えた（検証環境で測定、ADR-0005）
```

大きな判断や実測の詳細はADRに書き、{{pr_equivalent}}からリンクする。

## 知見の更新

- 知見のもとはハーネスのリポジトリにあり、月1回とハーネスの新しいバージョンを出すときに見直される
- このプロジェクトで得た知見を、ほかのプロジェクトでも使えるようにする場合は、利用者の承認を得てから、ハーネスのリポジトリへ{{harness_proposal_way}}。AIが勝手に知見を登録・変更しない
