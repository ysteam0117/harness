# エラー応答・API

作業の過程と結果は、すべて日本語で書く。

## エラーをもみ消さない

フロントエンド・バックエンド・SQLのいずれでも、エラーをもみ消したり、ごまかしたりしない。

- 何もしない`catch`（空の`catch`、コメントだけの`catch`）を書かない
- エラーを受け止めて、成功したように見える値（空の配列・`null`・既定値・`true`等）を返さない
- `Promise`の失敗を放置・無視しない（`await`し忘れ、`.catch(() => {})`等）
- エラーをログに出すだけで、処理を成功として続けない
- SQLのエラーや結果を無視しない。更新・削除した件数を確かめるべき処理で、件数を確かめずに成功扱いにしない。`INSERT OR IGNORE`・`ON CONFLICT DO NOTHING`は、意図と理由を書いた場合だけ使う

その場で対処できる場合（再試行・代わりの処理等）だけ、その場で処理する。対処できない場合は受け止めずに呼び出し元へ伝え、最終的な処理はグローバル例外ハンドリングに任せる。エラーの種類を変えて伝える場合は、元のエラーを含める。

例外は、主の処理に付随する後始末の失敗だけ。その場合も、主の処理の結果を変えずに、必ずログに残す。

## グローバル例外ハンドリング

### バックエンド

- アプリ全体で1つのエラーハンドラ（{{error_handler}}）を用意し、処理しきれなかったエラーはすべてここで受け止める
- 想定できるエラー（入力の誤り・権限不足・リソースなし・競合等）は、アプリ独自のエラーの型で投げ、エラーハンドラでHTTPステータスとエラーコードに変換する
- 想定していないエラーは、利用者には`500`と一般的なメッセージだけを返し、詳細はリクエストIDと一緒にログに記録する
- Controller・Serviceで、エラーハンドラと同じ変換を個別に書かない

### フロントエンド

- API通信のエラーは、Axiosの応答のインターセプターで共通のエラーの形に変換する（Skill「フロントエンド」）
- 画面の表示中のエラーはError Boundaryで受け止める
- 処理されなかった`Promise`の失敗・`window`のエラーも、全体の受け止め口でログに記録する

## エラー応答

- HTTPステータスはエラーの大分類として、RFC 9110に沿って使い分ける
- 細かい原因は、アプリ独自の安定したエラーコードで表す。HTTPステータスとエラーコードを混同しない
- エラー応答の形式（項目名・構造）をアプリ全体で統一し、OpenAPIに書く
- 各機能で期待するステータス・エラーコード・メッセージは、API仕様で明示する。RFCの名前や例から推測しない

| 状況 | ステータス |
| --- | --- |
| 認証情報がない・無効 | `401` |
| 認証済みだが許可されない | `403`（ログイン切れとして扱わず、ログアウトや遷移をしない） |
| リソースがない、または存在を開示しない | `404` |
| 現在の状態と競合する（更新の衝突等） | `409` |
| 形式は正しいが内容を処理できない | `422` |
| 要求が多すぎる | `429`（`Retry-After`を付ける） |
| 予期しないサーバーのエラー | `500` |

## 利用者向けのメッセージ

- 何が起きたかと、次に取れる行動（入力の修正・再試行・再ログイン・問い合わせ等）が分かる表現にする。「エラーが発生しました」だけの表示を避ける
- 内部の例外・スタックトレース・SQL・秘密情報・ほかの利用者の情報を、メッセージや応答に含めない
- 権限の変更などで使える機能が変わった場合は、関係する画面の近くで、その変化と次の行動を知らせる

## 401を受けた場合（フロントエンド）

- 認証の更新手段があれば一度だけ試す。元の要求の再送は、二重に実行されないと確かめられる場合だけ一度行う
- 更新できない場合は認証状態を解除し、ログイン画面へ一度だけ遷移する。複数の要求が同時に`401`になっても、更新・遷移を重複させない
- ログイン後の戻り先は、許可したアプリ内の画面に限る

## テスト

- 期待するステータス・エラーコード・応答の形式・データが変わっていないことを、要件・API仕様で決めた値と照合する。実装が返した値をそのまま期待値にしない
- 想定していないエラーで、詳細が応答に含まれないこと、ログに記録されることを確かめる
