# レビュー

作業の過程と結果は、すべて日本語で書く。

## レビューするAIの選び方

見落としの重なりを減らすため、次の優先順位で選ぶ。

1. **原則**：計画・実装を担当したAIとは別の会社のAIでレビューする（Claude Codeで実装したらCodex、Codexで実装したらClaude Code）
2. **1が使えない場合**：同じ会社の別のモデルで、新しい会話（計画や実装の経緯を渡さない）でレビューする（`plan-reviewer`・`code-reviewer`）
3. **最低限**：同じモデルでも、必ず新しい会話でレビューする。実装と同じ会話の中での見直しは、レビューとして扱わない

- 計画と同じモデルでレビューする場合は、計画を作った会話とは別の会話で行う
- どの段階でレビューしたかを、記録に書く

## 計画・コード共通の依頼

CodexにもClaude Codeにも「計画・コード共通の依頼」を渡す。役割の定義を使わずに依頼する場合も同じ項目を渡す。

```markdown
以下の範囲をレビューしてください。ファイルを変更しないでください。結果は日本語で書くこと。

- レビューの対象（計画本文または差分）：<計画本文、または確認する差分（対象コミットまたは未コミット差分の範囲）>
- 受け入れ条件：<AC-1…>
- 確かめる観点：<下の「確かめる観点」から今回の変更に当たるもの。Skill のルールへの違反は、Skill の名前とルールを根拠に書く>
- 合意済みの判断と参照先：<{{review_agreement_sources}}で参照できる合意済みの判断と理由。なければ「なし」>
- レビューの回数と範囲：<1回目は対象全体。2回目以降は前回の指摘と関連部分、対応した差分>
- 終了条件：<下記の指摘の基準と「終了と再レビュー」の条件を渡す>
- 報告：重大・軽微の件数、確認できなかった範囲、終了可否。指摘ごとに重大度・対象箇所・内容・根拠・修正案を書く。指摘がなければ「指摘なし」と書く。

{{review_finding_criteria}}
```

## Claude Codeで実装し、Codexでレビューする場合

計画レビューもコードレビューも、読み取り専用の `codex exec -s read-only` に、指示の文をファイルから渡して行う。`codex review` は、指示の文（観点・日本語・読むべき Skill・合意済みの判断）を渡せないため使わない。

| 用途 | 指示の文に入れる範囲 |
| --- | --- |
| 計画レビュー | 計画の本文そのもの（リポジトリの外のファイルを読めないことがあるため）。手元・CIの分担、対象の漏れと安全な実行の入口、CIに含まれない必須確認を観点に入れる |
| コミット前のコードレビュー | 「未コミットの変更（`git diff`・`git diff --cached`・`git status` で見える新しいファイル）をレビューする」 |
| ブランチ全体のコードレビュー | 「`git diff main...HEAD` の変更をレビューする」 |

指示の文は、作業用のフォルダのファイル（例：`<作業用フォルダ>/review-prompt.md`）に書き、標準入力から渡す（`-`）。長い指示の文をコマンドの引数に入れると、引数の長さの上限を超えて実行できないことがある。

依頼する側が、Skill「実装の進め方」の「委譲時の作業場所と状態」に従って指示文とログの置き場所を用意する。読み取り専用のレビュー担当には書き込みを求めない。

```bash
codex exec -s read-only - < "<作業用フォルダ>/review-prompt.md" > "<作業用フォルダ>/codex-review-1.log" 2>&1
```

コードレビューの指示には、`AGENTS.md`の「コードを書く前に、ルールを読んで従う（必須）」の表を読み、該当するSkill（`.agents/skills/<名前>/SKILL.md`、無ければ`.claude/skills/<名前>/SKILL.md`）をすべて読むことも含める。

### 実行時に必ず守ること

Codexは完了まで時間がかかり、失敗しても静かに終わることがある。「動いていない」と「時間がかかっている」を区別できるよう、次を守る。

- **標準入力は、指示の文のファイルにつなぐ**：`- < <指示の文のファイル>` の形にする。何もつながないと、入力待ちで止まることがある（指示の文を引数で渡す場合は `< /dev/null` を付ける）
- **出力はファイルに書き出す**：パイプ（`| tail`等）でつながず、ログのファイルへ直接書き出す。バックグラウンドで実行する
- **進み具合を見えるようにする**：起動後にログの末尾を確認して動いていることを確かめ、利用者にはログを見られる場所を伝える
- **出力が極端に短いときは、成功と見なさない**：数十バイトしかない・空の場合は、実行できていない可能性があるので、`git diff`などで実際の状態を確かめる
- **計画レビューでは、計画の本文を指示の文に直接入れる**：読み取り専用の設定では、リポジトリの外のファイルを読めないことがある
- **日本語での出力を指示する**：指示の最後に「結果は日本語で書くこと」を入れる。英語で返ってきた場合は、日本語にまとめ直して利用者に見せる
- 承認を必要としない通常のコマンドの失敗は、Codex自身がやり方を変えて続けることがあるため、それだけでレビュー全体の失敗と判断しない

## Codexで実装し、Claude Codeでレビューする場合

- Claude Codeを、計画や実装の経緯を渡さない新しい会話で起動し、「計画・コード共通の依頼」を渡す
- Claude Code側では、エージェント`code-reviewer`・`plan-reviewer`を使ってよい
- 出力はファイルに書き出し、極端に短い・空の場合は成功と見なさない（上と同じ）

## 確かめる観点

| レビュー | 観点 |
| --- | --- |
| 計画レビュー | 要件の漏れ、既存の動作の退行、テスト不足、過剰な設計、秘密情報の混入 |
| コードレビュー | 不具合、エラーのもみ消し、セキュリティ、影響範囲、テスト不足、テストを弱める変更、Skill のルールへの違反（AGENTS.md の表で該当する Skill）、共通のルール・既存の書き方との食い違い |

品質チェック（実行結果と要件の照合）とは範囲を重ねない。

## 指摘の扱い

- 統括は、指摘が要件・仕様に照らして妥当かを確かめ、採用しなかった指摘と理由も記録する。
- 参照できる合意済みの判断について前提と根拠が同じ場合は、判断の理由と参照先を伝える。その再指摘だけの往復は回数に数えない。合意を変更する必要がある場合は、統括が既存の手順で利用者に確認する。
- 計画の指摘は計画担当に、実装の指摘は実装担当（`implementer`）に修正を依頼する。既存テストの変更が必要なら、理由を統括に示し、テスト担当が要件に照らして変更する。実装を修正した後は品質チェックをやり直す。

## 終了と再レビュー

- 1回目は全体、2回目以降は指摘した箇所とその関連部分に絞る。計画レビューは必要な場合も原則2回以内とし、2回目に重大が残る場合に3回目を行う。コードレビューは最大3回とする。
- 重大な指摘は修正して独立して再レビューする。3回目でも重大が残る場合は先に進まず利用者に相談する。データ破損・認証の回避・情報漏えいにつながる指摘は、回数の上限を超えても解消するまで続ける。レビューを重ねてIssueが単独でマージできる大きさを明らかに超えた場合は、レビューを続けずに利用者に相談する。
- 統括は、重大が0件で、必要な範囲を確認でき、軽微の修正・後追い・採用しない理由を記録したことを確かめ、レビューを終了する。空・不完全な結果を「指摘なし」と扱わない。
- レビュー後に受け入れ条件・仕様・動作・安全の守りが変わった場合、または既存テストの期待値を変更したり、既存テストを削除・スキップしたりした場合は、文書・テストだけの差分でも独立して再レビューする。
- 軽微だけの修正で再レビューを省けるかは、統括が独立レビュー後に増えた差分を照合する。判定者（統括）、差分のファイルと行・元の指摘番号・受け入れ条件・仕様・動作・安全の守り・既存テストに影響しない理由を、下の記録先に残す。この照合は独立レビューの代わりにしない。判断に迷う場合は変更箇所を独立して再レビューする。回数の上限に達して必要な再レビューが残る場合は利用者に相談し、必要な独立確認を満たすまで先へ進まない。

## 記録（{{review_record_place}}に残す）

記録するのは統括。後追いは{{review_follow_up_place}}につなぐ。読み取り専用のレビュー担当には記録の編集やIssueの作成を任せない。

```markdown
## コードレビュー（1回目）
- レビューしたAI：Codex（段階1）
- 指摘：5件（重大1・軽微4）
- 採用：4件
- 採用しなかった指摘と理由：...
- 誤った指摘：1件（内容）
- 確認できなかった範囲・終了可否：...
- 再レビューを省く場合：判定者（統括）、差分のファイルと行・元の指摘番号、受け入れ条件・仕様・動作・安全の守り・既存テストに影響しない理由
- 後追いとする指摘：対象・担当・理由・追跡先
```

指摘の数・採用した数・誤った指摘の数は、どのAIがどの役割に向いているかを知見として確かめる根拠にも使う。
