# レビュー

作業の過程と結果は、すべて日本語で書く。

## レビューするAIの選び方

見落としの重なりを減らすため、次の優先順位で選ぶ。

1. **原則**：実装とは別の会社のAIでレビューする（Claude Codeで実装したらCodex、Codexで実装したらClaude Code）
2. **1が使えない場合**：同じ会社の別のモデルで、新しい会話（実装の経緯を渡さない）でレビューする（`plan-reviewer`・`code-reviewer`）
3. **最低限**：同じモデルでも、必ず新しい会話でレビューする。実装と同じ会話の中での見直しは、レビューとして扱わない

- 計画と同じモデルでレビューする場合は、計画を作った会話とは別の会話で行う
- どの段階でレビューしたかを、記録に書く

## Claude Codeで実装し、Codexでレビューする場合


| 用途 | コマンド |
| --- | --- |
| 計画レビュー | `codex exec -s read-only "<計画の本文と、確かめてほしい観点>"` |
| コミット前のコードレビュー | `codex review --uncommitted` |
| ブランチ全体のコードレビュー | `codex review --base main` |

### 実行時に必ず守ること

Codexは完了まで時間がかかり、失敗しても静かに終わることがある。「動いていない」と「時間がかかっている」を区別できるよう、次を守る。

- **標準入力を閉じる**：`< /dev/null`を付ける。付けないと、入力待ちで止まることがある
- **出力はファイルに書き出す**：パイプ（`| tail`等）でつながず、ログのファイルへ直接書き出す。バックグラウンドで実行する
- **進み具合を見えるようにする**：起動後にログの末尾を確認して動いていることを確かめ、利用者にはログを見られる場所を伝える
- **出力が極端に短いときは、成功と見なさない**：数十バイトしかない・空の場合は、実行できていない可能性があるので、`git diff`などで実際の状態を確かめる
- **計画レビューでは、計画の本文を指示に直接入れる**：読み取り専用の設定では、リポジトリの外のファイルを読めないことがある
- **日本語での出力を指示する**：指示の最後に「結果は日本語で書くこと」を入れる。英語で返ってきた場合は、日本語にまとめ直して利用者に見せる
- Codexが実行した個々のコマンドの失敗は、Codex自身がやり方を変えて続けることがあるため、それだけで失敗と判断しない

```bash
codex review --uncommitted < /dev/null > <作業用フォルダ>/codex-review-1.log 2>&1
```

## Codexで実装し、Claude Codeでレビューする場合

- Claude Codeを、実装の経緯を渡さない新しい会話で起動し、レビューを依頼する。依頼の文には、レビューの範囲（`git diff main...HEAD`等）・受け入れ条件・確かめる観点・「結果は日本語で書くこと」を入れる
- Claude Code側では、エージェント`code-reviewer`・`plan-reviewer`を使ってよい
- 出力はファイルに書き出し、極端に短い・空の場合は成功と見なさない（上と同じ）

## 確かめる観点

| レビュー | 観点 |
| --- | --- |
| 計画レビュー | 要件の漏れ、既存の動作の退行、テスト不足、過剰な設計、秘密情報の混入 |
| コードレビュー | 不具合、エラーのもみ消し、セキュリティ、影響範囲、テスト不足、テストを弱める変更、共通のルール・既存の書き方との食い違い |

品質チェック（実行結果と要件の照合）とは範囲を重ねない。

## 指摘の扱い

- 指摘はそのまま受け入れず、要件・仕様に照らして妥当かを確かめてから対応する。対応しない指摘は理由を記録する
- 重大度は「重大（直さないと進めない・マージできない）」「軽微」に分ける。データ破損・認証の回避・情報漏えいにつながるものは重大とする
- 合意済みの設計判断（ADR等）が再び指摘された場合は、回数に数えず、コードも変えない。既知のトレードオフである理由と参照先を伝えるだけにする
- 指摘に対応する修正は、実装の役割（`implementer`）が行い、品質チェックをやり直してから再レビューする

## 回数の上限

- 計画レビュー・コードレビューとも最大3回。1回目は全体、2回目以降は指摘した箇所とその関連部分に絞る
- 3回目でも重大な指摘が残る場合は、止まって利用者に判断を求める
- ただし、データ破損・認証の回避・情報漏えいにつながる指摘は、解消するまで続ける
- レビューを重ねてIssueが単独でマージできる大きさを明らかに超えた場合は、レビューを続けずに利用者に相談する

## 記録（{{issue_record_place}}に残す）

```markdown
## コードレビュー（1回目）
- レビューしたAI：Codex（段階1）
- 指摘：5件（重大1・軽微4）
- 採用：4件
- 採用しなかった指摘と理由：...
- 誤った指摘：1件（内容）
```

指摘の数・採用した数・誤った指摘の数は、どのAIがどの役割に向いているかを知見として確かめる根拠にも使う。
